## 요구 사항

- **Node 24.** `.nvmrc`가 `24`, `package.json`의 `engines.node`가 `>=24.0.0`이다. nvm-windows는 `nvm install 24 && nvm use 24`, fnm은 `fnm use --install-if-missing`.
- **pnpm 11.** 저장소가 `packageManager: "pnpm@11.10.0"`을 선언하지만, 그 값이 저절로 쓰이는 것은 **Corepack이 켜져 있을 때뿐이다.** 클론 직후 한 번 `corepack enable`을 실행한다(Node 24에 동봉되어 있다). 권한 오류가 나면 관리자 셸에서 한 번 실행하거나, Corepack을 쓰지 않고 `npm i -g pnpm@11`로 직접 설치한다 — `engines.pnpm`이 `>=11.10.0`이라 10.x로는 설치가 거절된다.
- **Docker Desktop 4.22 이상이 실행 중일 것.** 설치되어 있는 것만으로는 부족하다. 엔진이 떠 있어야 `docker compose`가 동작한다(`docker compose version`으로 Compose 2.20.2 이상을 확인). 루트 `compose.yaml`의 `include`가 Compose 2.20.0을, `docker/docker-compose.yml`의 헬스체크 `start_interval`이 2.20.2 스키마를 요구하고, `start_interval`은 Docker Engine 25(Desktop 4.27) 이상에서만 실제로 적용된다(ADR-0014).
- **Windows라면** 아래 [문제 해결](#문제-해결)의 첫 항목(WinNAT 예약 포트)을 기동 전에 먼저 읽는다. 안 읽으면 `docker compose up`이 bind 오류로 멈춘다.

## 로컬 실행

```bash
corepack enable                  # 한 번만. pnpm 11 을 packageManager 필드에서 가져온다
cp .env.example .env             # 기본값 그대로 로컬에서 동작한다
pnpm install

# Windows: 아래 "문제 해결 · WinNAT" 를 읽고 필요하면 먼저
#   cp compose.override.example.yaml compose.override.yaml   (+ .env 의 REDIS_URL/TEST_REDIS_URL)

docker compose up -d --wait      # postgres(5432) · redis(6379) · mailpit(1025/8025)
pnpm db:migrate                  # drizzle 마이그레이션 (스키마 + 롤 권한 + 프로필 트리거)
pnpm db:seed                     # 카테고리 5개(+세부 21개) + 판매 중지 충전 상품 5개 + 관리자 둘(관리자가 없을 때만) + 초안 시장 14개
pnpm dev                         # web(3000) · api(4000) · worker + 공유 패키지 watch
```

시간의 대부분은 `pnpm install`과 첫 이미지 pull이 쓴다. 나머지는 몇 초씩이다. PowerShell에서도 그대로 붙여 넣으면 된다 — `cp`는 `Copy-Item`의 별칭이다.

기동을 확인하는 자리:

- 웹 <http://localhost:3000>
- API 레디니스 <http://localhost:3000/api/health>(web rewrite 경유) 또는 <http://localhost:4000/api/health>. 워커는 <http://localhost:4100/health>.
- Mailpit UI <http://localhost:8025> — 가입 인증·비밀번호 재설정·이메일 변경 메일이 전부 여기로 온다. 이메일 가입은 **주소만** 입력하고, 메일의 인증 링크를 누르면 로그인된 뒤 `/set-password`에서 첫 비밀번호를 정한다(인증 전에는 비밀번호가 없어 로그인할 수 없다). 운영 메일은 AWS SES(`.env.example`의 `SMTP_*` 주석).
- 본인확인 인증번호(`/onboarding`, ADR-0070)도 로컬에서는 Mailpit으로 온다. `SMS_PROVIDER`가 비었거나 `dev`이면(운영 밖의 기본) 개발용 발송기가 문자 대신 `sms-<번호 숫자>@sms.buddha.local`로 메일을 보낸다(제목 `[buddha] 개발용 SMS: 본인확인 인증번호 123456`). 실제 문자는 알리고(`SMS_PROVIDER=aligo`와 `ALIGO_API_KEY`·`ALIGO_USER_ID`·`ALIGO_SENDER`, 알리고에 등록한 발송 서버 IP에서만 보내진다)로 가고, 운영(`NODE_ENV=production`)은 `dev`를 거절한다. 키가 없으면 발송이 실패해(`SMS_SEND_FAILED`) 아무도 본인확인을 마치지 못한다. 사업자의 답을 받지 못한 발송(시간 초과·5xx)은 `SMS_SEND_UNCONFIRMED`이고 문자가 갔을 수 있어 한도에 세며 그 인증번호를 쓸 수 있다. 번호 하나에는 계정 하나만 본인확인할 수 있다. 발송 한도(직전 24시간: 계정마다 10번, 계정·번호 쌍마다 10번, 한 번호에 계정 3개, 접속 주소(IP)마다 50번, 서비스 전체 500건)는 개발용 발송기의 발송도 센다 — 발송 기록은 탈퇴 뒤에도 보존기간 동안 두는 본인확인 기록이라 로컬 DB에서도 쌓인다. 다른 계정과 함께 세는 한도(번호의 계정 수·접속 주소·서비스 전체)의 다시 될 때는 분 단위로 답하고, 그 한도는 답한 분까지 닫혀 있다. 발송 수는 관리자 화면 `/admin/sms`에서 본다.
- 관리자 로그인은 `.env`의 `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD`(기본 `admin@buddha.local` / `admin1234!`). 이 두 값이 둘 다 없으면 `pnpm db:seed`가 관리자와 시드 시장을 통째로 건너뛴다. 2인 통제(같은 사람이 요청하고 승인하지 못한다)는 로컬에서도 서로 다른 관리자 둘이 필요하므로 둘째 관리자 `SEED_SECOND_ADMIN_EMAIL` / `SEED_SECOND_ADMIN_PASSWORD`(`.env.example` 기본 `admin2@buddha.local` / `admin5678!`)도 둔다. 첫째·둘째 모두 두 값을 함께 채우거나 함께 비운다 — 한 쌍에서 하나만 있거나(공백만 있는 값은 빈 값) 첫째 없이 둘째만 있으면 시드가 아무것도 넣지 않고 실패한다. 시드는 **관리자가 한 명도 없을 때만** 두 관리자를 만들고 부여 기록(사유 '시드')을 남긴다. 그 뒤에는 아무 계정도 만들거나 올리지 않고, 회수된 계정을 되돌리지도 않는다 — 관리자는 관리자 화면 `/admin/admins`에서 사유와 함께 부여·회수한다(아래 [관리자 계정과 2인 통제](#관리자-계정과-2인-통제)). 이미 관리자가 있는 DB에 둘째를 더하려면 그 화면에서 부여하거나 DB를 비우고 다시 시드한다. 시드 관리자는 화면의 부여 조건(이메일 인증과 휴대전화 본인확인)의 예외다: 시드가 이메일을 인증해 두고 본인확인은 하지 않으므로, 관리자도 **첫 로그인에서 `/onboarding`을 만나** 약관 동의·실명과 휴대전화의 SMS 본인확인·닉네임 설정을 마친다(시드는 자동 닉네임을 그대로 두고, 예전 시드가 준 '관리자'는 예약어라 닉네임 단계가 거절해 새로 정한다, ADR-0072) — 로컬에서도 운영에서도 같다(`/admin`도 게이트 예외가 아니고, 마칠 때까지 관리자 API도 `ONBOARDING_REQUIRED`로 거절한다, ADR-0043·ADR-0070·ADR-0072). e2e는 `admin`·`secondAdmin` 픽스처가 로그인 직후 API(동의, `POST /api/v1/me/phone-verification/code`·`/confirm`과 Mailpit에 온 인증번호, 닉네임 확정 — 지금 닉네임이 규칙에 걸리면 새 닉네임)로 두 관리자의 남은 온보딩을 마친다(이미 마쳤으면 건너뛴다).
- 가입 직후 온보딩(#58, ADR-0072): 로그인한 계정은 약관 동의(필수 이용약관·개인정보 수집·이용·'만 14세 이상입니다', 선택 마케팅 정보 수신 — 항목마다와 전체 동의, 판·시각·IP·브라우저를 기록) → 본인확인 → 닉네임 설정(자동 닉네임을 그대로 확정해도 된다) → 시작 Coin → 지급 안내 → 관심 카테고리(건너뛸 수 있다, 닉네임 단계 바로 뒤에 한 번만 보이고 지급 안내나 이 화면을 답하지 않고 떠나면(로그아웃도) 건너뛴 것이며 화면이 서버에 건너뛰기를 보낸다 — 닿지 않는 때는 ADR-0078 7-23. 작성 제한·계정 제한 중에도 받는 첫 선택은 닉네임 단계 뒤 24시간 안의 답뿐이고, 그 뒤의 고르기는 MY 설정의 바꾸기와 같아 제한 중에는 거절되며(작성 제한 #185는 끝나는 때와 '건너뛰기는 할 수 있습니다.'(오너 결정 2026-10-23 답 9), 조치·신고 내역 링크로, 제한이 없으면 늦은 고르기도 저장되고 단계를 답한다) 건너뛰기는 그대로 단계를 답한다, ADR-0078 오너 결정 2026-10-21 3차 답 1)를 거쳐 가입 전에 보던 화면으로 간다(근거 글 화면에서 가입·로그인해도 그 글로). 세 단계(동의·본인확인·닉네임) 가운데 마치지 않은 것이 있으면 약관·인증 화면을 뺀 어느 화면에서든 `/onboarding`의 남은 단계로 간다. 온보딩을 한 번 마친 뒤 재동의만 남은 계정은 로그인만으로 하는 동작의 화면(지금 근거 글 화면과 MY 설정)도 열어 자기 글을 지울 수 있고(지운 뒤 가는 커뮤니티 목록에서 남은 단계로 간다), 그 화면의 '수정'은 남은 단계를 거쳐 수정 화면으로 간다(ADR-0073, 오너 결정 2026-10-20). MY 설정에서는 공개 프로필의 소개를 비우고 관심 카테고리를 빼고 프로필 이미지를 지우며 계정 관리(이메일·비밀번호·로그인 연결·실명·시간대·테마)도 그대로 쓰고, 새 소개·카테고리 더하기·새 프로필 이미지·닉네임 바꾸기(서버도 온보딩을 마친 계정만 받는다)와 마케팅 정보 수신 켜고 끄기는 남은 단계를 거쳐 MY 설정으로 돌아오며, 그때 쓰던 소개·고른 카테고리·닉네임은 이 탭에 1시간 두었다가 단계를 마치고 돌아오면 되살린다(ADR-0078 7-24·7-25, 오너 결정 2026-10-21 답 2·2026-10-22 답 1·3·2026-10-22 (2차) 답 2; 프로필 이미지는 ADR-0079 결정 9 — 새 이미지는 파일을 고르기 전에 단계로 가므로 둘 것이 없다). 재동의 단계 화면에는 MY 설정으로 가는 링크가 있다(오너 결정 2026-10-22 답 2). 쓰기·수정 화면에서 보내질 때 쓰던 글은 이 탭에 1시간 두었다가 단계를 마치고 돌아오면 되살린다. 권리를 바꾸는 약관 개정 뒤의 재동의는 서지 않게 된 항목만 다시 묻고(마케팅 답은 그대로), 앞 단계로 돌려보내지면 그 까닭을 단계 제목 위에 보인다. 마케팅 정보 수신은 이메일만이고 MY 설정에서 언제든 켜고 끈다(바꿀 때마다 동의 기록). 소셜 로그인 제공자의 이름·사진은 묻지도 저장하지도 않는다(구글에는 `openid`·`email`, 카카오에는 `account_email`만 묻고, 네이버가 넘기는 항목은 개발자 콘솔에서 정한다 — ADR-0072 결과 3. better-auth `user.name`은 비고 `user.image`는 null이며 그 둘을 담는 제공자의 ID 토큰 `account.id_token`도, 제공자의 접근·갱신 토큰도 두지 않는다. `/api/auth/update-user`·`/api/auth/account-info`·`/api/auth/get-access-token`·`/api/auth/refresh-token`은 꺼짐). 세 단계(동의·본인확인·닉네임)를 마치지 않은 계정은 열람만 하고, 쓰기 라우트는 서버가 `OnboardedGuard`로 막는다(`ONBOARDING_REQUIRED`). 닉네임은 대소문자를 구분하지 않고 유일하며, 직접 입력한 닉네임은 `user_`로 시작하거나 운영자를 사칭하는 낱말(운영자·관리자·운영팀·공식·admin·buddha)을 담을 수 없고, 온보딩 뒤에는 30일에 한 번 바꾸며, 내려놓은 닉네임은 30일 동안 다른 계정이 쓰지 못한다. 시드 관리자도 첫 로그인에서 같은 온보딩을 거친다.
- 가입만으로는 Coin을 주지 않는다. 이메일·Google·Kakao·Naver 어느 경로든 새 계정은 잔고 0이고 원장이 비어 있다(#70, ADR-0071). 시작 Coin은 본인확인한 휴대전화 번호마다 한 번이다 — 탈퇴한 계정의 번호로 다시 가입해도 다시 주지 않는다(ADR-0069 결정 1 #57-1). 온보딩(#58, ADR-0072)의 닉네임 단계가 약관 동의·본인확인·닉네임을 서버에서 확인하고 같은 트랜잭션에서 내부 지급 기능(`StartGrantService`, 요청 경로 없음)을 부를 때 준다. 금액은 출시 설정 '시작 지급액'(`grant.start_coin`, `/admin/settings`)이고 아직 미정이다(N01 §10, #71·#133). 미정인 동안 지급은 기다리고 지갑과 MY 요약의 지갑 미리보기가 '시작 Coin은 준비되는 대로 지급됩니다.'를 보이며, 관리자가 값을 넣으면(상태와 상관없이) 워커의 `start_grant.pay`가 1분 안에 기다리던 계정에 그 값을 준다. 기다리는 동안 탈퇴하면 그 지급은 취소되고(#140이 부를 내부 기능 `cancelStartGrant`), 지급된 적이 없으니 그 번호의 다음 계정은 받을 수 있다(오너 결정 2026-10-18, ADR-0071). 번호는 `PHONE_HASH_KEY`를 키로 쓴 해시로만 기록되고, 운영자가 회원의 번호를 바꾸면 새 번호도 받은 번호로 기록한다. 번호 변경은 가입 이메일(계정의 지금 이메일 — 대체 주소의 계정은 MY 설정에서 실제 이메일을 먼저 등록한다)에서 발신 인증(보낸 주소의 도메인으로 SPF와 DKIM이 모두, 또는 DMARC가 통과)을 통과해 온 요청에만, 그 주소의 계정을 찾고 새 번호가 다른 계정이 본인확인한 번호도, 금액을 기다리는 다른 계정의 지급이 붙든 번호도 아닌지 미리 본 뒤 운영자가 새 번호로 문자로 보낸 6자리 확인 번호(30분, 한 요청에 세 번까지)를 회원이 그 이메일에서 답장으로 보내면 한다. 그 뒤에 그런 번호가 되었으면 바꿀 계정에 지급 기록이 없어도 SQL이 거절한다. 번호 변경을 거절할 때는 언제나 까닭 없이 '지금은 그 번호로 바꿀 수 없습니다'라고만 알린다 — 회원이 나중에 다시 요청하면 요청 확인부터 다시 한다(오너 결정 2026-10-19와 그 3차·4차, [docs/OPERATIONS.md](docs/OPERATIONS.md)). `PHONE_HASH_KEY`는 운영에서는 필수(32자 이상, `BETTER_AUTH_SECRET`과 달라야 한다)이고 **한 번 정하면 바꾸지 않는다** — 바꾸면 모든 번호가 처음 보는 번호가 되어 시작 Coin을 다시 받는다. 로컬·시험은 비워 두면 개발용 키를 쓰고, 운영은 저장소에 있는 개발용 키를 거절한다. 유료 충전·결제·쿠폰은 초기 제품에서 닫혀 있다(ADR-0049) — 아래 [유료 충전·결제·쿠폰(닫힘)](#유료-충전결제쿠폰닫힘).
- 소셜 로그인(Google/Kakao/Naver)은 `.env`에 그 프로바이더의 키 **쌍**을 넣을 때만 켜진다(Q-M1-1).

## 문제 해결

### `docker compose up`이 bind 오류로 죽는다 (Windows 전용)

```
bind: An attempt was made to access a socket in a way forbidden by its access permissions
```

Windows는 WinNAT/Hyper-V를 위해 100포트짜리 TCP 범위를 **동적으로** 예약하고, 그 안의 포트는 Docker가 게시할 수 없다. 범위는 부팅마다 옮겨 다니며, `docker/docker-compose.yml`이 쓰는 Redis 6379·6380과 Mailpit 8025가 자주 그 안에 들어간다. 지금 예약된 범위는 이렇게 본다.

```powershell
netsh int ipv4 show excludedportrange protocol=tcp
```

관리자 셸에서 `net stop winnat; net start winnat`으로 한 번 지울 수는 있지만 재부팅하면 다른 위치에 다시 생긴다. 영구적인 해법은 게시 포트를 범위 밖으로 옮기는 것이고, 그 파일이 저장소에 있다.

```bash
cp compose.override.example.yaml compose.override.yaml
```

Compose는 `compose.override.yaml`만 자동으로 읽는다(`.example.` 이름은 읽지 않는다). 복사본은 `.gitignore`에 있어 커밋되지 않으므로 머신마다 마음대로 고쳐도 된다. 옮긴 포트는 **컨테이너 안쪽이 아니라 호스트 쪽뿐**이며, 그만큼 `.env`와 e2e 환경 변수를 맞춰야 한다.

| 서비스     | 기본 | 오버라이드 | 맞춰야 하는 값                                                        |
| ---------- | ---- | ---------- | --------------------------------------------------------------------- |
| redis      | 6379 | 6479       | `.env`의 `REDIS_URL=redis://localhost:6479`                           |
| redis-test | 6380 | 6480       | `.env`의 `TEST_REDIS_URL=redis://localhost:6480`                      |
| mailpit UI | 8025 | 8125       | e2e의 `MAILPIT_URL=http://127.0.0.1:8125` (`apps/web/e2e/helpers.ts`) |

Mailpit UI도 그때부터 <http://localhost:8125>다. Postgres 5432/5433과 SMTP 1025는 예약 범위를 피해 다녀서 그대로 둔다.

### `pnpm install`이 `ERR_PNPM_IGNORED_BUILDS`로 실패한다

pnpm 11은 `strictDepBuilds`가 기본 `true`라, 검토되지 않은 (post)install 스크립트를 가진 의존성이 하나라도 있으면 설치를 실패시킨다. 판단은 `pnpm-workspace.yaml`의 `allowBuilds`에 적혀 있다(`esbuild`·`msgpackr-extract`는 허용, `fsevents`·`@scarf/scarf`는 금지). 새 의존성을 추가하다 이 오류를 만나면 그 항목을 `allowBuilds`에 명시적으로 넣거나 `pnpm approve-builds <pkg>`를 실행하고, 결과를 커밋한다 — 오류를 지우려고 스크립트를 무턱대고 켜지 않는다.

같은 파일 아래쪽의 `minimumReleaseAgeExclude`는 다른 이야기다. pnpm 11은 배포된 지 24시간이 안 된 버전을 기본적으로 경계하는데(`minimumReleaseAge`), 카탈로그가 그런 버전을 고정하고 있으면 설치는 해 주되 이 목록을 파일 끝에 **덧붙인다**. 그 목록은 반드시 커밋한다: 없으면 CI의 `pnpm install --frozen-lockfile`이 락파일을 거절한다.

### 에디터가 `@buddha/*` 타입을 못 찾는다

공유 패키지는 컴파일된 `dist/`만 export한다. `pnpm build`(또는 `pnpm dev`)를 **한 번** 돌리면 잡힌다. 같은 이유로 `pnpm db:migrate`/`db:seed`는 실행 전에 `@buddha/shared`를 먼저 빌드한다(Turbo `dependsOn: ^build`) — 스키마 enum 값이 공유 패키지에서 오기 때문이다.

### `pnpm test` / `pnpm check`가 연결 오류로 실패한다

`packages/db`와 `apps/api`의 통합 테스트는 개발 DB를 절대 건드리지 않고 **test 프로필**(5433/6380)만 쓴다. 기본 `.env`가 `TEST_*`를 채워 두므로, 그 프로필이 떠 있지 않으면 globalSetup이 연결 오류로 죽는다.

```bash
docker compose --profile test up -d postgres-test redis-test
```

`TEST_*`를 비우면 해당 스위트를 건너뛴다(CI에서는 `CI=true`라 건너뛰지 않고 실패한다).

### `pnpm --filter web start`가 BUILD_ID 불일치로 종료한다

```
standalone output is stale (BUILD_ID ... != ...)
```

`.next/standalone/**`은 Turbo 캐시에서 제외되어 있다(ADR-0016 — Windows에서 pnpm 심링크 경로가 캐시 tar에 들어가지 않았다). 그래서 빌드가 캐시 히트하면 `.next/BUILD_ID`만 복원되고 standalone 복사본은 이전 빌드의 것으로 남는다. 안내대로 강제 재빌드한다.

```bash
pnpm turbo run build --filter=web --force
```

### 다른 기기에서 웹이 안 열린다

기본값은 전부 루프백이다. API는 `.env`의 `API_HOST`(기본 `localhost`), 웹 dev 서버는 `next dev --hostname localhost`, 로컬 standalone 실행은 `WEB_HOST`(기본 `localhost`)를 따른다. Next 기본값(모든 인터페이스)이면 `/api/*` rewrite를 통해 API까지 LAN에 노출되기 때문이다(ADR-0015). Next는 주소 하나에만 바인드하므로 Node 24에서는 `::1`만 열린다 — `http://localhost:3000`은 브라우저·curl·fetch 모두 정상이고 `http://127.0.0.1:3000`은 거부된다.

정말 열어야 한다면 웹 포트만으로는 부족하다. M4부터 브라우저가 실시간 소켓 때문에 API에 직접 붙으므로(아래 [아키텍처](#아키텍처)) 그 기기에서 API도 닿아야 한다: `pnpm --filter web exec next dev --port 3000 -H 0.0.0.0` + `next.config.ts`의 `allowedDevOrigins`, `API_HOST=0.0.0.0`, 그리고 빌드 시점에 번들로 들어가는 `NEXT_PUBLIC_API_URL`과 핸드셰이크를 통과시킬 `WEB_ORIGIN`이 실제 주소와 맞아야 한다.

### 시드 시장을 열 수 없다 (`VALIDATION_ERROR`, `closeAt`)

시드 시장은 검수 전 초안(`draft`)이고 `rules`가 정한 절대 마감 시각(KST)을 갖는다. 그 시각이 지난 초안은 관리자 열기가 `closeAt`을 지목한 400(`VALIDATION_ERROR`)으로 거절된다. 관리자 시장 상세의 수정에서 마감 시각을 미래로 옮긴 뒤 연다. `pnpm db:seed`는 실행마다 마감이 지났거나 14일 안에 마감되는 시드 시장을 경고한다 — 근본 해법은 새 slug로 시드 문안을 바꾸는 것이다.

## 아키텍처

```
                                  [Browser]
 |
             +------------------------+---------------------+
| HTML + REST (same-origin /api/*) | Socket.IO /ws
             v                                              | (NEXT_PUBLIC_API_URL)
   [apps/web  Next.js :3000]                                |
     SSR / RSC                                              |
     rewrite  /api/:path*  -------------------+             |
     src/lib/api.server.ts -------------------+             |
       (bypasses the rewrite)                 |             |
                                              v             v
                             [apps/api  NestJS + Fastify :4000]
                               /api/auth/*   better-auth
                               /api/v1/*     REST + rate limit + security headers
                               /ws           Socket.IO gateway
                               /api/health   readiness    /api/health/live   liveness
 |
              +---------------------------+----------------------+
              v                           v                      v
     [Postgres :5432]                    [Redis :6379]    [Mailpit :1025 / :8025]
       Drizzle                             pub/sub        SMTP -> AWS SES
              ^                            BullMQ queues
| rate-limit buckets
| ^
              +-----------+---------------+          [media store]
| dev: ./.media   prod: private S3 bucket
            [apps/worker  BullMQ  /health :4100]       (api writes and serves, worker deletes)
              markets : market.close, market.finalize
              audit   : ledger.audit (04:00 KST)
              wallet  : start_grant.pay (every minute)
              media   : media.orphan_cleanup (hourly, :17)
              community : community.records_purge (hourly, :37)
```

- **브라우저가 API로 가는 길은 두 개다.** REST와 문서는 Next의 서버 사이드 rewrite(`/api/:path*`)를 타서 같은 오리진으로 남고, Socket.IO만 `NEXT_PUBLIC_API_URL`(기본 `http://localhost:4000`)에 **직접** 붙는다. Next rewrite가 WebSocket 업그레이드를 프록시하지 않기 때문이다(Q-M0-2, ADR-0017). `WEB_ORIGIN`이 그 핸드셰이크의 CORS와 Origin 검사를 함께 결정한다.
- **서버 사이드 호출은 rewrite를 타지 않는다.** `apps/web/src/lib/api.server.ts`(공개 읽기 전용)와 `session.server.ts`는 API 오리진을 직접 부른다. 상대 경로는 서버 컴포넌트가 fetch할 수 없고, 세션 쿠키는 의도적으로 전달하지 않는다.
- **Redis는 세 가지 일을 겸한다.** 실시간 pub/sub(API 게이트웨이와 워커가 함께 쓴다), BullMQ 큐와 지연 잡, 레이트 리밋·멱등성 키. 워커는 API와 직접 말하지 않고 Postgres와 Redis만 통해 붙는다(PLAN §9).
- **워커가 발행하면 게이트웨이가 중계한다.** `market.close`·`market.finalize`(API가 마감 시각에 맞춰 예약하는 지연 잡과 판정 직후 바로 넣는 잡 + 매 분 안전망 스캔), `ledger.audit`(매일 04:00 KST), `start_grant.pay`(매 분, 시작 지급액이 정해져 있으면 지급을 기다리던 계정에 준다, #70). 잡 결과는 Redis로 나가고, `/ws` 게이트웨이가 그것을 브라우저의 방으로 밀어 준다. 이벤트 목록·룸·순서 키는 [docs/API.md](docs/API.md)의 실시간 절.
- **메일은 API만 보낸다.** 워커에는 메일러가 없다.
- **작성 빈도 제한과 반복 링크는 DB에서 센다(#187, ADR-0083).** 글·댓글·수정·이미지 업로드는 쓰는 트랜잭션 안에서 본인확인한 번호의 키 있는 해시마다 한 줄(`write_limit_events`)을 남기고, 한도(`packages/shared/src/write-limits.ts`의 `WRITE_LIMITS` — 오너의 고정값, 출시 설정이 아니다)는 그 줄을 지난 10분·1분·24시간으로 센다. 넘으면 `WRITE_LIMITED`(429)이고 아무것도 쓰지 않는다. 글·댓글의 링크(본문 순서로 앞의 20개)는 견준 모양으로 `link_uses`에 남고, 반복 규칙에 맞으면 `link_flags`(운영자 검토 목록 — 운영자의 '확인함' 표시는 `admin_actions`)에 오를 뿐 거절하지 않는다. 두 기록은 24시간에 한 시간이 더 지나면 워커가 지운다(`community.records_purge` — 한 시간은 진행 중인 셈이 아직 넣는 기록을 남기는 여유다). 운영자가 회원의 번호를 바꾸면 지난 24시간의 두 기록도 새 번호로 옮긴다(docs/OPERATIONS.md). 검토 목록은 보존기간이 지나면 #184가 지운다. Redis의 레이트 리밋(아래 'M6에서 들어온 것')과는 따로다 — 그것은 접속 주소마다의 짧은 창이다.
- **글의 이미지와 프로필 이미지는 API를 거쳐서만 오간다(#46, ADR-0073; #141, ADR-0079).** 브라우저는 파일을 `POST /api/v1/media/images`(글)나 `PUT /api/v1/me/profile-image`(프로필)로 보내고, API가 내용으로 검사·변환(EXIF 제거, 글은 긴 변 2,048px, 프로필은 가운데를 자른 정사각형 — 512px까지 줄이고 키우지 않는다. 둘 다 긴 변이 짧은 변의 32배를 넘는 아주 가는 이미지는 변환이 화소보다 훨씬 많은 메모리를 써서 받지 않고, PNG는 채널·비트·인터레이스의 종류마다 잰 한 프레임까지만 받는다 — 알파가 있는 PNG와 16비트 RGB, 인터레이스 RGB는 5,000만보다 작아 8비트 RGBA는 1,970만 화소이고, 알파가 없는 회색과 인터레이스가 아닌 8비트 RGB는 전의 값 그대로(5,000만, 인터레이스 16비트 회색만 약 4,194만)다, 오너 결정 2026-10-21 (2차). 다시 인코딩하는 몫까지 변환 하나가 프로세스의 메모리를 144MiB 넘게 올리지 않도록 인코더 설정을 고르고, 움직이는 WebP는 장면마다 105만·모두 1,200만, 움직이는 GIF는 장면마다 500만, 성분이 넷(CMYK)인 점진적 JPEG는 약 959만 화소까지만 받으며, 알파가 있는 정지 WebP는 풀 때의 한도(약 895만 화소)까지 받아 340만 화소 안으로 줄여 저장한다(정사각이면 1,843px, 오너 결정 2026-10-22) — 그 값들은 잰 것이라 sharp·libvips를 올리거나 2,048px이나 인코더 설정을 바꾸면 [scripts/image-memory/](scripts/image-memory/)로 다시 잰다 — CI에서는 돌지 않는다. 프로필 이미지는 비율·PNG 종류마다의 한 프레임·JPEG와 정지 WebP의 한도·변환 하나의 몫(144MiB)과 인코더 설정을 같은 값으로 지나고(그 정사각형 변환으로 다시 재었다), 움직이는 WebP는 첫 장면만 정지 이미지로 세어 장면의 한도를 걸지 않으며, 다만 파일에서 정사각형을 먼저 자르는 긴 WebP는 통째로 풀리므로 화소마다 17바이트로 세어 약 790만 화소까지 받는다(GIF는 받지 않고, 512px 이하라 340만 화소로 줄여 쓰는 것은 걸리지 않는다) — ADR-0079 결정 4·10)해 저장소에 쓴다. 읽기도 `GET /api/v1/media/:id`가 지금 보이는 글이 쓰는 이미지와 회원의 프로필이 지금 가리키는 이미지만 돌려준다(프로필 이미지는 바꾸거나 지우면 곧바로 지우고, 저장소가 그 파일을 지우지 못하면 키를 아래의 `media_deletions`에 남겨 워커가 다시 지운다 — 오너 결정 2026-10-22, ADR-0079 7-5). 저장소는 `@buddha/storage` 하나의 인터페이스이고 `MEDIA_STORAGE`가 고른다: 개발·e2e는 저장소 루트의 `.media/`(git이 무시한다, `MEDIA_LOCAL_DIR`로 옮긴다), 운영은 비공개 S3 버킷(`MEDIA_S3_*`, `terraform/media.tf`). 어느 글도 24시간 안에 가져가지 않은 업로드는 워커가 매시 지운다(저장소가 그 객체 지우기를 거절하면 키를 `media_deletions`에 남겨 뒤의 실행이 다시 지운다. API가 객체를 쓴 뒤 행을 쓰지 못한 업로드의 객체를 곧바로 지우지 못해도 그 키를 같은 표에 넣는다). 이미지 읽기는 접속 주소마다의 기본 한도(분당 100) 대신 따로 분당 600에 든다(304 포함). 보내는 중인 이미지는 API 프로세스 전체에서 32MiB까지 쥐고(저장소에서 읽는 중에 클라이언트가 끊어도 그 읽기가 멈출 때까지), 넘는 읽기는 429와 `Retry-After`다(천천히 읽거나 읽다 끊는 클라이언트가 API의 메모리를 채우지 못하게). 웹은 글 화면의 이미지와 카드의 썸네일에서 그 429를 `Retry-After` 뒤에 다시 받는다(이미지마다 세 번까지. 수정 화면 편집기 안의 저장된 이미지는 다시 받지 않는다, ADR-0073 9-39). 업로드의 본문은 다른 출처가 아니고, 쿠키의 세션이 better-auth에 있으며, 온보딩을 마친 계정일 때만 읽는다(아니면 읽지 않고 403·401·409). 그런 업로드도 계정마다 한꺼번에 셋까지(답이 끝나고 그 변환·저장도 끝날 때까지 하나로 센다 — 클라이언트가 먼저 끊어도), API 프로세스 전체에서 한꺼번에 받는 본문 64MiB 안에서만 읽는다(오너 결정 2026-10-21): 밝힌 `Content-Length`만큼(밝히지 않은 본문은 10MiB) 잡고 본문을 다 받거나 요청이 끝나면 돌려주며, 계정의 넷째나 예산을 넘는 업로드는 읽지 않고 429와 `Retry-After`(편집기는 그만큼 기다려 두 번까지 다시 올리고 그래도 거절되면 그 파일의 실패만 알린다, 오너 결정 2026-10-22 (2차)), 10MiB 넘게 밝힌 본문은 413, 30초 동안 한 바이트도 오지 않거나 읽기 시작한 지 2분 안에 다 오지 않는 본문은 끊고 408이다(계속 보내도 2분이면 끊는다 — 오너 결정 2026-10-22 (2차)). 업로드의 본문·변환·이미지 읽기는 API의 메모리도 본다(오너 결정 2026-10-22): 프로세스의 상주 메모리(RSS)와 이미 내준 몫에 제 몫(본문의 길이, 변환 하나의 144MiB, 읽는 이미지의 바이트)을 더해 한도(`API_MEMORY_CEILING_MIB` — 비우면 프로세스의 메모리 한도에서 32MiB를 뺀 값으로 api 컨테이너의 448MiB에서 416MiB, 한도가 없는 개발·시험에서는 보지 않는다)를 넘으면 기다리고(업로드 10초, 변환은 대기열에 든 때부터 10초, 읽기 2초) 그래도 자리가 나지 않으면 429와 `Retry-After`다(본문은 읽지 않고, 변환은 아무것도 저장하지 않는다). 업로드 본문과 변환은 이미지 읽기의 몫(32MiB 가운데 빈 것)도 남겨 두고, 이미지 읽기는 도는 변환을 기다리지 않는다. 배포한 뒤 요청이 없을 때 api 컨테이너의 메모리를 `docker stats`로 확인한다 — 그 값에 변환 하나(144MiB)와 읽기의 몫(32MiB)을 더해 한도 안이어야 업로드가 변환된다(오너가 할 일, 절차는 [docs/OPERATIONS.md](docs/OPERATIONS.md)의 'API 컨테이너의 메모리 확인'). api 이미지는 glibc가 큰 할당을 놓는 대로 돌려주게 `MALLOC_MMAP_THRESHOLD_=131072`로 뜬다(`Dockerfile` — 없으면 변환이 쥔 메모리가 RSS에 남아 가장 비싼 변환 몇 개면 448MiB를 넘었다). 운영 DB 초기화(`deploy/reset-db.sh`)는 버킷도 비운다.

PLAN 부록 C의 다이어그램은 M4 이전 그림이라 위와 다르다(브라우저가 rewrite로만 API에 닿고, Mailpit이 없다).

### M6에서 들어온 것

- **레이트 리밋** — 한도 표는 `packages/shared/src/rate-limit.ts` 한 곳에 있고(클라이언트도 읽는 계약이다), 구현은 `apps/api/src/rate-limit/`에 있으며 카운터는 Redis에 있다 — 주소별 한도는 파싱·핸들러보다 앞서 도는 Fastify 훅(`address-limit.ts`, 파싱 실패·404까지 센다. 이미지 읽기 `GET /api/v1/media/:id`는 기본 버킷이 아니라 자기 버킷 `mediaRead`에), 지목한 버킷은 `/api/v1/*`에서는 Nest 가드(`@RateLimit`), `/api/auth/*`에서는 better-auth의 `hooks.before`(`auth.ts`)다. 버킷·헤더·면제는 [docs/API.md](docs/API.md)의 레이트 리밋 절. **주의: 주소별 기본 한도는 클라이언트를 지목할 수 없는 피어에게 적용되지 않는다.** 브라우저 요청은 Next rewrite라는 서버 사이드 프록시를 거쳐 오므로 Fastify가 보는 주소는 방문자가 아니라 웹 서버의 것이고, Next가 채우는 `X-Forwarded-For`는 클라이언트가 덮어쓸 수 있어 `TRUST_PROXY`는 `false`로 둔다(A-M0-13, ADR-0034). 그래서 "클라이언트를 지목할 수 없는 주소는 아예 세지 않는다"가 규칙이다 — 전부 한 통에 넣으면 방문자 전체가 하나의 100/분을 나눠 쓰게 된다. 루프백은 내장이고, **웹 서버를 다른 호스트·컨테이너에 두는 배포는 그 주소를 `RATE_LIMIT_UNCOUNTED_PEERS`에 적어야 한다** — 비워 두면 사이트 전체가 한 통이다. 근거는 `apps/api/src/rate-limit/rate-limit.tracker.ts`에 길게 적혀 있다. 방문자별 한도를 되살리는 것은 웹 서버 **앞**에서 `/api/*`를 API로 바로 넘기며 `X-Forwarded-For`에 방문자를 덧붙이는 리버스 프록시와 그 CIDR을 담은 `TRUST_PROXY`다 — 그래도 웹 호스트는 목록에 남는다(SSR과 서버 컴포넌트의 세션 호출은 여전히 거기서 온다). 계정별·이메일별 버킷은 rewrite 뒤에서도 처음부터 정상 동작한다.
- **요청 로깅** — `LOG_LEVEL`이 이제 `apps/api`에도 적용된다(`apps/api/src/logger.ts`). 워커와 같은 모양의 pino로 요청 한 건이 한 줄의 JSON이 되고(개발에서는 pino-pretty), 요청마다 생성한 id로 도착·완료·핸들러 로그가 한 줄기로 묶인다. 기본값은 개발 `debug` / 운영 `info`. URL은 쿼리 문자열을 떼고 남기고(관리자 검색어가 로그에 남지 않도록) 매칭된 라우트 패턴을 함께 적는다.
- **헬스체크** — `GET /api/health`는 **레디니스**(db·redis를 각각 2초 상한으로 프로브하고, 하나라도 실패하면 같은 본문 모양으로 503), `GET /api/health/live`는 **라이브니스**(아무것도 프로브하지 않는다). 둘을 바꿔 물리면 Redis가 한 번 흔들렸다는 이유로 컨테이너가 재시작된다. 워커의 `GET :4100/health`도 `uptimeSeconds`와 소비 중인 큐 이름을 함께 답한다(200/503의 뜻은 그대로).
- **보안 헤더** — API는 `@fastify/helmet`과 모든 응답의 `X-Robots-Tag: noindex`(`apps/api/src/infra/http/security-headers.ts`, ADR-0075), 웹은 `next.config.ts`의 `headers()`가 각자 붙인다. `/api/*`로 프록시되는 응답에는 웹이 헤더를 덧붙이지 않는다 — 한 응답에 CSP가 둘이면 브라우저가 교집합으로 강제해서, 어느 파일에도 적혀 있지 않은 정책이 만들어진다.

## 배포

운영은 **AWS EC2 `t4g.small` 한 대**(`ap-northeast-2`)에 Docker Compose로 올라간다 — Caddy가 `https://buddha.sboh.dev` 하나의 오리진에서 `/api/*`·`/socket.io/*`를 api로, 나머지를 web으로 넘기고, Postgres·Redis는 같은 호스트의 별도 EBS(`/data`, 일일 스냅샷)에 산다. 내부 테스터 3명용 최소 비용 구성(월 ≈ $22)이고, 그렇게 정한 이유와 재검토 조건은 [ADR-0040](docs/DECISIONS.md)에 있다. 앱 코드는 로컬과 같다 — 위 아키텍처 그림에서 브라우저가 API에 닿는 두 길(Next rewrite, `NEXT_PUBLIC_API_URL` 직접 연결)이 운영에서는 둘 다 Caddy를 지난다는 점만 다르다.

- **인프라**는 [terraform/](terraform/README.md)(리소스는 전부 `tf-buddha-` 접두사, 부트스트랩·롤백·복구·시크릿 교체 절차가 그 README에 있다).
- **호스트에서 도는 것**은 [deploy/](deploy/)(`compose.yaml` · `Caddyfile` · `deploy.sh` · `host-setup.sh` · `reset-db.sh`) — api 이미지에 동봉되어 배포마다 `/data/buddha`에 풀린다. 이미지는 루트 `Dockerfile`의 세 타깃(`api` / `worker` / `web`)이다.
- **배포**는 `main`에 push하면 [.github/workflows/deploy.yml](.github/workflows/deploy.yml)이 arm64 이미지를 ECR에 밀고 SSM으로 호스트에서 `migrate && seed` → 컨테이너 교체 → `/api/health` 스모크까지 한다. 롤백은 `gh workflow run deploy.yml --ref main -f image_tag=<sha>`. SSH는 없고 셸은 `aws ssm start-session`이다.
- **#70 배포**: 배포 **전에** `PHONE_HASH_KEY`를 만드는 `terraform apply`(terraform/README.md), 배포 **뒤에** 오너가 정한 때 운영 DB 초기화 — #70 전에 가입해 10,000 Coin을 받은 계정이 시작 Coin을 또 받지 않게 한다(오너 결정 2026-10-18, [docs/RESET.md](docs/RESET.md#70-배포-때-오너-결정-2026-10-18)).
- **운영자의 손 작업**(회원의 휴대전화 번호 바꾸기 등)은 [docs/OPERATIONS.md](docs/OPERATIONS.md). 해시가 필요한 일은 api 컨테이너의 해시 CLI(`apps/api/dist/identity/phone-hash-cli.js`)로 한다 — 키는 그 컨테이너 밖으로 나오지 않는다.
- **운영 DB 초기화**는 [docs/RESET.md](docs/RESET.md). #125의 배포가 마이그레이션 0017로 계정까지 한 번 비우고 시드로 다시 채웠다. 다시 비울 때는 호스트에서 `deploy/reset-db.sh`가 같은 문장을 돌리고 Redis도 비운다(계정까지 모두). #149의 출시 전 재초기화가 이 절차를 쓰고, 다시 할지와 남길 데이터는 #133이 정한다 — 무엇이든 남기기로 하면 그 전에 이 절차를 좁힌다. 지금은 출시 설정의 값과 변경 기록(`release_settings`, `admin_actions`)도 함께 비운다.

## 유료 충전·결제·쿠폰(닫힘)

초기 제품은 유료 충전·결제·쿠폰을 쓰지 않는다(N06, D9, [ADR-0049](docs/DECISIONS.md)). 코드와 테이블은 남아 있고, 스위치는 `packages/shared/src/constants.ts`의 `PAID_COIN_SALES_ENABLED`(지금 `false`) 하나다 — env나 DB 값이 아니라 API와 웹이 같은 빌드에서 읽는 상수다.

- **API.** 공개 `GET /api/v1/charge-packages`·`GET /api/v1/payments/provider`, `POST /api/v1/payments/charge`, `POST /api/v1/coupons/redeem`, 관리자 `POST /api/v1/admin/payments/:id/refund`가 무엇을 읽거나 쓰기 전에 `404 NOT_FOUND`(`Not available`, 기능 이름 없음)로 답한다(`PaidCoinSalesGuard`). 관리자 충전 상품·쿠폰 관리와 결제 목록, 본인 결제 내역 `GET /api/v1/me/payments`는 열려 있다.
- **웹.** 지갑의 충전·쿠폰·결제 내역, 공개 `/charge`(404)와 푸터의 충전 안내 링크, 관리자 메뉴의 충전 상품·쿠폰·결제, `/admin/payments`의 환불 버튼을 그리지 않는다. 컴포넌트 파일은 남아 있다. 막힌 응답을 만나는 화면은 '이용할 수 없습니다.'만 보인다.
- **결제 프로바이더는 mock 하나다**(`PAYMENT_PROVIDER=mock`, 돈이 움직이지 않고 바로 충전). 스마트로페이 연동(ADR-0042)은 다른 PG를 쓰기로 해 지웠고, `PAYMENT_PROVIDER=smartro`면 API가 기동하지 않는다. 운영 compose는 api에 `mock`을 그대로 준다.
- **시험.** 보존한 충전·쿠폰·환불의 API 시험은 `createTestApp({ paidCoinSales: true })`로 판매를 켠 앱에서 돌고, `apps/api/src/payments/paid-coin-sales.test.ts`와 e2e `payment.spec.ts`가 닫힌 상태를 고정한다.
- **다시 열기**(#111이 정한다). 상수를 `true`로 바꾸고, 닫힌 상태를 고정한 시험(`packages/shared/src/constants.test.ts`, 위 두 시험)을 고친 뒤 main에 머지한다(자동 배포). env·terraform·DB는 바꿀 것이 없다. 그대로 열면 충전은 mock이므로 실제 판매에는 다음 PG 연동이 먼저다.

## 관리자 계정과 2인 통제

관리자 권한은 `profiles.role = 'admin'` 하나이고, 같은 사람이 요청하고 승인하지 못하게 하는 2인 통제 규칙을 공용으로 둔다(#171, [ADR-0056](docs/DECISIONS.md)).

- **부여·회수.** 기존 관리자가 `/admin/admins`에서 사유와 함께 하고, 다른 관리자의 승인은 받지 않는다. 부여는 이메일 인증과 휴대전화 본인확인(ADR-0070)을 마친 계정에만 된다. 회수는 관리자가 2명 미만이 되면 자기 회수까지 거절되고, 회수된 계정은 모든 세션이 지워져 모든 기기에서 로그아웃되며 다음 요청부터 관리자 기능을 쓰지 못한다. 부여·회수마다 작업자·대상 계정·시각·사유가 `admin_actions`(`admin_grant`·`admin_revoke`)에 남고, 같은 화면의 권한 변경 기록에서 본다. API는 `GET`·`POST /api/v1/admin/admins`, `POST /api/v1/admin/admins/{userId}/revoke`, `GET /api/v1/admin/admins/changes`([docs/API.md](docs/API.md)).
- **기록 접근.** 운영 기록(원장 감사 실패, 출시 설정 변경 기록, 권한 변경 기록, 신고와 운영 조치의 기록 — 신고자 포함, 다만 관리자 자신에 관한 신고·조치에서는 그 관리자에게 신고자·신고 설명·운영자가 보이지 않는다, #50·ADR-0081 — , 앞으로의 작업 기록)은 모두 `/admin` 아래에 있고 관리자라면 누구나 본다. 모든 `/admin` 라우트가 `SessionGuard`·`AdminGuard`·`OnboardedGuard`를 이 순서로 거는지 `apps/api/src/admin/admin-access.test.ts`가 확인한다 — 관리자가 아닌 계정은 403, 온보딩(약관 동의·본인확인·닉네임)을 마치지 않은 관리자는 409 `ONBOARDING_REQUIRED`다(ADR-0072).
- **2인 통제.** `ApprovalService`(`apps/api/src/approvals`)와 `approval_requests` 표: 요청을 남기고, 요청한 계정이 아닌 관리자만 한 번 승인·거절한다. 로컬·CI·내부 배포·출시 어디서도 끌 수 없다. 아직 이 규칙을 쓰는 작업은 없고, 개설 검수(#78)·판정 승인(#152)·보상 승인(#144)·봇 통제(#130)·계정 제한(#139) 등이 각자 붙인다.
- **시드의 관리자 둘.** `pnpm db:seed`는 관리자가 한 명도 없을 때만 `SEED_ADMIN_*`와 `SEED_SECOND_ADMIN_*`(선택. 각 쌍의 두 값을 함께 채우거나 함께 비우고, 하나만 있거나 첫째 없이 둘째만 있으면 시드가 실패한다)로 관리자 둘을 만들고 각자 부여 기록(사유 '시드')을 남긴다. 화면의 부여 조건을 거치지 않는 유일한 길이다. 관리자가 이미 있는 DB에는 아무도 만들거나 올리지 않으므로, 둘째를 더하려면 화면에서 부여하거나 DB를 비우고 다시 시드한다. 운영은 terraform의 `seed_second_admin_*`가 호스트 `.env`의 `SEED_SECOND_ADMIN_*`가 된다([terraform/README.md](terraform/README.md)).

## 테스트

단위·통합 테스트(`pnpm test`)는 docker의 **test 프로필**(5433/6380)을 쓴다. 위 [문제 해결](#pnpm-test--pnpm-check가-연결-오류로-실패한다) 참고.

e2e는 반대로 **개발 스택 전체**를 쓴다(test 프로필이 아니라 `.env`의 기본 DB다). 준비는 한 번만 하면 된다.

```bash
pnpm --filter web exec playwright install chromium   # 버전은 @playwright/test 와 맞아야 한다
docker compose up -d --wait                          # Mailpit 포함
pnpm db:migrate && pnpm db:seed                      # 스펙이 관리자 API로 시장을 직접 만든다
pnpm dev                                             # 이미 떠 있으면 그대로 쓴다
pnpm --filter web test:e2e
```

- 다른 웹 오리진은 `E2E_BASE_URL`로 가리킨다. 가입 흐름은 `MAILPIT_URL`(기본 `http://127.0.0.1:8025`)의 메일함을 폴링한다. 본인확인 인증번호도 그 메일함에서 읽으므로 API가 개발용 발송기(`SMS_PROVIDER` 비움이나 `dev`)로 떠 있어야 한다. 가입마다 새 휴대전화 번호를 쓴다(번호 하나에 계정 하나). 시험의 계정은 온보딩을 API로 마치고(`completeOnboardingThroughApi`: 동의 → 인증번호 → 자동 닉네임 확정 → 관심 카테고리 건너뛰기), 화면의 단계는 `onboarding.spec.ts`·`phone-verification.spec.ts`가 본다. 시작 지급액은 e2e DB에서 미정이어야 한다 — 값을 넣으면 워커가 모든 시험 계정에 지급해 잔고 0을 보는 시험이 깨진다(ADR-0072 결정 7-22). 전체를 한 번 돌 때(두 프로젝트) 인증번호를 80통 남짓 보내고 그 발송 기록은 지우지 않으므로(ADR-0070), 같은 DB에서 24시간 안에 여러 번 돌리면 서비스 전체 500건 한도에 걸린다 — 헬퍼가 그 거절을 알아보고 멈춘다. e2e 전용 DB라면 마이그레이션 롤로 `DELETE FROM phone_verification_codes`를 하고 다시 돌린다(개발 DB에는 하지 않는다).
- 스펙은 매번 자기 계정과 자기 시장을 새로 만들므로 같은 데이터베이스에서 반복 실행해도 된다.
- 관리자 계정 스펙(`admin-accounts.spec.ts`)은 시드한 관리자 둘이 필요하다 — `.env`에 `SEED_SECOND_ADMIN_*`를 두고 빈 DB에 시드한다(관리자가 이미 있으면 시드가 둘째를 만들지 않는다). 2명 하한을 시드한 두 관리자만 있는 상태에서 확인하므로, 역할을 바꾸는 시험은 데스크톱 프로젝트에서만 순서대로 돌고 셋째 관리자가 남아 있으면 그 `e2e-` 계정부터 회수한다.
- 정산 스펙(`settlement.spec.ts`)은 워커가 떠 있어야 한다(`pnpm dev`가 띄운다. 없으면 Playwright가 `WORKER_HEALTH_PORT`(기본 4100)의 `/health`를 확인해 직접 띄우고, `0`이면 확인할 포트가 없어 이 스펙만 건너뛴다). 관리자가 판정하면 워커가 곧바로 정산하므로 기다리는 기간은 없다(ADR-0046).
- 작성 빈도 제한 스펙(`write-limits.spec.ts`, #187)은 회원 하나가 10분에 근거 글 셋을 쓰고 넷째에서 거절과 다시 쓸 수 있는 시각을 보고, 운영자가 반복 링크 검토 목록(`/admin/link-flags`)에서 회원 하나가 같은 주소를 쓴 글 하나와 댓글 둘을 한 줄로 보고 펼쳐 각 항목을 본 뒤 '조치함'으로 확인해 그 줄이 '확인함'으로 옮겨지는 것을 본다. 한도는 본인확인한 번호마다라 계정마다 새 번호로 가입하는 다른 스펙은 한도에 닿지 않는다 — 한 계정으로 근거 글을 10분에 셋보다, 댓글을 1분에 다섯보다 많이 쓰는 스펙을 더하면 429다(시드 관리자는 예외). 반복 링크는 시험마다의 새 주소로 본다: `https://example.com/source`처럼 여러 스펙이 함께 쓰는 주소는 검토 목록에 계속 쌓이므로(시험 DB의 일이다) 목록은 최근 탐지순으로 '더 보기'를 눌러 찾는다(스펙이 확인함으로 표시한 줄은 '확인 전'에서 빠진다).
- 근거 글 스펙(`posts.spec.ts`, #46)은 글에 이미지를, 프로필 이미지 스펙(`profile-image.spec.ts`, #141)은 프로필 이미지를 올린다. API가 개발 기본값인 로컬 저장소(`MEDIA_STORAGE` 비움이나 `local`, 저장소 루트의 `.media/`)로 떠 있어야 한다 — `s3`에 버킷이 없으면 업로드가 모두 실패한다.
- 운영 공지 스펙(`notices.spec.ts`, #138)은 고정한 공지가 서비스에 하나뿐인 묶음(최대 3개)이라 고정하는 시험을 데스크톱 프로젝트에서만 차례로 돌리고, 시작과 끝에 그 DB의 고정된 공지를 모두 해제한다 — 개발 DB에 돌리면 개발 중에 고정한 공지도 풀린다. 고정하지 않은 공지의 비공개, 두 운영자의 동시 수정(두 시드 관리자)과 그 '최신 내용 불러오기'가 읽는 동안 올라온 이미지, 쓰기·수정 화면을 떠날 때의 확인과 온보딩 게이트가 쓰던 공지에서 남은 단계로 보낼 때의 보관과 되살림(재동의는 그 브라우저의 `GET /me`만 그리고, 단계의 동의도 브라우저 안에서 답해 시드 관리자의 동의 기록과 그 한도를 건드리지 않는다. 수정 화면의 시험은 그사이 둘째 시드 관리자가 API로 저장하므로 이것도 두 시드 관리자가 필요하다)은 공지를 고정하지 않으므로 두 프로젝트에서 돈다. 공지에 이미지를 올리므로 근거 글 스펙과 같은 저장소가 필요하다.

```
packages/   shared (순수 도메인 로직) · db (Drizzle) · api-client (OpenAPI 클라이언트) · config-ts · config-eslint

deploy/     운영 compose.yaml · Caddyfile · deploy.sh · host-setup.sh · reset-db.sh (api 이미지에 동봉)
terraform/  AWS 인프라 (tf-buddha-*), README.md 에 운영 절차
scripts/    generate-api-doc.mjs (pnpm api:openapi 의 마지막 단계) · image-memory/ (이미지 변환 메모리 측정, 손으로 돌림)
docs/       plan/(기획서 v0.2 원문) · PLAN.md · API.md · DECISIONS.md · QUESTIONS.md · RESET.md(운영 DB 초기화) · OPERATIONS.md(운영자의 손 작업) · TERMS.md(용어 대응표) · SETTINGS.md(출시 설정 등록 규칙) · GUARDS.md(회귀 가드 등록 규칙)
```

패키지 의존 규칙은 PLAN §4.1을 따른다: 앱은 `packages/*`만 import하고, `shared`는 어떤 프레임워크에도 의존하지 않는다.

`docker/docker-compose.yml`의 자격 증명(postgres/postgres, buddha/buddha, 인증 없는 Redis)은 로컬 개발 전용이며 모든 포트는 `127.0.0.1`에만 게시된다(A-M0-14). 게시 주소는 IPv4뿐이라 `::1`은 열리지 않는다 — `.env`의 `localhost` URL은 Node의 주소 패밀리 폴백으로 동작하지만, 폴백이 없는 GUI DB 도구 같은 클라이언트는 `127.0.0.1`을 써야 한다.
