# 운영 DB 초기화

배포 환경(buddha.sboh.dev)의 Postgres와 Redis, 글 이미지 버킷을 비우고 DB를 시드로 다시 채우는 절차다. #125가 마이그레이션 0017로, #174가 0048로, #116이 0060으로 한 번씩 비웠다(ADR-0048, ADR-0093 결정 3, ADR-0107 결정 3). 배포 환경에는 실사용자·실결제 데이터가 없어 초기화하고 다시 시드해도 된다(ADR-0047 D4). **되돌릴 수 없다.** `deploy/reset-db.sh`는 계정까지 모두 지우고 테스터는 다시 가입한다. 오너가 #125의 초기화에 정한 범위다(ADR-0048 결정 1-4).

#149의 출시 전 재초기화는 이 절차를 쓰지만, 다시 초기화할지와 무엇을 남길지는 #133 14항이 정한다(ADR-0047 결정 10). 다시 하지 않을 수도 있다. 출시 설정의 값과 변경 기록을 남길지도 #133이 정한다(오너 결정 2026-10-13\~14, ADR-0055). #133이 운영자 계정이나 사용자 계정처럼 무엇이든 남기기로 하면 #149 전에 이 절차(비우는 문장과 스크립트)를 그 범위로 먼저 좁혀야 한다. 아래는 지금의 절차, 곧 모두 지우는 경우다.

## 지우는 것과 남는 것

#72의 `market_liquidity_versions`도 전체 초기화의 대상이며, 개별 버전의 수정·삭제는 허용하지 않는다(ADR-0122). 현재·개장 버전 포인터는 시장과 함께 지워진다. 0067은 기존 시장에 설정을 채우거나 데이터를 초기화하지 않으며 시드도 유동성 설정값을 입력하지 않는다. 초기화 뒤 초안은 관리자가 명시한 설정과 독립 검수를 거쳐야 개장한다. 여섯 유동성 표준값도 다른 출시 설정과 함께 미정으로 돌아가며, 관리자가 값을 입력하기 전에는 최초 폼에 임의 값을 채우지 않는다.

기록하고, 그 뒤 질문·규칙 항목·시각은 한 관리자가 보충을 요청하고 다른 관리자가 승인해야 바뀐다(#80, ADR-0101 — 관리자가 한 명뿐이면 보충은 요청부터 거절된다). #80 전에 연 시장은 규칙 버전이 없어 보충할 수 없지만, 재초기화가 모두 지우므로 다시 연 시장은 모두 v1을 가진다. 거래 중인 시장은 관리자 한 명이 사유와 함께 바로 거래를 일시 중단하고, 재개나 조기 마감은 한 관리자가 요청하고 다른 관리자가 승인해야 된다(#114, ADR-0102 — 관리자가 한 명뿐이면 요청부터 거절된다). 관리자 한 명이 시장을 마감하는 길은 없다: 시장은 거래 마감 시각에 워커가 마감하고(거래 일시 중단 중이어도), 그 전에 끝내려면 일시 중단한 뒤 조기 마감을 승인받는다. 일찍 열려면 개장 예정 시장의 예정 개장 시각을 사유와 함께 앞당긴다(지금이나 지난 시각이면 바로 열린다). 거래 마감인 시장의 판정은 한 관리자가 등록하고 다른 관리자가 승인해야 잠정 결과로 공개되고, 이의 기한이 지나면 워커가 결과를 확정해 지급한다(#152, ADR-0103 — 관리자 한 명이 판정하는 길은 없어졌고, 관리자가 한 명뿐이면 판정은 등록부터 거절된다). 다만 처리하지 않았거나 수용한 판정 이의가 있으면 기한이 지나도 확정하지 않고 '판정 지연'으로 머물며, 그 판정을 등록하지 않은 관리자가 이의를 모두 기각하면 바로 확정된다(#175, ADR-0104 — 수용한 이의는 판정 정정까지 시장을 잡아 둔다. 잠정 결과인 동안의 판정 정정도 한 관리자가 등록하고 다른 관리자가 승인해야 새 판정 버전과 새 결과, 첫 기한과 같은 길이의 새 이의 기한이 공개되고, 기다리는 정정은 기한이 지나도 확정을 잡아 둔다 — 반려하면 원래 판정대로 확정된다, #176·ADR-0105. 체결 이력이 있는 회원만 이의를 내므로 주문 접수(`order.accepting`)가 열리기 전에는 이의가 없다. 결정할 다른 관리자가 없으면 이의가 그대로 남으니 관리자를 더 둔다, ADR-0093 결정 4). 판정 지연으로 보이는 시장의 지연 사유와 다음 검토 시각은 관리자 한 명이 바로 기록한다(#142, ADR-0106 — 재초기화 뒤에는 기록이 없어 공개 상세에 '판정 지연'만 보인다). 재초기화 뒤에는 출시 설정 `market.dispute_window`(이의 기간)도 미정이라 관리자가 값(설계 제안 1,440분 = #93의 불변 대사 결과(`reconciliation_results`), 지속 보류(`reconciliation_holds`), 보정 기록(`reconciliation_corrections`), 복구 근거(`reconciliation_recoveries`)와 연결 승인·감사도 **이미 승인된 전체 초기화**에서는 다른 공개 스키마 표와 함께 지워진다. 동적 전체 표 inventory가 포함하며 별도 보존기간이나 부분 삭제 경로를 추가하지 않는다. 보류를 해결하기 위해 일반 운영에서 이 기록을 지우거나 초기화하라는 뜻이 아니다.

#93의 0065 자체는 reset·backfill·잔고 교정을 하지 않는다. 최초 검사부터 현재 데이터에 같은 규칙을 적용하고 옛 `ledger_failure` 중단을 연결하므로 보류·자동 중단이 생길 수 있다. #116의 과거 초기화 절차를 다시 실행하지 않는다. 이후 Coin 보정은 실제 실패에 묶인 요청과 다른 관리자 승인으로만 실행하며 보류 해제는 별도 복구 승인이다. 주문 접수는 #126과 완료된 #93이 배포된 뒤 오너가 연다.

#143의 영구 이해관계 신고(`market_conflict_declarations`, ADR-0120)도 위 `public` 전체 초기화 대상이다. 시장·회원·신고 사유·시각·감사 연결을 담으며 평소 UPDATE/DELETE는 막고 승인된 전체 초기화의 TRUNCATE로만 비운다. 자동 체결 배제의 근거인 주문과 마지막 권한 회수 기록인 `admin_actions`도 전체 초기화 때 함께 비워진다. 역할 회수나 탈퇴가 이 신고를 지우지는 않는다.

마이그레이션 0066 자체는 DB를 초기화하거나 과거 행을 채우지 않는다. 신고 표·최신 회수 조회 인덱스·주문 사유와 제약/트리거만 더한다. 배포 뒤 기존 체결/회수 기록은 새 자격·주문 판단에 그대로 쓰고, 기존 관리자의 주문·대기 판정을 일괄 수정하지 않는다. 새 시장 시드와 기존 회원의 관리자 승격 시드는 생성 시각 경계와 원자적 취소 규칙을 따른다([운영 절차](OPERATIONS.md#관리자-권한과-이해관계-143-adr-0120)).

## 한 문장, 두 곳

비우는 문장은 `packages/db/src/wipe.ts`의 `WIPE_PUBLIC_TABLES_SQL` 하나다. `public` 스키마의 테이블 목록을 실행할 때 `pg_tables`에서 읽어 `TRUNCATE … RESTART IDENTITY CASCADE`하므로, 뒤에 생기는 테이블도 빠지지 않는다. TRUNCATE는 테이블 소유자의 권한이라 `buddha_migrate`로 돈다(`buddha_app`은 할 수 없다).

- **마이그레이션 0017**(`packages/db/drizzle/0017_remove_direct_amm.sql`), **0048**(`0048_market_lifecycle.sql`)과 **0060**(`0060_ledger_accounts.sql`)의 첫 문장이 이 문장 그대로다. #125, #174, #116 배포 때 한 번씩 돈다.
- **재초기화**는 `packages/db/src/wipe-cli.ts`(빌드 결과 `packages/db/dist/wipe-cli.js`, api 이미지에 들어 있다)로 같은 문장을 다시 돌린다. 운영 호스트에서는 `deploy/reset-db.sh`가 부른다.
- `packages/db/src/wipe.test.ts`가 세 마이그레이션의 첫 문장과 CLI가 같은 문장인지, 스크립트가 그 CLI를 부르는지 고정한다. 시험 하네스의 `reset()`도 같은 문장으로 매 DB 시험 전에 비운다.
- `packages/db/src/reset-db.test.ts`가 `deploy/reset-db.sh`를 가짜 `docker`로 실제로 돌려 단계 순서(버킷 비우기는 DB를 비운 뒤, api·worker가 멈춘 동안)와 덤프 처리(아래 3·10단계, 실패하면 남김)를 고정한다. 버킷을 비우는 CLI(`packages/storage/src/empty-cli.ts` — 하는 일은 `empty.ts`의 `runEmptyCli`이고 그 파일은 줄을 찍고 그 코드로 끝날 뿐이다)가 `--yes` 없이는 아무것도 하지 않고, compose가 넘기는 빈 `MEDIA_S3_*`(버킷을 만드는 `terraform apply` 전)이면 건너뛰며 성공으로 끝나고, 객체를 천 개씩 나열해 지우는 것은 `packages/storage/src/empty.test.ts`가 본다(`runEmptyCli`를 compose와 같은 변수로 부른다).

## 운영 호스트에서

**준비.**

- 배포된 이미지가 #125 이후의 것이어야 한다(`wipe-cli.js`가 있다). 스크립트가 아무것도 멈추기 전에 확인한다.
- 테스터에게 미리 알린다: 전원 로그아웃되고, 계정·잔고·기록이 모두 사라지며, 다시 가입해야 한다.
- (선택) 워크스테이션의 `terraform/`에서 EBS 수동 스냅샷을 뜬다. 스크립트도 시작할 때 `pg_dump`를 뜨지만 초기화가 끝까지 성공하면 지우므로, 성공한 뒤의 확인에서 문제가 보였을 때 되돌릴 길은 이 스냅샷뿐이다.

```bash
aws ec2 create-snapshot --profile inno-frame --volume-id "$(terraform output -raw data_volume_id)" \
  --description pre-reset
```

**실행.** 셸은 `aws ssm start-session --profile inno-frame --target "$(terraform output -raw instance_id)"`([terraform/README.md](../terraform/README.md#셸)).

```bash
sudo bash /data/buddha/reset-db.sh --yes
```

스크립트는 배포마다 api 이미지에서 `/data/buddha`로 풀린다. `--yes`가 없으면 아무것도 하지 않고 끝난다. 하는 일은 차례로 다음과 같다.

1. `/data`가 마운트되어 있는지 확인하고 `deploy.sh`와 같은 락(`/data/buddha/.deploy.lock`)을 잡는다. 배포와 겹치지 않는다.
2. postgres·redis가 떠 있게 하고, 배포된 api 이미지에 `wipe-cli.js`와 `empty-cli.js`(#46부터)가 있는지 확인한다. 없으면 여기서 끝나고 사이트는 그대로다.
3. `pg_dump`를 `/data/buddha-pre-reset-<시각>.dump`(소유자만 읽기)로 뜬다. 덤프가 끝나지 못하면(실패·중단) 그 파일을 지우고 아무것도 바꾸지 않은 채 끝난다.
4. api·worker를 멈춘다. web·caddy는 그대로라 그동안 화면은 오류를 낸다(보통 1분 안).
5. 비운다: `docker compose run --rm --no-deps migrate node packages/db/dist/wipe-cli.js --yes`(`DATABASE_MIGRATE_URL` = `buddha_migrate`).
6. Redis를 비운다: `docker compose exec -T redis redis-cli FLUSHALL`.
7. 글 이미지 버킷을 비운다: `docker compose run --rm --no-deps api node packages/storage/dist/empty-cli.js --yes`. 한 번 쓰고 지우는 api 컨테이너가 api의 `MEDIA_S3_*`(앱 전용 IAM user의 키)로 버킷의 객체를 천 개씩 나열해 지우고 지운 수를 찍는다(`[media:empty] deleted N objects from …`). 호스트의 자격증명은 쓰지 않는다. `MEDIA_S3_BUCKET`이 비어 있으면 그렇다고 찍고 건너뛴다. 5단계 뒤에 하는 까닭: 그 전에 실패하면 남은 행이 지운 이미지를 가리킨다. api·worker가 멈춘 동안이라 그사이 올라오는 이미지도 없다.
8. `docker compose run --rm migrate`: 남은 마이그레이션(보통 없다)과 시드.
9. `docker compose up -d --wait`로 api·worker를 다시 띄운다.
10. 여기까지 모두 성공했으면 3단계의 덤프를 지운다(오너 결정, ADR-0048). 앞서 실패한 실행이 남긴 덤프가 `/data`에 있으면 그 이름을 알리고 지우지 않는다.

**확인.**

- `https://buddha.sboh.dev/api/health`가 200이다. 7단계가 지운 이미지 수(또는 건너뜀)를, 8단계의 시드 로그가 `market maker account: created`, `admin … created`, `markets: 14 inserted`를 찍는다.
- 시드 관리자로 로그인 → `/onboarding`(약관 동의, 실명·휴대전화를 넣고 SMS로 받은 인증번호로 본인확인, 시드가 둔 자동 닉네임을 그대로 확정하거나 직접 정하기 — 예전 시드가 준 '관리자'는 규칙에 걸려 새로 정한다, 시작 Coin 안내, 관심 카테고리 건너뛰기, ADR-0070·ADR-0072) → `/admin/markets`에 초안 14개가 있다. 시드가 마감이 지났거나 14일 안에 마감되는 초안을 경고하면 관리자가 마감 시각을 고치거나 시드 문안을 새로 만든다.
- 테스터 계정으로 가입하면 잔고 0, 원장 0줄이다(가입 지급이 없다, ADR-0071). 시작 Coin은 온보딩의 닉네임 단계(ADR-0072)를 마친 계정에, `/admin/settings`의 시작 지급액에 값이 있을 때 원장의 '시작 지급' 한 줄로 생긴다. 값이 없으면 지급 안내와 지갑이 '시작 Coin은 준비되는 대로 지급됩니다.'를 보인다.

**실패하면.** 스크립트는 첫 오류(또는 SSM 세션이 끊기는 등의 중단)에서 멈추고, 3단계의 덤프를 지우지 않은 채 그 경로를 알린다. 4단계 뒤라면 api·worker가 멈춘 채로 남는다. 5단계(비우기)가 끝나기 전이면 데이터는 그대로이니 `sudo docker compose -f /data/buddha/compose.yaml up -d`로 되돌린다. 그 뒤라면 원인을 고친 뒤 스크립트를 다시 돌린다 — 다시 돌려도 안전하다(빈 DB를 덤프하고 다시 비운 뒤 버킷에 남은 것을 마저 지우고 시드한다). 다시 돈 실행이 성공하면 지우는 것은 그 실행이 뜬 덤프뿐이고, 실패한 실행의 덤프는 남는다(스크립트가 끝에 이름을 알린다). 7단계(버킷 비우기)가 시작된 뒤라면 덤프로 DB를 되돌려도 지운 이미지는 돌아오지 않는다 — 되돌린 글의 이미지는 없는 이미지(404)로 보인다. 초기화 전 상태로 되돌리려면 실패한 실행의 덤프를 [terraform/README.md](../terraform/README.md#수동-pg_dump) 「수동 pg_dump」의 실제 복구 절차로 넣고, Redis는 비운 채로 둔다(워커의 매 분 스캔이 마감·정산을 다시 잡는다).

**덤프 정리.** 덤프에는 테스터의 이메일·실명·본인확인한 휴대전화가 들어 있다. 성공한 실행은 자기 덤프를 스스로 지운다. 실패한 실행이 남긴 덤프는 복구나 재실행의 성공을 확인한 뒤 손으로 지운다(`sudo rm /data/buddha-pre-reset-<시각>.dump`). `/data`에 있는 동안은 일일 스냅샷(7개)에도 들어간다.

## #125 배포 때의 한 번 (마이그레이션 0017)

#125를 머지하면 평소 배포가 그대로 초기화한다: `deploy.sh`의 `migrate`가 0017을 적용하고(비우기 → 직접 AMM 열·enum 값 삭제) 시드가 다시 채운 뒤 컨테이너를 바꾼다. 따로 할 일은 없다.

- drizzle은 남은 마이그레이션을 한 트랜잭션에서 적용한다. 0017이 실패하면 아무것도 지워지지 않고, 이전 릴리스가 계속 돈다(`deploy.sh`가 `migrate` 실패에서 멈춘다).
- 배포 창: `migrate`가 도는 수십 초 동안 이전 api·워커가 지운 열을 읽어 500·잡 실패를 낸다. 새 컨테이너가 뜨면 풀린다(ADR-0046 D3과 같다).
- 덤프는 자동으로 남지 않는다. 남기려면 머지 전에 [terraform/README.md](../terraform/README.md#수동-pg_dump)의 「수동 pg_dump」를 한다.
- 0017은 Redis를 건드리지 않는다. 지운 시장을 가리키던 지연 잡(`market.close`·`market.finalize`)은 워커에서 'not found'로 세 번 실패하고 버려진다. 데이터에는 영향이 없다. 로그까지 깨끗이 하려면 배포 직후, 테스터가 다시 가입하기 전에 위 스크립트를 한 번 돌린다. #149의 리허설도 된다.

## #174 배포 때 (마이그레이션 0048, ADR-0093)

#174를 머지하면 평소 배포가 그대로 DB를 비운다: `deploy.sh`의 `migrate`가 0048을 적용하고(비우기 → 시장 상태 enum을 열한 값으로 다시 만들고 결과 유형 YES/NO/VOID를 따로 둔다) 시드가 다시 채운 뒤 컨테이너를 바꾼다. 계정까지 비워지므로 테스터는 다시 가입한다. 오너가 정한 초기화다(ADR-0093 결정 3의 #174 'DB 초기화' 행). 아래 #70의 초기화를 겸한다.

- drizzle은 남은 마이그레이션을 한 트랜잭션에서 적용한다. 0048이 실패하면 아무것도 지워지지 않고, 이전 릴리스가 계속 돈다.

## #116 배포 때 (마이그레이션 0060, ADR-0107 결정 3)

#116을 머지하면 평소 배포가 그대로 DB를 **계정까지** 비운다: `deploy.sh`의 `migrate`가 0060을 적용하고(비우기 → 원장을 원장 계정 사이의 이동으로 다시 짜기: 원장 계정 표 `ledger_accounts`, 원장 계정마다의 잔고, 출처마다의 원장 유형 enum, 관리자 잔고 조정과 옛 수수료 열 `markets.taker_fee_bps`·`settlement_fee_bps`의 삭제, ADR-0109) 시드가 다시 채운 뒤 컨테이너를 바꾼다. 오너가 정한 초기화다(ADR-0107 결정 3의 '배포 DB 초기화(#116)' 행, ADR-0093 결정 3의 #174 행). 옮기거나 채우는 작업은 없다(#116 수용 기준, D4·D13). **머지는 오너의 허락을 받은 뒤에 한다**(ADR-0107 결정 3 '오너를 기다리는 머지'의 (1)).

- 지우는 것은 [지우는 것과 남는 것](#지우는-것과-남는-것)의 Postgres 행과 같다: 계정·세션·인증, 프로필·잔고·원장, 시장과 그 기록, 시작 지급 기록, 본인확인 기록, 출시 설정의 값과 변경 기록, 관리자 권한과 작업 기록까지 모두.
- drizzle은 남은 마이그레이션을 한 트랜잭션에서 적용한다. 0060이 실패하면 아무것도 지워지지 않고, 이전 릴리스가 계속 돈다.
- 배포 창: `migrate`가 도는 수십 초 동안 이전 api·워커가 지운 열(`ledger_entries.user_id`·`balance_after_coin`, `markets`의 수수료 두 열)과 없어진 원장 유형 값을 읽거나 써 500·잡 실패를 낸다. 새 컨테이너가 뜨면 풀린다. 이전 웹의 잔고 조정 양식도 그동안만 남고, 새 api는 그 라우트에 404로 답한다.
- 덤프는 자동으로 남지 않는다. 남기려면 머지 전에 [terraform/README.md](../terraform/README.md#수동-pg_dump)의 「수동 pg_dump」를 한다.
- **0060은 Postgres만 비운다.** Redis의 지연 잡은 0017 때처럼 'not found'로 실패하고 버려지고, 글 이미지·프로필 이미지 버킷의 객체는 남는다. 함께 비우려면 배포 직후, 테스터가 다시 가입하기 전에 [운영 호스트에서](#운영-호스트에서)의 스크립트를 한 번 돌린다(선택, ADR-0107 결과 3).
- 다시 채움: 시드가 관리자 둘, 검수 전 초안 시장 14개, 운영 마켓메이커 계정(새 id)을 다시 만든다(ADR-0107 결정 3). 관리자는 사람 계정이라 사용자 원장 계정을 잔고 0으로 받고, 운영 마켓메이커는 사용자 원장 계정이 없다. 운영 금고와 시장별 마켓메이커 자금 원장 계정은 봇(#129)이 처음 쓸 때까지 없다.

**오너가 할 일**(ADR-0107 결과 3).

1. 머지 전에 테스터에게 알린다: 전원 로그아웃되고, 계정·잔고·기록이 모두 사라지며, 다시 가입하고 SMS 본인확인을 다시 해야 한다.
2. (선택) 이미지 버킷과 Redis까지 비우려면 배포 직후, 관리자 온보딩과 출시 설정보다 먼저 `deploy/reset-db.sh`를 돌린다(위). 이 스크립트는 Postgres도 다시 비우고 시드하므로, 3·4단계 뒤에 돌리면 관리자 온보딩·출시 설정 값과 그 기록·그동안 다시 가입한 테스터가 다시 사라져 3·4단계를 또 해야 한다.
3. 시드 관리자 둘이 다시 로그인해 온보딩(약관 동의·본인확인·닉네임)을 마친다. 시장을 열려면 관리자 둘이 필요하므로 호스트 `.env`에 `SEED_SECOND_ADMIN_*`가 있는지 확인한다.
4. `/admin/settings`에서 출시 설정을 사유와 함께 다시 넣는다(초기화가 값과 기록을 지웠다): `grant.start_coin`(시작 지급액 — 값을 넣기 전에 온보딩을 마친 계정의 지급은 기다렸다가 워커가 준다), `market.lead_close_gap`(제안 60분), `market.dispute_window`(1,440분), `retention.consent_records`, `retention.phone_verification_records`, `retention.deleted_posts`, `retention.moderation_records`, `retention.removed_profile_items`, `retention.market_proposals`. #116은 새 출시 설정을 등록하지 않는다. 그 뒤에 배포된 M9 항목이 있으면 그것도 넣는다 — #119 뒤에는 `order.rate_limit`(시험값 20회/분)과 `order.price_protection_ticks`(시험값 5틱. 미정이면 시장을 검수 제출할 수 없다)이고, `order.accepting`(주문 접수)은 #126과 #93이 배포되기 전에는 넣지 않는다(미정이면 닫혀 있다, ADR-0107 결정 3 — [OPERATIONS.md의 주문 접수](OPERATIONS.md#주문-접수-119-adr-0112)). 초기화는 주문 접수 값도 지우므로, 연 뒤에 초기화하면 오너가 다시 연다.
5. (선택) [OPERATIONS.md의 원장 계정](OPERATIONS.md#원장-계정-116-adr-0109) 확인 SQL로 원장을 본다: 사용자 계정 밖의 원장 계정이 없고(주문 접수가 열리기 전과 #129 전), `held` = `minted` − `burned`이며 `burned` = 0, `minted`는 온보딩을 마친 계정의 '시작 지급' 합이다 — 3·4단계 뒤에는 관리자 둘의 시작 지급(시작 지급액 × 2)이 들어 있어 0이 아니다. 0은 아직 아무도 온보딩을 마치지 않았을 때뿐이다. 운영 마켓메이커 계정이 하나인지는 [OPERATIONS.md의 운영 마켓메이커 계정](OPERATIONS.md#운영-마켓메이커-계정-115-adr-0108) 확인 SQL로 본다(줄 하나).

**확인.** [운영 호스트에서](#운영-호스트에서)의 '확인'과 같다. 테스터 계정은 가입하면 잔고 0, 원장 0줄이고, 시작 지급액을 넣은 뒤 온보딩을 마치면 원장에 '시작 지급' 한 줄이 생긴다. `/admin/users`에는 잔고 조정 양식이 없다.

## #70 배포 때 (오너 결정 2026-10-18)

#174의 0048이 이 초기화를 겸한다(ADR-0093 결정 3). #174가 배포되면 아래를 따로 돌릴 필요는 없고, Redis와 버킷을 비우는 일은 [#174 배포 때](#174-배포-때-마이그레이션-0048-adr-0093)의 「0048은 Postgres만 비운다」 항목대로다. 아래는 그 전의 기록이다.

#70(마이그레이션 0031)은 가입 트리거의 10,000 Coin(`BONUS`) 지급을 없애고, 시작 Coin을 본인확인한 번호마다 한 번 `START_GRANT`로 주게 한다. 0031은 기존 계정의 잔고·원장을 건드리지 않으므로(D4), 그대로 두면 #70 전에 가입한 계정은 가입 때 받은 10,000 Coin에 더해 온보딩(#58)을 마친 뒤 시작 Coin도 받는다. 오너는 이것을 코드로 막지 않고, #70을 배포할 때 배포 DB를 이 문서의 절차로 초기화하기로 했다(ADR-0071 결정 1의 답 1). **시점은 오너가 정한다.**

- **#70이 배포된 뒤에** 돌린다: 배포 워크플로가 0031을 적용하고 새 api가 뜬 뒤(`/api/health` 200). 그 전에 돌리면 옛 트리거가 남아 있어 다시 가입한 계정이 또 10,000 Coin을 받는다. 배포 전에 `PHONE_HASH_KEY`를 만드는 `terraform apply`는 그대로 먼저 한다([terraform/README.md](../terraform/README.md)의 '#70(마이그레이션 0031)을 처음 배포할 때 한 번').
- 하는 일은 [운영 호스트에서](#운영-호스트에서)와 같다(`sudo bash /data/buddha/reset-db.sh --yes`). 계정까지 모두 지우므로 테스터는 다시 가입하고 다시 본인확인한다.
- 확인: [운영 호스트에서](#운영-호스트에서)의 '확인'에 더해, 비운 뒤 원장에 `BONUS` 행이 없다(`SELECT count(*) FROM ledger_entries WHERE type = 'BONUS'`가 0 — 쿠폰도 닫혀 있다, ADR-0049). 다시 가입한 계정은 잔고 0으로 시작한다.
- #58 전에 초기화하면 다시 가입한 계정은 #58이 배포될 때까지 0 Coin에 머문다(오너가 받아들인 공백, ADR-0069 결정 4 #70).

## #121 배포 때 (마이그레이션 0063, ADR-0116)

#121은 DB를 비우지 않는다. 0063은 `markets`에 빈 칸 `last_fill_at`과 그 짝 CHECK를 더하고 `fills`의 인덱스 하나를 바꿀 뿐 행을 바꾸거나 지우지 않는다. 다만 시장 통계는 첫 체결부터 주문 접수가 쓰므로, 0063의 첫 문장은 체결이 하나라도 있거나 통계(`last_price`·`volume_coin`·`trade_count`·`trader_count`)가 기본값이 아닌 시장이 있는 DB에서 아무것도 하지 않고 멈춘다. 운영 DB는 0060이 비웠고 주문 접수(`order.accepting`)가 닫혀 있어 지나간다. 멈추면 그 DB에는 0063 전의 체결이나 통계가 있다는 뜻이다 — 다시 세는 UPDATE는 데이터를 바꾸는 마이그레이션이라 오너가 정한다(ADR-0107 결정 3). 그 전까지 배포는 이전 릴리스로 계속 돈다(drizzle은 남은 마이그레이션을 한 트랜잭션에서 적용한다).

## #24 배포 때 (ADR-0121)

기존 중단 메모나 사건을 재작성하지 않는다. 새 공개 중단 입력만 사건 payload에 공개 근거를 남기고, 과거 관리자 전용 메모는 그 근거가 없으므로 비공개로 유지한다.

공개 판정 기록은 기존 판정·중단·지연·이의·시장 사건·정산 단계의 허용된 사실을 읽는다. 새 표·마이그레이션·초기화·backfill은 없다. 옛 판정에 버전이나 근거를 만들어 채우지 않는다. 승인된 전체 초기화가 해당 원본 표를 비우면 공개 기록도 함께 사라지며, 별도 공개 사본을 남기지 않는다. 이의 본문/링크의 개인정보 보존 처리는 기존대로이고 행·상태·처리 사유는 남는다. 공개 범위가 바뀌었다는 이유로 원본 기록을 삭제하는 절차는 추가하지 않는다.

## 로컬 개발 환경

개발 DB도 0060을 적용하는 다음 `pnpm db:migrate`에서 한 번 더 비워진다(시험 DB는 원래 시험마다 비운다). 계정까지 비워지므로 개발 DB의 관리자와 테스트 계정도 `pnpm db:seed`와 가입으로 다시 만든다. 개발 Redis에 남은 지연 잡도 위처럼 실패하고 버려진다.

0063 전에 개발 DB에서 주문을 체결했다면(주문 접수를 연 개발 DB) 다음 `pnpm db:migrate`가 0063의 첫 문장에서 멈춘다. 아래대로 비우고 다시 채운다(#121).

같은 초기화를 로컬에서 하려면 `pnpm dev`를 멈추고 다음을 돌린다. `wipe-cli`는 `@buddha/shared` 빌드가 있어야 한다(`pnpm build`나 `pnpm dev`를 한 번 돌렸으면 된다).

```bash
pnpm --filter @buddha/db run db:wipe --yes   # .env의 DATABASE_MIGRATE_URL
docker compose exec redis redis-cli FLUSHALL
pnpm db:migrate && pnpm db:seed
```

글 이미지와 프로필 이미지의 로컬 저장소(저장소 루트의 `.media/`, ADR-0073·ADR-0079)는 DB와 따로 남는다(운영의 7단계와 달리 로컬 폴더는 스크립트가 건드리지 않는다). 지운 행이 가리키던 파일이므로 아무 데도 보이지 않는다. 함께 비우려면 `rm -rf .media`.

볼륨째 지우는 `docker compose down -v`도 된다. 이때는 롤 초기화 SQL부터 다시 돈다.

## #129 배포와 초기화 (마이그레이션 0069, ADR-0124)

0069는 `treasury_issuances`, `market_maker_allocations`, `market_maker_runtime`, `market_maker_runs`, `market_maker_open_attempts` 다섯 표와 승인·개장 결합 제약을 더한다. 배포 자체는 DB를 비우거나 기존 원장·시장에 승인·배정·런타임을 채우지 않는다. 시드의 전역 MM 계정은 기존 방식대로 하나이며, 금고 발행은 별도 2인 승인이고 시장별 초기 자금과 런타임은 정상 개장에서만 생성한다. 금고가 부족하면 SCHEDULED에서 기다리며, 초기화나 자동 발행으로 해결하지 않는다.

오너가 별도로 승인한 전체 초기화는 기존 `WIPE_PUBLIC_TABLES_SQL`이 실행 시 `pg_tables`에서 `public` 전체를 읽으므로 다섯 표도 빠짐없이 포함한다. 하드코딩된 별도 reset 목록이나 새 삭제 경로는 없다. 원장·승인·시장과 함께 TRUNCATE되며 시퀀스가 재설정되고, 마이그레이션 이력은 유지된다. 초기화 뒤 시드는 금고 발행이나 배정 기록을 복원하지 않는다. 출시 설정의 세 위험 단계 값도 다시 입력해야 하며 미정이면 봇 호가는 닫혀 있다. 이 설명은 운영 초기화의 실행 승인을 대신하지 않는다.

## #181 회수 완료·시도 기록 (마이그레이션 0070·0071)

0070은 시장별 불변 완료 표 `market_maker_recalls`와 새 `BOT_RECALL`의 원장·완료 결합 검사를 더한다. 마이그레이션은 기존 회수 원장에 완료 기록을 추측해 채우거나 자금을 옮기지 않는다. 0071은 최신 시도 관측 표를 추가하며, 배포 뒤 실행되는 자동 scan은 과거 SETTLED/CANCELLED 미완료 시장도 회수한다. 이 운영 효과는 머지·배포 승인 때 명시한다. 시드가 회수를 실행하지 않으며 수동 실행 API·버튼은 없다.

정상 완료는 SETTLED/CANCELLED의 남은 실제 Coin 전액을 금고로 옮기는 기록이다. 0 Coin 완료는 원장 행 없이 남고, 미배정 취소는 funds/treasury 계정을 새로 만들지 않는다. 원장 보류, 손상된 잔고·잠금·계약·정산 근거는 회수로 복구하지 않는다. 기존 `public` 전체 TRUNCATE는 이 표도 원장·시장과 함께 포함하며, 시드는 회수 완료를 복원하지 않는다. 이 설명은 운영 초기화 또는 회수 실행 승인이 아니다.

## #182 게시 호가 관측 (마이그레이션 0072)

0072는 `market_maker_supply_states`와 `market_maker_supply_intervals` 및 지연 관측·쓰기 제한·커밋 구간 불변 제약을 추가한다. 배포 자체는 과거 구간을 채우지 않으며 기존 시장의 최초 관측 전은 자료 없음이다. 정상 운영에서는 정산 후에도 개인정보 없는 구간을 보존하고 자동 삭제하지 않는다. 명시 승인된 전체 초기화의 public 표 TRUNCATE에는 두 표도 포함되며, 이후 새 시장은 개장 전부터 새로 관측한다. 시드·조회가 과거 관측을 복원하거나 임의 지표 0을 넣지 않는다.

### #130 운영 통제 기록

0073의 `market_maker_controls`는 승인된 정지·재개·설정 변경·증액의 영구 실행 기록이다. 앱 역할은 INSERT/SELECT만 가능하며 UPDATE/DELETE할 수 없다. 승인 요청과 새 설정 버전·원장·운영 세대가 함께 검증된다. 초기화는 기존 전체 테스트/개발 초기화 절차만 사용하고, 운영에서 기록을 지우거나 버전을 되돌려 재개하지 않는다. 신규 마이그레이션은 기존 시장의 가동 상태나 자본을 변경하거나 요청을 자동 승인하지 않는다.

## 거래 패턴 검토 (#98)

후보 표·저장 보고서·주기 작업은 없다. 조회는 기존 체결과 현재 별명/출시 설정에서만 계산하므로 초기화 대상 경제 표를 추가하지 않는다. 여섯 `trading_anomaly.*` 설정의 값과 변경 이력은 기존 `release_settings`/`release_setting_changes` 초기화 범위에 포함되며 재생성 뒤 미정이다. 새 `fills_created_at_id_idx`는 스키마의 조회 index라 마이그레이션 재적용으로 돌아온다. 후보를 지우려고 원 체결을 삭제하거나 경제 기록을 수정하지 않는다.

### #132 체결 분류 기록

`fill_classifications`는 고정 체결에 대한 불변 관리자 결정이며 일반 앱 역할로 수정·삭제하지 않는다. 전체 시험 reset/wipe의 기존 소유자 절차만 사용한다. 별도 초기 clock 행이나 과거 분류 추정 backfill은 없다. `markets.stats_revision`은 일반 참여자 최신성 키로 새 시장은 0부터 시작한다. 원 체결·주문·원장·정산의 보존/삭제 정책은 이 분류로 바꾸지 않는다.
