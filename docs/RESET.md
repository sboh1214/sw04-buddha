# 운영 DB 초기화

배포 환경(buddha.sboh.dev)의 Postgres와 Redis, 글 이미지 버킷을 비우고 DB를 시드로 다시 채우는 절차다. #125가 마이그레이션 0017로 한 번 비웠다(ADR-0048). 배포 환경에는 실사용자·실결제 데이터가 없어 초기화하고 다시 시드해도 된다(ADR-0047 D4). **되돌릴 수 없다.** `deploy/reset-db.sh`는 계정까지 모두 지우고 테스터는 다시 가입한다. 오너가 #125의 초기화에 정한 범위다(ADR-0048 결정 1-4).

#149의 출시 전 재초기화는 이 절차를 쓰지만, 다시 초기화할지와 무엇을 남길지는 #133 14항이 정한다(ADR-0047 결정 10). 다시 하지 않을 수도 있다. 출시 설정의 값과 변경 기록을 남길지도 #133이 정한다(오너 결정 2026-10-13\~14, ADR-0055). #133이 운영자 계정이나 사용자 계정처럼 무엇이든 남기기로 하면 #149 전에 이 절차(비우는 문장과 스크립트)를 그 범위로 먼저 좁혀야 한다. 아래는 지금의 절차, 곧 모두 지우는 경우다.

## 한 문장, 두 곳

비우는 문장은 `packages/db/src/wipe.ts`의 `WIPE_PUBLIC_TABLES_SQL` 하나다. `public` 스키마의 테이블 목록을 실행할 때 `pg_tables`에서 읽어 `TRUNCATE … RESTART IDENTITY CASCADE`하므로, 뒤에 생기는 테이블도 빠지지 않는다. TRUNCATE는 테이블 소유자의 권한이라 `buddha_migrate`로 돈다(`buddha_app`은 할 수 없다).

- **마이그레이션 0017**(`packages/db/drizzle/0017_remove_direct_amm.sql`)의 첫 문장이 이 문장 그대로다. #125 배포 때 한 번 돈다.
- **재초기화**는 `packages/db/src/wipe-cli.ts`(빌드 결과 `packages/db/dist/wipe-cli.js`, api 이미지에 들어 있다)로 같은 문장을 다시 돌린다. 운영 호스트에서는 `deploy/reset-db.sh`가 부른다.
- `packages/db/src/wipe.test.ts`가 둘이 같은 문장인지, 스크립트가 그 CLI를 부르는지 고정한다. 시험 하네스의 `reset()`도 같은 문장으로 매 DB 시험 전에 비운다.
- `packages/db/src/reset-db.test.ts`가 `deploy/reset-db.sh`를 가짜 `docker`로 실제로 돌려 단계 순서(버킷 비우기는 DB를 비운 뒤, api·worker가 멈춘 동안)와 덤프 처리(아래 3·10단계, 실패하면 남김)를 고정한다. 버킷을 비우는 CLI(`packages/storage/src/empty-cli.ts` — 하는 일은 `empty.ts`의 `runEmptyCli`이고 그 파일은 줄을 찍고 그 코드로 끝날 뿐이다)가 `--yes` 없이는 아무것도 하지 않고, compose가 넘기는 빈 `MEDIA_S3_*`(버킷을 만드는 `terraform apply` 전)이면 건너뛰며 성공으로 끝나고, 객체를 천 개씩 나열해 지우는 것은 `packages/storage/src/empty.test.ts`가 본다(`runEmptyCli`를 compose와 같은 변수로 부른다).

## 운영 호스트에서

**준비.**

- 배포된 이미지가 #125 이후의 것이어야 한다(`wipe-cli.js`가 있다). 스크립트가 아무것도 멈추기 전에 확인한다.
- 테스터에게 미리 알린다: 전원 로그아웃되고, 계정·잔고·기록이 모두 사라지며, 다시 가입해야 한다.
- (선택) 워크스테이션의 `terraform/`에서 EBS 수동 스냅샷을 뜬다. 스크립트도 시작할 때 `pg_dump`를 뜨지만 초기화가 끝까지 성공하면 지우므로, 성공한 뒤의 확인에서 문제가 보였을 때 되돌릴 길은 이 스냅샷뿐이다.

```bash
aws ec2 create-snapshot --profile inno-frame --volume-id "$(terraform output -raw data_volume_id)" \
  --description pre-reset
```

**실행.** 셸은 `aws ssm start-session --profile inno-frame --target "$(terraform output -raw instance_id)"`([terraform/README.md](../terraform/README.md#셸)).

```bash
sudo bash /data/buddha/reset-db.sh --yes
```

스크립트는 배포마다 api 이미지에서 `/data/buddha`로 풀린다. `--yes`가 없으면 아무것도 하지 않고 끝난다. 하는 일은 차례로 다음과 같다.

1. `/data`가 마운트되어 있는지 확인하고 `deploy.sh`와 같은 락(`/data/buddha/.deploy.lock`)을 잡는다. 배포와 겹치지 않는다.
2. postgres·redis가 떠 있게 하고, 배포된 api 이미지에 `wipe-cli.js`와 `empty-cli.js`(#46부터)가 있는지 확인한다. 없으면 여기서 끝나고 사이트는 그대로다.
3. `pg_dump`를 `/data/buddha-pre-reset-<시각>.dump`(소유자만 읽기)로 뜬다. 덤프가 끝나지 못하면(실패·중단) 그 파일을 지우고 아무것도 바꾸지 않은 채 끝난다.
4. api·worker를 멈춘다. web·caddy는 그대로라 그동안 화면은 오류를 낸다(보통 1분 안).
5. 비운다: `docker compose run --rm --no-deps migrate node packages/db/dist/wipe-cli.js --yes`(`DATABASE_MIGRATE_URL` = `buddha_migrate`).
6. Redis를 비운다: `docker compose exec -T redis redis-cli FLUSHALL`.
7. 글 이미지 버킷을 비운다: `docker compose run --rm --no-deps api node packages/storage/dist/empty-cli.js --yes`. 한 번 쓰고 지우는 api 컨테이너가 api의 `MEDIA_S3_*`(앱 전용 IAM user의 키)로 버킷의 객체를 천 개씩 나열해 지우고 지운 수를 찍는다(`[media:empty] deleted N objects from …`). 호스트의 자격증명은 쓰지 않는다. `MEDIA_S3_BUCKET`이 비어 있으면 그렇다고 찍고 건너뛴다. 5단계 뒤에 하는 까닭: 그 전에 실패하면 남은 행이 지운 이미지를 가리킨다. api·worker가 멈춘 동안이라 그사이 올라오는 이미지도 없다.
8. `docker compose run --rm migrate`: 남은 마이그레이션(보통 없다)과 시드.
9. `docker compose up -d --wait`로 api·worker를 다시 띄운다.
10. 여기까지 모두 성공했으면 3단계의 덤프를 지운다(오너 결정, ADR-0048). 앞서 실패한 실행이 남긴 덤프가 `/data`에 있으면 그 이름을 알리고 지우지 않는다.

**확인.**

- `https://buddha.sboh.dev/api/health`가 200이다. 7단계가 지운 이미지 수(또는 건너뜀)를, 8단계의 시드 로그가 `admin … created`, `markets: 14 inserted`를 찍는다.
- 시드 관리자로 로그인 → `/onboarding`(약관 동의, 실명·휴대전화를 넣고 SMS로 받은 인증번호로 본인확인, 시드가 둔 자동 닉네임을 그대로 확정하거나 직접 정하기 — 예전 시드가 준 '관리자'는 규칙에 걸려 새로 정한다, 시작 Coin 안내, 관심 카테고리 건너뛰기, ADR-0070·ADR-0072) → `/admin/markets`에 초안 14개가 있다. 시드가 마감이 지났거나 14일 안에 마감되는 초안을 경고하면 관리자가 마감 시각을 고치거나 시드 문안을 새로 만든다.
- 테스터 계정으로 가입하면 잔고 0, 원장 0줄이다(가입 지급이 없다, ADR-0071). 시작 Coin은 온보딩의 닉네임 단계(ADR-0072)를 마친 계정에, `/admin/settings`의 시작 지급액에 값이 있을 때 원장의 '시작 지급' 한 줄로 생긴다. 값이 없으면 지급 안내와 지갑이 '시작 Coin은 준비되는 대로 지급됩니다.'를 보인다.

**실패하면.** 스크립트는 첫 오류(또는 SSM 세션이 끊기는 등의 중단)에서 멈추고, 3단계의 덤프를 지우지 않은 채 그 경로를 알린다. 4단계 뒤라면 api·worker가 멈춘 채로 남는다. 5단계(비우기)가 끝나기 전이면 데이터는 그대로이니 `sudo docker compose -f /data/buddha/compose.yaml up -d`로 되돌린다. 그 뒤라면 원인을 고친 뒤 스크립트를 다시 돌린다 — 다시 돌려도 안전하다(빈 DB를 덤프하고 다시 비운 뒤 버킷에 남은 것을 마저 지우고 시드한다). 다시 돈 실행이 성공하면 지우는 것은 그 실행이 뜬 덤프뿐이고, 실패한 실행의 덤프는 남는다(스크립트가 끝에 이름을 알린다). 7단계(버킷 비우기)가 시작된 뒤라면 덤프로 DB를 되돌려도 지운 이미지는 돌아오지 않는다 — 되돌린 글의 이미지는 없는 이미지(404)로 보인다. 초기화 전 상태로 되돌리려면 실패한 실행의 덤프를 [terraform/README.md](../terraform/README.md#수동-pg_dump) 「수동 pg_dump」의 실제 복구 절차로 넣고, Redis는 비운 채로 둔다(워커의 매 분 스캔이 마감·정산을 다시 잡는다).

**덤프 정리.** 덤프에는 테스터의 이메일·실명·본인확인한 휴대전화가 들어 있다. 성공한 실행은 자기 덤프를 스스로 지운다. 실패한 실행이 남긴 덤프는 복구나 재실행의 성공을 확인한 뒤 손으로 지운다(`sudo rm /data/buddha-pre-reset-<시각>.dump`). `/data`에 있는 동안은 일일 스냅샷(7개)에도 들어간다.

## #125 배포 때의 한 번 (마이그레이션 0017)

#125를 머지하면 평소 배포가 그대로 초기화한다: `deploy.sh`의 `migrate`가 0017을 적용하고(비우기 → 직접 AMM 열·enum 값 삭제) 시드가 다시 채운 뒤 컨테이너를 바꾼다. 따로 할 일은 없다.

- drizzle은 남은 마이그레이션을 한 트랜잭션에서 적용한다. 0017이 실패하면 아무것도 지워지지 않고, 이전 릴리스가 계속 돈다(`deploy.sh`가 `migrate` 실패에서 멈춘다).
- 배포 창: `migrate`가 도는 수십 초 동안 이전 api·워커가 지운 열을 읽어 500·잡 실패를 낸다. 새 컨테이너가 뜨면 풀린다(ADR-0046 D3과 같다).
- 덤프는 자동으로 남지 않는다. 남기려면 머지 전에 [terraform/README.md](../terraform/README.md#수동-pg_dump)의 「수동 pg_dump」를 한다.
- 0017은 Redis를 건드리지 않는다. 지운 시장을 가리키던 지연 잡(`market.close`·`market.finalize`)은 워커에서 'not found'로 세 번 실패하고 버려진다. 데이터에는 영향이 없다. 로그까지 깨끗이 하려면 배포 직후, 테스터가 다시 가입하기 전에 위 스크립트를 한 번 돌린다. #149의 리허설도 된다.

## #70 배포 때 (오너 결정 2026-10-18)

#70(마이그레이션 0031)은 가입 트리거의 10,000 Coin(`BONUS`) 지급을 없애고, 시작 Coin을 본인확인한 번호마다 한 번 `START_GRANT`로 주게 한다. 0031은 기존 계정의 잔고·원장을 건드리지 않으므로(D4), 그대로 두면 #70 전에 가입한 계정은 가입 때 받은 10,000 Coin에 더해 온보딩(#58)을 마친 뒤 시작 Coin도 받는다. 오너는 이것을 코드로 막지 않고, #70을 배포할 때 배포 DB를 이 문서의 절차로 초기화하기로 했다(ADR-0071 결정 1의 답 1). **시점은 오너가 정한다.**

- **#70이 배포된 뒤에** 돌린다: 배포 워크플로가 0031을 적용하고 새 api가 뜬 뒤(`/api/health` 200). 그 전에 돌리면 옛 트리거가 남아 있어 다시 가입한 계정이 또 10,000 Coin을 받는다. 배포 전에 `PHONE_HASH_KEY`를 만드는 `terraform apply`는 그대로 먼저 한다([terraform/README.md](../terraform/README.md)의 '#70(마이그레이션 0031)을 처음 배포할 때 한 번').
- 하는 일은 [운영 호스트에서](#운영-호스트에서)와 같다(`sudo bash /data/buddha/reset-db.sh --yes`). 계정까지 모두 지우므로 테스터는 다시 가입하고 다시 본인확인한다.
- 확인: [운영 호스트에서](#운영-호스트에서)의 '확인'에 더해, 비운 뒤 원장에 `BONUS` 행이 없다(`SELECT count(*) FROM ledger_entries WHERE type = 'BONUS'`가 0 — 쿠폰도 닫혀 있다, ADR-0049). 다시 가입한 계정은 잔고 0으로 시작한다.
- #58 전에 초기화하면 다시 가입한 계정은 #58이 배포될 때까지 0 Coin에 머문다(오너가 받아들인 공백, ADR-0069 결정 4 #70).

## 로컬 개발 환경

개발 DB도 0017을 적용하는 다음 `pnpm db:migrate`에서 한 번 비워진다(시험 DB는 원래 시험마다 비운다). 개발 Redis에 남은 지연 잡도 위처럼 실패하고 버려진다.

같은 초기화를 로컬에서 하려면 `pnpm dev`를 멈추고 다음을 돌린다. `wipe-cli`는 `@buddha/shared` 빌드가 있어야 한다(`pnpm build`나 `pnpm dev`를 한 번 돌렸으면 된다).

```bash
pnpm --filter @buddha/db run db:wipe --yes   # .env의 DATABASE_MIGRATE_URL
docker compose exec redis redis-cli FLUSHALL
pnpm db:migrate && pnpm db:seed
```

글 이미지와 프로필 이미지의 로컬 저장소(저장소 루트의 `.media/`, ADR-0073·ADR-0079)는 DB와 따로 남는다(운영의 7단계와 달리 로컬 폴더는 스크립트가 건드리지 않는다). 지운 행이 가리키던 파일이므로 아무 데도 보이지 않는다. 함께 비우려면 `rm -rf .media`.

볼륨째 지우는 `docker compose down -v`도 된다. 이때는 롤 초기화 SQL부터 다시 돈다.
