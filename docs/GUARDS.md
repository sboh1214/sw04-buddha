# 회귀 가드 등록 규칙

기획이 제외한 기능이 화면·API·저장 데이터에 다시 들어오거나, 공개 응답과 공개 실시간 이벤트에 본인 전용·인증·내부 정보가 실리거나, 다른 계정의 비공개 자산·주문을 조회할 수 있게 되면 평소 시험이 실패하게 하는 검사다(#113). 이 문서는 검사가 무엇을 어디서 보는지와 등록 규칙을 적는다. 결정과 근거는 [ADR-0057](DECISIONS.md)에 있다. 기획 인용 표기(NR, N00\~N06 §n)와 오너 결정 D1\~D26은 ADR-0047을 따른다. 뒤 이슈는 공개 API·본인 전용 API·공개 실시간 이벤트·알림 유형을 더할 때 이 문서대로 등록한다.

- 기획: 독립 확률 입력이 어느 화면에도 없고 매수 입력값이 개인 신념 확률로 저장되지 않아야 한다(N02 §10). 계정 이메일·인증 정보·내부 위험 플래그를 노출하지 않고, 초기에는 잔액·주문·미정산 보유 수량·개별 체결·손익이 본인 전용이다(N04 §2). 다른 사용자가 비공개 자산·주문을 조회할 수 없어야 한다(N04 §7). 상대 계정은 익명으로 표시한다(N01 §5).
- 오너 결정(2026-10-13, #113): 등록이 빠진 공개 API·이벤트를 검사가 스스로 찾아내 실패시킨다((a)). '점수·순위를 제공하지 않습니다' 같은 부정 안내는 서비스 안내(#136)에서만 허용하고((b)), 현금 환전·출금을 제공하지 않는다는 안내는 어디서나 허용한다.
- 오너 결정(2026-10-14, #113 추가 답): 서비스 안내의 부정 문장은 #14 용어 표의 낱말('확률'·'투표'·'예측')이 들어 있어도 허용한다. 대회 어휘(상금·참가비·우승)는 제외 목록에 넣지 않는다(챌린지 #81에서 다시 본다). API의 제외 기능 이름 검사는 공개 API만 보고, 송금·활동량 보상·현금 환전·출금은 경로만 모든 API에서 본다. 관리자 화면은 도박 어휘만 검사하고, 메일은 모든 제외 기능 문구를 검사한다.

## 언제 도나

- 평소 시험과 함께 돈다. `pnpm test`(`turbo run test`)와 CI의 `turbo run lint typecheck test build`가 돌리고, 켜고 끄는 설정이나 환경 변수는 없다.
- 대부분은 DB 없이 도는 정적 검사다. 실제 응답을 보는 `apps/api/src/surface/private-data.test.ts`만 test 프로필의 Postgres·Redis가 필요하다. 로컬에서 `TEST_*`가 없으면 그 시험은 건너뛰고(CI에서는 실패한다), 같은 파일의 'private data cases (static)'은 DB 없이도 돈다.
- API의 정적 검사는 커밋된 `apps/api/openapi.json`을 읽는다. 컨트롤러나 응답 스키마를 고쳤으면 `pnpm api:openapi`로 다시 만든 뒤 결과를 믿는다. 문서가 코드와 어긋나면 CI의 `OpenAPI contract check`가 실패한다. 실제 응답의 필드 이름은 런타임 검사가 따로 본다.
- **#149의 출시 점검이 이 검사를 다시 돌린다.** 아래 '검사와 자리' 표의 시험이 모두 대상이다.

- **화면 문구**는 사람이 읽는 글이다: 웹 문구, 메일, 시드 시장 문구, 알림 문구. `words`로 찾는다(`findExcludedText`). 관리자 화면은 도박 어휘만 찾고(`ADMIN_SCREEN_FEATURES`), 메일과 회원 화면은 모든 항목으로 찾는다(오너 결정 2026-10-14).
- **화면 주소·메뉴, API, 저장 데이터**는 식별자다. 식별자를 낱말로 나눠(`identifierWords`: `realizedPnlCoin`, `realized_pnl_coin`, `/admin/audit-failures`) 한 낱말이 토큰이나 그 굴절형(`tokenForms`: `rankings`, `scoring`, `withdrawal`)과 같으면 걸린다(`findExcludedIdentifier`). 그래서 `p_yes_bp`나 `priceAvgBp`는 걸리지 않는다. 두 낱말 토큰(`check in`, `send coin`, `daily bonus`)은 함께일 때만 그 뜻이라, 두 낱말이 잇달아 있거나(`checkIn`, `/me/check-in`, `sendCoins`) 한 낱말로 붙어 있으면(`DAILY_CHECKIN`) 걸린다. 홀로 쓴 `send`·`give`·`tip`(메일·인증 코드 발송, 도움말)은 토큰이 아니고 Coin과 함께일 때만 찾는다. 경로 토큰(`pathTokens`)은 경로(화면 주소·메뉴, API 라우트 경로)와 큐·작업 이름에서만 찾는다. 지금은 활동량 보상의 `bonus` 하나다. 필드와 저장 이름에서는 시작 Coin의 `BONUS`이기도 해서 찾지 않고, 저장 이름은 `BONUS_NAMES`가 따로 본다.
- **API**는 공개 API다: 공개 라우트와 better-auth 라우트의 경로, OpenAPI 문서의 공개 작업의 경로·매개변수·스키마·필드 이름과 enum·const 값, 공개 응답의 실제 필드, 시장 채널 이벤트의 필드. 알림 유형 이름도 API 토큰으로 찾는다. 모든 오류 봉투에 붙는 `ErrorCode`의 값은 유료 구매만 찾지 않는다(보존한 결제 코드의 `PAYMENT_GATEWAY_*`). 본인 전용·관리자 라우트는 경로만, 그것도 송금·활동량 보상·현금 환전·출금(`EVERY_ROUTE_PATH_FEATURES`)만 찾는다. 송금과 출금은 본인 전용 라우트로, 활동량 보상은 관리자 라우트로 들어올 수 있어서다(오너 결정 2026-10-14). 같은 셋을 워커의 큐·작업 이름에서도 경로처럼 찾는다. 매일 주는 보상은 허용한 원장 유형(`BONUS`)에 Coin을 넣는 예약 작업으로 들어오기 쉬워서다. 본인 전용·관리자 응답의 필드와 문서의 작업은 이름으로 보지 않는다. 유료 구매는 공개 라우트와 공개 응답에서만 찾고, 보존한 결제 코드는 뺀다(D9). 결제·쿠폰 코드와 표, 관리자 충전 상품·쿠폰 관리는 남아 있어서다(ADR-0049).
- **용어와 도박 어휘**는 [docs/TERMS.md](TERMS.md)의 대응표(`REPLACED_TERMS`)에서 가져온다. 대응표를 고치면 이 검사도 따라 바뀐다. '뜻' 행은 `TERM_MEANING_PATTERNS`로 찾는다. 읽는 법은 TERMS.md의 '찾는 법'에 있다.
- **개인 확률**: 사람에게 묶일 수 있는 표의 이름과 열에 `PERSONAL_PROBABILITY_WORDS`(prob·probability·belief·credence·confidence·forecast 등)의 낱말이 없어야 한다(`namesPersonalProbability`, N02 §10, N04 §5). 사람에게 묶일 수 있는 표는 `user`, 외래 키가 있든 없든 계정 열(`userId`·`user_id`·`accountId`)이 있는 표, 그 표들을 직접이나 다른 표를 거쳐 가리키는 표다(체결은 주문의 것, 결제 이벤트는 결제의 것). 시장 단위의 가격(`price_ticks.p_yes_bp`)은 개인 확률이 아니다. 공개 API(공개 라우트 경로, 문서의 공개 작업의 경로·매개변수·스키마·필드 이름, 공개 응답의 실제 필드, 시장 채널 이벤트의 필드)에는 그 낱말이 아예 없어야 한다. 거기서 확률은 누군가의 입력이거나 Community Forecast의 집계이고(N02 §1, N00 §5), 시장가격은 확률이라 부르지 않는다([docs/TERMS.md](TERMS.md)). 본인 전용·관리자 API와 본인 방 이벤트는 이 낱말로 보지 않고(오너 결정 2026-10-14의 API 범위), 웹의 주소도 보지 않는다(ADR-0057 결과 5). 화면 문구의 '확률'은 용어 행이, 주소의 `forecast`·`belief` 등은 `probability-input`의 토큰이 찾는다.
- **목록을 바꾸는 것은 결정이다.** 항목·낱말을 빼거나 넓히는 PR은 기획 절이나 오너 결정을 `basis`에 적는다. 점수·순위를 다시 들이면 #110의 결정이, 유료 Coin 판매를 열면 #111의 결정이, 대회 어휘(상금·참가비·우승)를 넣기로 하면 챌린지(#81)의 결정이 이 목록과 아래 허용을 고친다.

## 공개 금지 항목

공개 응답과 공개 실시간 이벤트에 실리면 안 되는 것은 한곳, `packages/shared/src/guards/private-data.ts`의 `PRIVATE_DATA`(`@buddha/shared`)다. 항목마다 이름·근거·필드(식별자 낱말의 줄)가 있다. 필드 이름을 낱말로 나눠 그 줄을 담고 있으면 걸린다(`findPrivateField`: `['real', 'name']`은 `realName`·`buyerRealName`에 걸리고 `nameKo`에는 걸리지 않는다). 공개된 익명 체결이나 시장가격은 비공개가 아니다. 그것을 누구의 것으로 만드는 것은 옆에 붙은 계정이나 '누구의 것'이라는 이름이다. `myFills`처럼 `my`·`mine`을 쓴 이름, 그리고 체결·거래 낱말(`fill`·`trade`)과 사용자·계정·회원·본인 같은 낱말을 어디에든 함께 쓴 이름(`userFills`·`accountFills`·`fillsByUser`, 항목의 `owned`)이 체결 내역이다. 익명의 `fills`·`recentFills`는 공개다.

- 관리자 화면: `app/admin` 아래 파일과, `app/` 밖에서 관리자 코드만 가져다 쓰는 컴포넌트·훅·lib(가져오는 곳을 따라 찾는다. 시험 파일은 세지 않고, Next가 직접 부르는 `proxy.ts`는 관리자 것이 되지 않는다), 그리고 그 파일들만 읽는 copy 키다. 문구는 도박 어휘만 검사하고(`ADMIN_SCREEN_FEATURES`), 원화 가격 표시도 찾지 않는다(오너 결정 2026-10-14). 회원 화면도 가져다 쓰는 파일은 회원 화면의 것이다. 주소와 링크는 다른 화면처럼 검사한다.
- `PRESERVED_PAID_SOURCES`: 유료 판매를 끈 동안 회원 화면에 닿지 않는 보존한 결제 코드(공개 `/charge`, 지갑의 충전·쿠폰·결제 내역 컴포넌트, 메뉴에서 뺀 관리자 충전 상품·쿠폰·결제 화면, 그 도우미). 유료 구매만 빠지고 다른 항목은 그대로 검사한다. 관리자 화면의 줄은 그 주소와 링크를 위한 것이다(문구는 관리자 화면이라 도박 어휘만 본다). `PAID_COIN_SALES_ENABLED`가 `false`일 때만 성립하므로 시험이 그 값을 고정하고, 목록의 경로가 모두 있는지도 본다.
- 판매 스위치가 여는 분기(`PAID_COIN_SALES_ENABLED ? … : …`의 참 쪽, `PAID_COIN_SALES_ENABLED && …`, `if (PAID_COIN_SALES_ENABLED) …`) 안의 문구·`copy` 읽기·`formatKrw`도 유료 구매만 빠진다(`screen-text.ts`의 `gated`).
- `COPY_ALLOWANCES`: copy 키별 허용. 지갑 이용 내역의 원장 유형 라벨 `ledgerTypeDeposit`·`ledgerTypePaymentCancel`·`ledgerTypePaymentCancelReversal`(충전·결제, 판매를 닫기 전의 행을 부르는 이름, D9)과 실명·휴대전화 수집 목적 안내 `onboardingSubtitle`·`settingsContactHint`·`setPasswordContactHeading`(결제·구매, #58이 온보딩을 고칠 때까지, ADR-0049). 허용할 낱말이 그 값에서 없어지면 시험이 실패하므로 그때 허용을 지운다.
- `SERVICE_GUIDE_ROOT`(`app/(service-guide)`): 서비스 안내(#136) 화면의 자리. 이 아래 파일과 이 아래에서만 읽는 copy 키는 서비스 안내의 허용을 받는다. 라우트 그룹은 주소에 들어가지 않으므로 주소는 #136이 정한다. 아직 아무것도 없어서 지금은 부정 안내가 어디서나 실패한다.
- `PRICE_FORMATTERS`(`formatKrw`): 원화 가격을 그리는 함수. 보존한 결제 코드와 판매 스위치 분기 밖에서 쓰면 가격표(N06)로 본다.
- `LEGAL_BODIES`(`test/screen-text.ts`): 약관 본문 네 파일. #137이 개정할 때까지 도박 어휘만 검사한다.

**API**(`apps/api/src/surface/registry.ts`). `preservedPaid: true`인 공개 라우트(`GET /charge-packages`, `GET /payments/provider`)만 공개에서 유료 구매를 말할 수 있다. `PaidCoinSalesGuard`가 그 라우트의 첫 가드이고 판매를 끈 동안 404로 답한다. 시험이 스위치가 `false`임과, 그 가드가 막는 라우트와 표시가 서로 맞는지를 고정한다.

**저장 데이터**(`packages/db/src/storage-names.test.ts`). 유료 구매는 찾지 않는다. 결제·충전 상품·쿠폰 표와 그 원장 유형·관리자 작업 유형은 보존한다(D9). `VARCHAR_VALUES`에 넣지 않은 열은 `approval_requests.kind`(작업마다 소비 이슈가 이름을 정하고 아직 목록이 없다, ADR-0056)와 `admin_actions.target_type`(대상 표의 이름)이다. `BONUS_NAMES`: 보너스를 담은 저장 이름(표·열·제약·enum·값) 가운데 허용한 것과 이유. 지금은 원장 유형 값 `BONUS`(인증된 계정에 한 번 주는 시작 Coin, N01 §2, 보존한 쿠폰 사용, D9) 하나다. 줄이 더 필요 없어져도 시험이 실패한다.

**시드 시장 문구**(`packages/db/src/seed-markets.test.ts`). 질문의 대상인 원화 금액('1,400.0원 이상', 단위를 붙인 '3만 원')은 유료 구매의 원화 가격 낱말에서 지운다. 원/달러 환율을 묻는 시장의 주제이지 Coin의 가격이 아니다. 충전·결제·할인·'₩' 같은 다른 낱말은 그대로 찾는다.

## 등록 규칙

### 공개 API

`SessionGuard`가 없는 라우트다. 로그인하지 않은 방문자도 부를 수 있다.

1. `apps/api/src/surface/registry.ts`의 `PUBLIC_ROUTES`에 한 줄을 넣는다. 키는 컨트롤러가 쓴 그대로의 `'METHOD /path'`다(`/api`와 버전 없이, 매개변수는 `:id`). `reason`(한국어)에 왜 공개인지와 그 기획 근거, 무엇을 돌려주는지 적는다. 리뷰어가 읽는 것이 이 사유다.
2. 보존한 결제 코드라면 `preservedPaid: true`를 붙이고 `PaidCoinSalesGuard`를 첫 가드로 건다. `@ApiExcludeController`로 OpenAPI 문서에서 뺀 라우트는 `undocumented: true`를 붙이고 `docs/API.md`의 손으로 쓴 절에 적는다(그 글은 `scripts/generate-api-doc.mjs` 안에 있다).
3. `apps/api/src/surface/private-data.test.ts`에 부르는 법을 넣는다. 경로 매개변수마다 `PUBLIC_PARAMS`에 이름으로 값을 둔다(A의 기록을 가리키게). GET이 아니면 `PUBLIC_BODIES`에 본문을 둔다(A에 대해 가장 많이 말하게 하는 요청).
4. 응답 필드가 `PRIVATE_DATA`나 제외 기능 이름에 걸리면 응답을 고친다(위 '공개 금지 항목').
5. `pnpm api:openapi`를 돌려 결과를 함께 커밋한다.

빠뜨리면: `registry.test.ts`가 모듈 그래프에서 찾은 공개 라우트(컨트롤러가 상속한 처리기도 Nest의 `MetadataScanner`로 찾는다) 가운데 등록이 없는 것과, 등록됐는데 없어졌거나 부류가 바뀐 것을 실패시킨다(오너 결정 (a)). `private-data.test.ts`의 정적 시험이 매개변수 값이나 본문이 없는 라우트를 DB 없이 실패시킨다. 공개 라우트에 `SessionGuard`를 걸거나 빼면 줄을 `PUBLIC_ROUTES`와 `OWNER_ROUTES` 사이에서 옮긴다.

런타임 검사는 계정 A의 이메일·닉네임·실명·휴대전화·비밀번호·세션·잔액·원장 메모·주문과 체결·보유와 손익·결제를 심고, 모든 공개 라우트를 비로그인·B·A로 불러 답에 A의 값, 금지 항목의 필드, 제외 기능 이름의 필드가 없는지 본다. 보존한 결제 라우트는 404, 나머지는 200이어야 한다. A의 닉네임과 계정 id도 찾는 값이다. 지금 사람을 보이는 공개 라우트가 없어서다. 공개 프로필·글(#41·#46)처럼 사람을 보여야 하는 공개 응답을 더할 때 이것을 어떻게 다룰지는 열려 있다(ADR-0057 결과 5).

### 본인 전용 API

`SessionGuard`가 있고 `AdminGuard`가 없는 라우트다. 세션 계정 자신의 것만 답한다.

1. `registry.ts`의 `OWNER_ROUTES`에 한 줄을 넣는다. 키는 공개 API와 같고, `reason`에 누구의 무엇을 돌려주거나 바꾸는지와 기획 근거를 적는다. 보존한 결제 코드는 `preservedPaid: true`.
2. `private-data.test.ts`의 `OWNER_CASES`에 교차 계정 경우를 넣는다. B가 A를 겨냥해 부르는 요청이다.
   - `params`: 경로 매개변수마다 A의 기록을 가리키는 값.
   - `query`: 라우트가 읽는 쿼리 키마다 값(`@Query('키')`의 키와 `@Query({ schema })` 객체 스키마의 키, `queryKeysOf`). 키가 A의 기록이나 A를 가리킬 수 있으면 A의 것을 준다(A의 행으로 만든 페이지 커서, A의 id). 지금 원장·주문·결제 목록은 A의 가장 새 행 바로 뒤에서 시작하는 커서로, 보유는 `status=open`으로 부른다. 객체 스키마 없이 쿼리 전체를 받는 `@Query()`는 키를 셀 수 없어 실패하므로 스키마를 단다.
   - `body`: GET이 아니면 본문. 본문이 계정을 받으면(`expectedAccountId` 등) A의 계정.
   - `status`: B가 받아야 하는 답(자기 것만 보이는 목록은 200, A의 기록 하나는 404, A의 계정을 댄 쓰기는 403 등).
   - `own`: 같은 요청을 A가 하면 보이는 A의 값(표지값의 라벨). 검사가 눈먼 것이 아님을 확인한다. A를 바꾸는 쓰기에는 두지 않는다.
3. 새 라우트가 다루는 A의 비공개 기록이 표지값에 없으면 시험의 `seed()`에 그 기록을 심고 표지값을 더한다.

빠뜨리면: `registry.test.ts`가 등록이 없는 본인 전용 라우트를, `private-data.test.ts`의 정적 시험이 `OWNER_CASES`가 `OWNER_ROUTES`와 다르거나 경로 매개변수·쿼리 키·본문이 빠진 경우를 DB 없이 실패시킨다. 런타임 검사는 B가 그 경로·쿼리·본문으로 부른 답에 A의 값이 없고 상태가 `status`인지, A가 같은 요청을 하면 답에 `own`이 있는지 본다.

이름: 본인 전용 라우트의 경로에 송금·활동량 보상·현금 환전·출금의 토큰이 있으면 `registry.test.ts`가 실패한다(`/me/coins/send`, `/me/withdrawals`). 그 밖의 이름(본인의 점수나 확률을 담은 필드 등)은 보지 않는다(오너 결정 2026-10-14).

### 관리자 API

이 등록 목록에 넣지 않는다. 모든 관리자 라우트는 `/admin` 아래에 두고 `SessionGuard` 다음 `AdminGuard`를 건다. `admin-access.test.ts`가 그것을, `admin-audit.test.ts`가 상태를 바꾸는 라우트마다의 작업 유형을 확인한다(ADR-0036·ADR-0056). 관리자 라우트는 경로만 송금·활동량 보상·현금 환전·출금의 이름 검사를 받는다(`/admin/rewards`는 실패한다, 오너 결정 2026-10-14). 필드와 문서의 작업은 이름으로 보지 않는다.

### better-auth 라우트

better-auth가 Nest 라우팅 앞에서 `/api/auth` 아래에 내는 라우트다. 모듈 그래프에 보이지 않고 누구나 부를 수 있다(세션은 라우트가 스스로 본다).

1. `registry.ts`의 `AUTH_ROUTES`에 한 줄을 넣는다. 키는 `'METHOD /path'`(`/api/auth` 뒤의 경로)이고 `reason`에 무엇을 누구에게 하는지 적는다.
2. 계정 데이터(사용자·세션·연결된 계정·제공자 토큰)를 답하는 라우트는 `answersAccount: true`를 붙이고 `private-data.test.ts`의 `AUTH_CASES`에 경우를 넣는다.
   - `request`: 비로그인과 B가 보내는 것. 계정이나 계정 id를 받으면 A의 것.
   - `status`: 둘이 받아야 하는 답(`anonymous`, `B`).
   - `own`: A가 보내면 보이는 A의 값(표지값의 라벨). A를 바꾸거나 A의 것이 보일 수 없으면 두지 않는다.

빠뜨리면: `registry.test.ts`가 인증 인스턴스(`createAuth`로 앱과 같게 만들고 OAuth 제공자를 모두 켠 것)의 `auth.api`에서 경로가 있는 엔드포인트를 메서드마다 찾아(플러그인의 것 포함, 서버 전용과 `disabledPaths` 빼고) 등록이 빠진 것과 더는 내지 않는 줄을 실패시킨다(오너 결정 (a)). 플러그인(#183의 SMS OTP 등)을 켜거나 better-auth를 올려 엔드포인트가 늘면 여기서 걸린다. `private-data.test.ts`의 정적 시험은 `answersAccount` 줄과 `AUTH_CASES`가 다르면 DB 없이 실패한다. 런타임 검사는 앱의 실제 인증 인스턴스가 내는 라우트가 `AUTH_ROUTES`와 같은지와, 각 경우의 답에 A의 값이 없는지 본다. `/sign-up/email`은 꺼 두었다(ADR-0024, 서버의 `RegistrationService`만 부른다).

### 실시간 이벤트

공개 방은 `market:<id>`(누구나 구독), 본인 방은 `user:<id>`(핸드셰이크 세션이 들어간다)다.

1. `packages/shared/src/realtime.ts`의 `REALTIME_EVENT_TYPES`에 유형을 넣고 스키마를 그 계열(`marketRealtimeEventSchema` 또는 `userRealtimeEventSchema`)에 더한다.
2. `packages/shared/src/guards/realtime-events.ts`의 `REALTIME_EVENT_REGISTRY`에 `channel`(`'market'` 또는 `'user'`)과 `reason`(한국어: 무엇을 알리는지와 기획 근거)을 넣는다. 유형을 키로 하므로 빠뜨리면 컴파일이 실패한다.
3. 본인 방 이벤트면 `realtime-events.test.ts`의 `USER_EVENTS`와 `private-data.test.ts` 시장 방 시험의 `own`에 그 이벤트의 예를 하나씩 더한다. 둘 다 유형마다 하나를 요구해서 빠뜨리면 컴파일이 실패한다.
4. `scripts/generate-api-doc.mjs`의 `REALTIME_EVENTS`에 방·설명·순서 키를 넣는다. 없으면 `pnpm api:openapi`가 실패한다.

게이트웨이와 소켓에 이벤트를 보내는 곳도 등록한다(오너 결정 (a)). 소켓은 로그인 없이도 열리므로 공개 표면이다.

- 새 `@WebSocketGateway`, 새 네임스페이스, 클라이언트가 보내는 새 메시지(`@SubscribeMessage`)는 `apps/api/src/surface/registry.ts`의 `REALTIME_GATEWAYS`에 네임스페이스를 키로 메시지 목록과 `reason`(한국어: 누가 무엇을 할 수 있고 무엇을 받는지)을 적는다. 지금은 `/ws`의 `subscribe`·`unsubscribe`다.
- 소켓에 보내는 코드를 더하면 `REALTIME_EMITS`에 파일(`src/` 아래 경로)·이벤트(호출에 쓴 그대로)·보내는 것의 스키마(`payload`: zod 스키마, 본문 없는 신호는 `null`)·`reason`을 적는다. 보내는 코드는 `emit`(`emitWithAck`·`serverSideEmit` 포함), 소켓 패키지를 가져오는 파일의 `send`·`write`(이벤트 `message`), 반환 형식이 `void`·`Promise<void>`가 아닌 `@SubscribeMessage` 처리기, 그리고 클라이언트의 응답 콜백(ack)을 부르는 곳이다. Nest가 처리기가 돌려준 값을 클라이언트에 보내므로(응답이나 `{ event, data }`) 그 처리기는 이벤트 `reply to '<메시지>'`로 적는다. 처리기의 `@Ack()` 매개변수는 읽는 곳마다(부르거나 다른 함수에 넘기거나) `ack to '<메시지>'`로, 소켓 패키지를 가져오는 파일에서 `on`·`once` 등으로 단 리스너가 마지막 인자(Socket.IO가 넘기는 응답 콜백)를 부르는 곳은 `ack to '<이벤트>'`로 적는다. 리스너는 그 자리에 쓴 함수, `this.멤버`, 파일이 그 이름으로 선언한 함수까지 따라간다. 데코레이터는 가져온 이름으로 읽는다(`import { SubscribeMessage as OnMessage }`, `import * as ws`). 그래도 읽지 못한 처리기(지역 상수나 합성 데코레이터로 붙인 것)는 Nest가 등록한 처리기·`@Ack()` 매개변수와 소스에서 읽은 것이 달라 실패한다. 지금 방에 가는 이벤트는 게이트웨이가 채널 계열 스키마로 파싱한 `event.type` 하나뿐이고, 그 밖의 `emit`은 그 소켓에만 가는 거절 봉투와 본문 없는 재동기화 신호다.
- 보내는 값은 줄의 `payload`로 검사한다. 시험은 API 소스를 TypeScript 형식 검사기로 읽어 보내는 값(이벤트 뒤의 인자, `send`·`write`의 인자, 응답 콜백을 부른 인자, 처리기가 돌려주는 값은 반환 형식)의 형식에서 속성 이름을 모든 깊이로 꺼낸다(배열의 원소와 합집합의 각 형식까지. 메서드와 `Date` 같은 TypeScript 기본 라이브러리 형식은 값으로 보고 이름을 꺼내지 않는다). 그 이름이 스키마(`z.toJSONSchema`의 속성 이름)에 없으면 실패하고, 그 이름이나 보내는 식에 적은 객체 리터럴의 키(스키마가 열어 둔 `details` 안의 `{ retryAfterSeconds }` 등), 스키마의 이름이 금지 항목·제외 기능·확률 낱말이면 실패한다. `null`로 적은 줄이 값을 보내도, 응답 콜백을 다른 함수에 넘겨 보내는 자리에서 값을 읽을 수 없어도 실패한다. 방에 가는 이벤트(`roomEvent: true`, 스키마 `realtimeEventSchema`)는 이름이 스키마에 있는지만 보고, 이름의 금지 검사는 채널별로 `realtime-events.test.ts`가 한다(본인 방 이벤트는 본인 것이다). 지금은 오류 봉투 두 곳이 `errorEnvelopeSchema`, 재동기화 신호가 `null`이다.

빠뜨리면 `registry.test.ts`가 모듈 그래프의 프로바이더에서 찾은 게이트웨이(네임스페이스와 메시지)와, 소스에서 찾은 보내는 곳이 목록과 다르다고 실패한다. 리스너를 이름이 아닌 값으로 넘기거나(`client.on(event, handlers[event])`) 미들웨어(`use`)·`onAny`에서 응답 콜백을 부르는 것, 리스너가 응답 콜백을 다른 함수에 넘기는 것은 보지 않는다. 보내는 값의 형식이 `unknown`·`any`이면 그 안의 이름은 형식으로 읽을 수 없어, 식에 적은 객체 리터럴의 키만 본다.

검사: 등록한 채널이 게이트웨이가 그 이벤트를 파싱하는 계열과 같고, 시장 채널 스키마의 필드에 금지 항목과 제외 기능 이름, 확률·믿음 낱말이 없으며(공개 API, 오너 결정 2026-10-14), 본인 방 이벤트는 시장 채널 이벤트로 읽히지 않는다. 런타임 검사는 시장 방을 구독할 때 받는 거절 봉투(구독 적용을 기다리는 데 쓴다)에 A의 값과 금지 필드가 없는지 보고, 비로그인·B로 시장 방을 듣는 동안 A의 이벤트를 A의 방에 발행하고 시장 채널에도 몰래 실은 뒤, 관리자 마감으로 실제 `market:status`를 발행해 시장 방에 그것만 오는지 본다. `market:tick`·`market:trade`는 아직 발행하는 경로가 없다(#119). 공개 이벤트를 실제로 발행하는 경로를 더하는 이슈는 이 시험에서 그 경로로 이벤트를 발행해, 받은 이벤트에도 A의 값과 금지 필드가 없음을 확인하게 한다.

### 웹이 페이지 밖에서 답하는 것

`apps/web`의 Next 프록시(`app/` 옆, 곧 `src/`의 `proxy.ts`나 옛 이름 `middleware.ts`. 맞는 라우트보다 먼저 돌고 스스로 답을 돌려줄 수 있다), 라우트 핸들러(`app/` 아래의 `route.ts`·`route.js`), 메타데이터 라우트(`app/` 아래의 `favicon`·`sitemap`·`robots`·`manifest`·`opengraph-image`·`twitter-image`·`icon`·`apple-icon`, 확장자와 번호(`icon1.png`)를 가리지 않고 만든 것이든 정적 파일이든), Pages Router의 API 라우트(`pages/api/`), 서버 액션(`'use server'` 파일이나 함수)은 API의 등록 목록 밖에서 요청에 답한다. 시험은 화면 문구를 읽는 스크립트만이 아니라 `app/`·`pages/` 아래 모든 파일과 `src/`의 모든 스크립트를 본다. 서버 액션은 스크립트를 TypeScript 파서로 읽어, 모듈이나 함수 본문을 여는 지시문(다른 지시문 뒤도 포함)의 `'use server'`로 찾는다. 같은 줄에 코드가 이어지거나(`async function save() { 'use server'; … }`) 뒤에 주석이 붙어도 찾는다. 지금은 프록시 하나다(`/admin`·`/my` 요청의 경로와 쿼리를 헤더에 덮어써 넘기기만 한다. 읽기와 쓰기는 API로 간다). 더하면 `apps/web/src/excluded-features.test.ts`의 `WEB_SERVER_ENDPOINTS`에 무엇을 답하는지와 이유를 적는다. 키는 `src/` 아래 파일이고(`proxy.ts`), 라우트 핸들러는 파일과 내보낸 HTTP 메서드마다 따로다(`app/feed/route.ts GET`, `app/feed/route.ts POST`). 메서드마다 따로 답하므로 등록한 파일에 메서드를 더해도 실패한다. 메서드는 `export function GET`, `export const PUT = …`(구조 분해 포함), `export { handler as POST }`, 이름으로 다시 내보내기, CommonJS(`exports.GET =`, `module.exports = { GET }`)로 읽고, `export * from`은 무엇이 오는지 알 수 없어 `*`로 등록한다. 빠뜨리면 그 시험이 실패한다. 이 검사는 등록과 사유만 요구하고, 답의 내용은 `private-data.test.ts`가 부르지 않는다.

### 알림 유형

알림 기능(#53) 전이라 자리만 있다.

1. `packages/shared/src/guards/notifications.ts`의 `NOTIFICATION_TYPES`에 유형마다 `type`(API와 저장 행이 쓰는 이름), `text`(사람이 읽는 모든 문구: 제목과 본문, 자리표시자는 쓴 그대로), `reason`(무엇을 알리는지와 기획 절)을 넣는다.
2. #53은 알림 유형 목록을 만들 때 이 목록을 그 원천으로 쓰거나 두 목록이 같음을 시험으로 고정해, 등록되지 않은 유형이 생기지 않게 한다. 어느 쪽으로 할지는 #53이 정한다. 뒤에 유형을 더하는 이슈도 같은 목록에 넣는다.

검사: 유형 이름은 API 값이라 공개 API의 토큰(유료 구매 포함, N05 §4)으로, 문구는 화면 문구로 찾는다(`findExcludedNotification`). 점수·순위·Forecast 수정·유료 Coin 구매 유도 알림(N05 §4)과 활동량 보상 알림이 걸린다. 알림 문구는 서비스 안내가 아니므로 현금 환전·출금 미제공 밖의 부정 안내도 걸린다.

### 저장 데이터의 값 목록

Postgres enum의 값은 저절로 검사된다. varchar 열이 고정 목록에서 값을 받으면(`market_events.type` 방식) 그 목록을 `packages/db/src/storage-names.test.ts`의 `VARCHAR_VALUES`에 `'표.열'`로 넣는다. 시험은 그 열이 실제로 있는지도 본다. 활동량 보상이나 송금은 새 원장 유형이나 작업 유형으로 들어올 가능성이 크다. 이름에 보상·출석·체크인·연속 기록·매일·로그인 보너스·송금·환전의 토큰이 있으면 토큰으로 걸리고, 보너스를 담은 값(`LIKE_BONUS`, `TRADE_VOLUME_BONUS`)과 표·열(`daily_bonuses`, `bonusClaimedAt`)은 `BONUS_NAMES`에 이유와 함께 있어야 통과한다. 그 밖의 이름이면 걸리지 않는다(아래 '검사하지 않는 것').

### 화면

- 새 화면 문구는 그냥 검사된다. 제외 기능 낱말이 그 뜻이 아니게 들어가야 하면 위 허용 가운데 맞는 것을 쓰고, 없으면 이유와 함께 가장 좁은 허용(구절, copy 키)을 더한다.
- 관리자 화면은 따로 등록하지 않는다. `app/admin` 아래 두거나 관리자 코드만 가져다 쓰면 도박 어휘만 검사된다. 관리자 전용이던 파일을 회원 화면이 가져다 쓰기 시작하면 그 파일은 회원 화면으로 모든 항목을 검사받는다.
- 보존한 결제 코드를 회원 화면에 다시 그리려면 그것은 유료 판매를 여는 일이다(#111). `PRESERVED_PAID_SOURCES`에 파일을 더해 비켜 가지 않는다.
- 서비스 안내(#136)는 `app/(service-guide)` 아래에 두거나, 다른 자리에 두면 `SERVICE_GUIDE_ROOT`를 그 폴더로 바꾼다. 부정 안내의 모양(`NEGATIVE_NOTICE`)이 #136의 문장에 맞지 않으면 그 이슈가 넓힌다.

## 검사하지 않는 것

- 저장된 행: 관리자가 쓴 시장 문구, 사용자가 고른 닉네임, 이미 DB에 있는 자동 닉네임 `예측가_XXXX`와 시드가 이미 넣은 시장 문구(TERMS.md '범위'). 검사는 코드와 스키마만 읽는다.
- 화면에 그려진 결과(Playwright로 페이지를 훑지 않는다). 화면 수준 확인은 #189다.
- `apps/mobile`(화면이 없는 Expo 스캐폴드), 마이그레이션 SQL의 트리거·함수 이름, 모든 오류 봉투에 붙는 `ErrorCode` 값의 유료 구매(`PAYMENT_GATEWAY_*`).
- 기록 문서: `docs/PLAN.md`(부록 A의 옛 문구 원칙 포함), `docs/QUESTIONS.md`, ADR 본문, 마이그레이션 주석.
- 대회 어휘(상금·참가비·우승). 제외 목록에 넣지 않았고 챌린지(#81)가 다시 본다(오너 결정 2026-10-14).
- 본인 전용·관리자 API의 경로 밖 이름(응답 필드, 문서의 작업)과 경로의 송금·활동량 보상·현금 환전·출금 밖 항목, 본인 방 이벤트의 필드 이름, 관리자 화면의 도박 어휘 밖 문구(오너 결정 2026-10-14). 비공개 정보 누출과 교차 계정 확인은 그대로 본다.
- 웹 주소의 확률·믿음 낱말(`PERSONAL_PROBABILITY_WORDS`). 확률 입력·Forecast의 토큰(`probability-input`)은 찾는다(ADR-0057 결과 5).
- 사용자에게 Coin이 들어오는 경로를 닫힌 목록으로 고정하는 일(#73). 지금은 이름으로만 찾는다. 낱말을 피한 이름(Coin 없이 `send`만 쓴 `/me/send`, 보상·보너스 낱말이 없는 원장 유형)은 걸리지 않는다.
