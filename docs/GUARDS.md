# 회귀 가드 등록 규칙

기획이 제외한 기능이 화면·API·저장 데이터에 다시 들어오거나, 공개 응답과 공개 실시간 이벤트에 본인 전용·인증·내부 정보가 실리거나, 다른 계정의 비공개 자산·주문을 조회할 수 있게 되면 평소 시험이 실패하게 하는 검사다(#113). 이 문서는 검사가 무엇을 어디서 보는지와 등록 규칙을 적는다. 결정과 근거는 [ADR-0057](DECISIONS.md)에 있다. 기획 인용 표기(NR, N00\~N06 §n)와 오너 결정 D1\~D26은 ADR-0047을 따른다. 뒤 이슈는 공개 API·본인 전용 API·공개 실시간 이벤트·알림 유형을 더할 때 이 문서대로 등록한다.

- 기획: 독립 확률 입력이 어느 화면에도 없고 매수 입력값이 개인 신념 확률로 저장되지 않아야 한다(N02 §10). 계정 이메일·인증 정보·내부 위험 플래그를 노출하지 않고, 초기에는 잔액·주문·미정산 보유 수량·개별 체결·손익이 본인 전용이다(N04 §2). 다른 사용자가 비공개 자산·주문을 조회할 수 없어야 한다(N04 §7). 상대 계정은 익명으로 표시한다(N01 §5).
- 오너 결정(2026-10-13, #113): 등록이 빠진 공개 API·이벤트를 검사가 스스로 찾아내 실패시킨다((a)). '점수·순위를 제공하지 않습니다' 같은 부정 안내는 서비스 안내(#136)에서만 허용하고((b)), 현금 환전·출금을 제공하지 않는다는 안내는 어디서나 허용한다.
- 오너 결정(2026-10-14, #113 추가 답): 서비스 안내의 부정 문장은 #14 용어 표의 낱말('확률'·'투표'·'예측')이 들어 있어도 허용한다. 대회 어휘(상금·참가비·우승)는 제외 목록에 넣지 않는다(챌린지 #81에서 다시 본다). API의 제외 기능 이름 검사는 공개 API만 보고, 송금·활동량 보상·현금 환전·출금은 경로만 모든 API에서 본다. 관리자 화면은 도박 어휘만 검사하고, 메일은 모든 제외 기능 문구를 검사한다.

## 언제 도나

- 평소 시험과 함께 돈다. `pnpm test`(`turbo run test`)와 CI의 `Unit Tests`(shared·web)·`Integration Tests (api)`·`Integration Tests (db)` job이 돌리고, 켜고 끄는 설정이나 환경 변수는 없다.
- 대부분은 DB 없이 도는 정적 검사다. 실제 응답을 보는 `apps/api/src/surface/private-data.test.ts`만 test 프로필의 Postgres·Redis가 필요하다. 로컬에서 `TEST_*`가 없으면 그 시험은 건너뛰고(CI에서는 실패한다), 같은 파일의 'private data cases (static)'은 DB 없이도 돈다.
- API의 정적 검사는 커밋된 `apps/api/openapi.json`을 읽는다. 컨트롤러나 응답 스키마를 고쳤으면 `pnpm api:openapi`로 다시 만든 뒤 결과를 믿는다. 문서가 코드와 어긋나면 CI의 `OpenAPI contract check`가 실패한다. 실제 응답의 필드 이름은 런타임 검사가 따로 본다.
- **#149의 출시 점검이 이 검사를 다시 돌린다.** 아래 '검사와 자리' 표의 시험이 모두 대상이다.

- **화면 문구**는 사람이 읽는 글이다: 웹 문구, 메일, 시드 시장 문구, 알림 문구. `words`로 찾는다(`findExcludedText`). 관리자 화면은 도박 어휘만 찾고(`ADMIN_SCREEN_FEATURES`), 메일과 회원 화면은 모든 항목으로 찾는다(오너 결정 2026-10-14).
- **화면 주소·메뉴, API, 저장 데이터**는 식별자다. 식별자를 낱말로 나눠(`identifierWords`: `realizedPnlCoin`, `realized_pnl_coin`, `/admin/audit-failures`) 한 낱말이 토큰이나 그 굴절형(`tokenForms`: `rankings`, `scoring`, `withdrawal`)과 같으면 걸린다(`findExcludedIdentifier`). 그래서 `p_yes_bp`나 `priceAvgBp`는 걸리지 않는다. 두 낱말 토큰(`check in`, `send coin`, `daily bonus`)은 함께일 때만 그 뜻이라, 두 낱말이 잇달아 있거나(`checkIn`, `/me/check-in`, `sendCoins`) 한 낱말로 붙어 있으면(`DAILY_CHECKIN`) 걸린다. 홀로 쓴 `send`·`give`·`tip`(메일·인증 코드 발송, 도움말)은 토큰이 아니고 Coin과 함께일 때만 찾는다. 경로 토큰(`pathTokens`)은 경로(화면 주소·메뉴, API 라우트 경로)와 큐·작업 이름에서만 찾는다. 지금은 활동량 보상의 `bonus` 하나다. 필드와 저장 이름에서는 시작 Coin의 `BONUS`이기도 해서 찾지 않고, 저장 이름은 `BONUS_NAMES`가 따로 본다.
- **API**는 공개 API다: 공개 라우트와 better-auth 라우트의 경로, OpenAPI 문서의 공개 작업의 경로·매개변수·스키마·필드 이름과 enum·const 값, 공개 응답의 실제 필드, 시장 채널 이벤트의 필드. 알림 유형 이름도 API 토큰으로 찾는다. 모든 오류 봉투에 붙는 `ErrorCode`의 값은 유료 구매만 찾지 않는다(보존한 결제 코드의 `PAYMENT_GATEWAY_*`). 본인 전용·관리자 라우트는 경로만, 그것도 송금·활동량 보상·현금 환전·출금(`EVERY_ROUTE_PATH_FEATURES`)만 찾는다. 송금과 출금은 본인 전용 라우트로, 활동량 보상은 관리자 라우트로 들어올 수 있어서다(오너 결정 2026-10-14). 같은 셋을 워커의 큐·작업 이름에서도 경로처럼 찾는다. 매일 주는 보상은 허용한 원장 유형(`BONUS`)에 Coin을 넣는 예약 작업으로 들어오기 쉬워서다. 본인 전용·관리자 응답의 필드와 문서의 작업은 이름으로 보지 않는다. 유료 구매는 공개 라우트와 공개 응답에서만 찾고, 보존한 결제 코드는 뺀다(D9). 결제·쿠폰 코드와 표, 관리자 충전 상품·쿠폰 관리는 남아 있어서다(ADR-0049).
- **용어와 도박 어휘**는 [docs/TERMS.md](TERMS.md)의 대응표(`REPLACED_TERMS`)에서 가져온다. 대응표를 고치면 이 검사도 따라 바뀐다. '뜻' 행은 `TERM_MEANING_PATTERNS`로 찾는다. 읽는 법은 TERMS.md의 '찾는 법'에 있다.
- **개인 확률**: 사람에게 묶일 수 있는 표의 이름과 열에 `PERSONAL_PROBABILITY_WORDS`(prob·probability·belief·credence·confidence·forecast 등)의 낱말이 없어야 한다(`namesPersonalProbability`, N02 §10, N04 §5). 사람에게 묶일 수 있는 표는 `user`, 외래 키가 있든 없든 계정 열(`userId`·`user_id`·`accountId`)이 있는 표, 그 표들을 직접이나 다른 표를 거쳐 가리키는 표다(체결은 주문의 것, 결제 이벤트는 결제의 것). 시장 단위의 가격(`price_ticks.p_yes_bp`)은 개인 확률이 아니다. 공개 API(공개 라우트 경로, 문서의 공개 작업의 경로·매개변수·스키마·필드 이름, 공개 응답의 실제 필드, 시장 채널 이벤트의 필드)에는 그 낱말이 아예 없어야 한다. 거기서 확률은 누군가의 입력이거나 Community Forecast의 집계이고(N02 §1, N00 §5), 시장가격은 확률이라 부르지 않는다([docs/TERMS.md](TERMS.md)). 본인 전용·관리자 API와 본인 방 이벤트는 이 낱말로 보지 않고(오너 결정 2026-10-14의 API 범위), 웹의 주소도 보지 않는다(ADR-0057 결과 5). 화면 문구의 '확률'은 용어 행이, 주소의 `forecast`·`belief` 등은 `probability-input`의 토큰이 찾는다.
- **목록을 바꾸는 것은 결정이다.** 항목·낱말을 빼거나 넓히는 PR은 기획 절이나 오너 결정을 `basis`에 적는다. 점수·순위를 다시 들이면 #110의 결정이, 유료 Coin 판매를 열면 #111의 결정이, 대회 어휘(상금·참가비·우승)를 넣기로 하면 챌린지(#81)의 결정이 이 목록과 아래 허용을 고친다.

## 공개 금지 항목

공개 응답과 공개 실시간 이벤트에 실리면 안 되는 것은 한곳, `packages/shared/src/guards/private-data.ts`의 `PRIVATE_DATA`(`@buddha/shared`)다. 항목마다 이름·근거·필드(식별자 낱말의 줄)가 있다. 필드 이름을 낱말로 나눠 그 줄을 담고 있으면 걸린다(`findPrivateField`: `['real', 'name']`은 `realName`·`buyerRealName`에 걸리고 `nameKo`에는 걸리지 않는다). 공개된 익명 체결이나 시장가격은 비공개가 아니다. 그것을 누구의 것으로 만드는 것은 옆에 붙은 계정이나 '누구의 것'이라는 이름이다. `myFills`처럼 `my`·`mine`을 쓴 이름, 그리고 체결·거래 낱말(`fill`·`trade`)과 사용자·계정·회원·본인 같은 낱말을 어디에든 함께 쓴 이름(`userFills`·`accountFills`·`fillsByUser`, 항목의 `owned`)이 체결 내역이다. 익명의 `fills`·`recentFills`는 공개다. 시간대도 같다. 시간대 낱말(`zone`·`timezone`·`tz`와 그 복수)과, 체결 내역의 그 사용자·계정·회원·본인 같은 낱말이나 `my`·`mine`·`viewer`를 어디에든 함께 쓴 이름(`userTimeZone`·`profileTimeZone`·`memberZone`·`myTz`)이 사용자가 고른 시간대이고(`time-zone`, 이 항목은 `owned`로만 건다), 그런 낱말이 없는 `timeZone`·`judgingTimeZone`·`resolutionTimeZone`(#22가 시장에 둘 판정 기준 시간대)은 공개다. 중첩 객체 안의 맨 `timeZone`(`Me.profile.timeZone`의 모양)은 이름으로 걸리지 않는다. 공개 라우트의 런타임 검사가 A의 시간대를 값으로 찾는다(아래 '공개 API'). 관심 시장(`watchlist`)은 '누구의 것'을 따지지 않는다. 공개 시장 모양이 관심 등록 여부(`watched`·`isWatched`)나 등록 수(`watchCount`·`watcherCount`)를 싣는 것 자체가 오너가 막은 것이라(ADR-0061 결정 3의 #89(#37)), `watch`·`watched`·`watcher`·`watchlist`와 그 복수·진행형, '관심'을 그대로 옮긴 `interested`(`interestedCount`), 다른 서비스가 같은 기능에 쓰는 `favorite`·`bookmark` 낱말의 필드를 모두 건다. 시장의 미결제 약정(open interest)인 `interest`와 그 복수, 실시간 방 메시지인 `subscribe`는 넣지 않았다(ADR-0064). 검색 기록(`search-history`)도 같은 식으로 무엇을 찾았는지(`searches`·`recentSearch`·`searchHistory`·`searchLog`·`searchQuery`·`searchTerm`)와 언제(`searched`, `searchedAt`)를 이름만으로 걸고, 검색 낱말(`search`·`query`·`keyword`와 그 복수)은 '누구의 것' 낱말과 함께일 때만 건다(`userQueries`·`myKeywords`·`viewerSearch`). 공개 요청의 `q`는 부른 사람의 것이라 답이 아니고, `query`·`search`만인 이름은 지나간다. 다른 사람들의 검색어를 세거나 줄 세운 공개 답('인기 검색어')도 이 이름들에 걸린다. 공개해도 된다는 결정이 없어서다(ADR-0066).

'인증 정보'·'내부 위험 플래그'의 범위와 본인 전용 목록 밖 항목(판정 담당자 표기 등)의 공개 여부는 #37, 체결 상대가 운영 유동성인지를 본인 체결이나 공개 최근 체결에 보일지는 #123·#122가 정한다. 답이 나오기 전에는 지금 목록 그대로다. #180은 시장별 봇 참여 여부와 설정을 관리자만 보게 했다(ADR-0058). 그래서 봇·마켓메이커·유동성 설정·최대 손실·재고·사용률·금고 같은 낱말의 필드(`market-maker`)를 미리 넣었다. #122·#123이 체결 상대가 운영 유동성인지를 보이기로 하면 그 결정과 함께 이 항목을 고친다. 오너는 사용자가 고른 시간대를 공개하지 않고 시장의 판정 기준 시간대(#22)는 막지 않기로 했다(2026-10-16, ADR-0063). 그래서 `time-zone`은 '누구의 것'이라는 이름으로만 건다. #37 가운데 관심 시장은 #89에서 답했다. 관심 시장 목록과 시장별 관심 등록 수는 본인 밖의 누구에게도 보이지 않는다(2026-10-16, ADR-0061 결정 3). 그래서 `watchlist`를 넣었다(ADR-0064). 본인의 `GET /me/watchlist`는 본인 전용 라우트라 이 목록이 보지 않는다. 이 항목이 막는 것은 공개 응답과 시장 채널 이벤트뿐이지만 오너의 글은 '누구에게도'라 운영자를 빼지 않는다. 그래서 관심 시장을 읽는 알림(#54)·지표(#151)는 운영자·관리자 화면을 포함한 어떤 화면에도 계정별 관심 시장 목록이나 시장별 관심 등록 수를 보이지 않는다. 관리자 라우트는 이 검사가 보지 않으므로 그 PR이 지킨다. 운영자가 본인 전용 정보를 볼 수 있는 범위(#37 11항)를 오너가 달리 답하면 그때 고친다. 검색 기록은 #15에서 답했다. 로그인한 회원의 검색어를 계정·시각과 함께 남기고 최근 검색은 본인에게 보인다(2026-10-16, ADR-0061 결정 3의 #15). 그래서 `search-history`를 넣었다(ADR-0066). 본인의 `GET /me/search-history`는 본인 전용 라우트라 이 목록이 보지 않는다. 이 항목은 오너의 글이 아니라 ADR-0066의 선택이다. 오너의 글은 최근 검색이 본인에게 보인다는 것이고 관심 시장처럼 '누구에게도'가 아니므로, 이 항목이 막는 것은 공개 응답과 시장 채널 이벤트에 회원의 검색어가 실리는 것뿐이다. 운영자가 검색 기록을 볼 수 있는 범위는 #37 11항이 정한다.
- 온보딩(#58)은 두 항목을 더했다(ADR-0072). 동의 기록(`consent`)은 누가 언제 무엇에 동의했는지와 동의 때의 브라우저(`userAgent`)를 공개 모양이 싣지 못하게 하고, 그 기록의 IP는 `identity-verification`의 `ip`가 막는다. 본인의 `GET /me`는 항목마다의 가장 새 답(항목·판·동의 여부·시각)을 보이지만 IP와 브라우저는 본인에게도 싣지 않는다(아래 `NEVER_SHOWN`). 이전 닉네임(`former-nickname`)은 공개 프로필과 글이 지금 닉네임만 보이게 한다는 #37 3항이다. 바꾼 때(`nicknameChangedAt`)와 30일 보류(`nicknameHold`)도 같은 항목이다. 본인의 다음 변경 가능 시각(`Me.profile.nicknameChangeAvailableAt`)은 본인 전용 라우트라 이 목록이 보지 않는다.
- 좋아요(#49)는 `likers`를 더했다(ADR-0076). 오너의 답은 '수만 보이고 누른 사람 목록은 없고, 본인은 자기가 눌렀는지 본다'(ADR-0069 결정 4)다. 그래서 공개 모양이 누가 무엇을 좋아했는지(`likedBy`·`likerIds`·`likers`)나 보는 사람이 눌렀는지(`liked`·`isLiked`·`likedByMe`)를 실으면 실패한다 — 보는 사람 자신의 것도 막는다. 공개 답이 묻는 사람마다 달라지고, 서버가 그린 글 화면과 브라우저가 읽은 글이 달라지기 때문이다. 수(`likeCount`·`likes`)는 공개다. 본인의 상태는 본인 전용 `GET /me/likes/posts/:postId`가 답하므로 이 목록이 보지 않는다. 운영자가 누가 눌렀는지를 볼 수 있는지는 #37 11항이 정한다(지금 관리자 화면에는 없다).
- 근거 글(#46)이 생기며 `author-holding`(글 작성자의 보유 방향·주문)이 더는 미리 넣은 항목이 아니다(ADR-0073). 글은 거래와 독립이라(N05 §2) 작성자의 보유·주문·잔액을 싣지 않고, 작성자가 고르는 보유 방향 표시도 두지 않는다(#37-13). 댓글·대댓글(#48, ADR-0074)과 시장 상세 토론의 카드(#47, ADR-0075 — 시장 줄을 뺀 커뮤니티 목록의 카드)도 같다. 토론의 글은 브라우저에서만 읽어 시장 상세의 서버 HTML(과 dehydrate한 상태)에 글의 내용도 작성자의 닉네임·공개 id도 없고, robots.txt가 검색 로봇에게 `/api/`를 막으며, API의 모든 응답(`/api/auth/*`와 오류 응답까지)은 `X-Robots-Tag: noindex`를 단다 — 글 화면과 커뮤니티 목록을 검색에서 빼는 #46 후속의 답(noindex)처럼, 근거 글이 검색 엔진에 열린 시장 상세를 거쳐 들어가지 않게 한다(오너 결정 2026-10-20·2026-10-21, `discussion.spec.ts`가 HTML과 헤더를, `apps/api/src/infra/http/robots-tag.test.ts`가 API의 공개·오류·인증 응답의 헤더를 본다). 글과 댓글의 공개 응답이 `authorPosition`·`authorOrders` 같은 필드를 실으면 실패하고, `positions`·`orders`는 누구의 것이든 위 항목들이 막는다.
- 작성자별 글·댓글 목록(#51)은 `moderation`을 더했다(ADR-0080). 오너의 답은 숨긴 글을 공개에는 자리표시로만 보이고 목록에서 빼며('운영 정책에 따라 숨긴 글입니다', #45-5), 숨긴 것의 '숨김' 표시와 사유는 본인에게만 보이고(MY '내 글', #45-5), 신고자와 처리한 운영자는 대상자에게도 보이지 않는다(#45-13)는 것이다. 그래서 공개 모양이 항목을 숨긴 것으로 표시하거나(`hidden`·`hiddenAt`·`isHidden`), 숨긴 사유를 싣거나(`hiddenReason`·`hideReason`·`hidingReason`), 조치나 조치한 운영자를 이름으로 실으면(`moderation`·`moderations`·`moderated`·`moderator`·`moderators`와 그것을 담은 이름) 실패한다. 공개 답은 숨긴 글을 그 상태(`state: 'hidden'`)로만 알린다 — `state`와 맨 `reason`(거절의 `details.reason`)은 지나간다. 본인의 `GET /me/posts`·`GET /me/comments`가 싣는 `hidden`(`{ reason: { code, note } | null }` — 신고 사유 하나와 운영자 설명, 오너 결정 2026-10-22. 사유는 #50이 기록하기 전에는 `null`)은 본인 전용 라우트라 이 목록이 보지 않는다. 운영자 화면(#50)도 관리자 라우트라 보지 않는다.
- 걸린 필드가 정말 공개여야 하면 시험을 느슨하게 하지 않는다. 그 근거가 되는 결정과 함께 이 목록을 고친다. 사람을 보이는 공개 응답은 필드가 아니라 값의 허용으로 다룬다: 아래 '공개 API'의 `showsPerson`(라우트마다 이유와 함께, ADR-0069 결정 5). 그 밖의 라우트별 허용은 없다.

현금 환전·출금 안내의 부정은 그 낱말의 것이어야 한다. '출금 신청은 취소할 수 없습니다'·'출금 내역이 없습니다'처럼 다른 말에 붙은 부정과 '출금 불가 기간'처럼 문장 끝이 아닌 '불가'는 출금을 지우지 않는다. 서비스 안내의 부정도 그 낱말의 것이어야 한다. 같은 절에서 낱말 뒤에 올 때만 지운다. 절은 문장 끝·쉼표·세미콜론, 낱말 끝의 연결 어미('…며'·'…고'·'…지만'·'…는데'·'…면서'·'…으나'·'…므로'·'…니까'. 인용의 '…라고'·'…다고'는 아니다)와 '그러나'·'그런데'·'반면'에서 끝난다(`CLAUSE_END`). 그래서 '점수와 순위를 제공하며 결제는 지원하지 않습니다'에서 부정은 결제의 것이라 점수·순위는 실패하고, 앞 절의 부정('결제는 지원하지 않습니다 점수는 매일 쌓입니다')도 뒤의 낱말을 지우지 않는다. '·'·'와·과'·'이나'·'하거나'로 이은 나열은 한 절이다('점수·순위를 제공하지 않습니다', '점수를 매기거나 순위를 보여주는 기능은 없습니다'). 쉼표로 나열하면 절이 나뉘어 실패한다. 서비스 안내에서는 현금 환전·출금도 다른 항목처럼 이 부정이면 지운다. 서비스 안내의 부정 문장은 용어 표의 낱말('확률'·'투표'·'예측')도 지운다('확률 입력이나 투표 기능은 없습니다', '시장가격은 확률이 아닙니다', 오너 결정 2026-10-14). 도박 어휘는 서비스 안내의 부정 문장 안에서도 허용하지 않는다.

**웹**(`apps/web/src/excluded-features.test.ts`).

- 관리자 화면: `app/admin` 아래 파일과, `app/` 밖에서 관리자 코드만 가져다 쓰는 컴포넌트·훅·lib(가져오는 곳을 따라 찾는다. 시험 파일은 세지 않고, Next가 직접 부르는 `proxy.ts`는 관리자 것이 되지 않는다), 그리고 그 파일들만 읽는 copy 키다. 문구는 도박 어휘만 검사하고(`ADMIN_SCREEN_FEATURES`), 원화 가격 표시도 찾지 않는다(오너 결정 2026-10-14). 회원 화면도 가져다 쓰는 파일은 회원 화면의 것이다. 주소와 링크는 다른 화면처럼 검사한다.
- `PRESERVED_PAID_SOURCES`: 유료 판매를 끈 동안 회원 화면에 닿지 않는 보존한 결제 코드(공개 `/charge`, 지갑의 충전·쿠폰·결제 내역 컴포넌트, 메뉴에서 뺀 관리자 충전 상품·쿠폰·결제 화면, 그 도우미). 유료 구매만 빠지고 다른 항목은 그대로 검사한다. 관리자 화면의 줄은 그 주소와 링크를 위한 것이다(문구는 관리자 화면이라 도박 어휘만 본다). `PAID_COIN_SALES_ENABLED`가 `false`일 때만 성립하므로 시험이 그 값을 고정하고, 목록의 경로가 모두 있는지도 본다.
- 판매 스위치가 여는 분기(`PAID_COIN_SALES_ENABLED ? … : …`의 참 쪽, `PAID_COIN_SALES_ENABLED && …`, `if (PAID_COIN_SALES_ENABLED) …`) 안의 문구·`copy` 읽기·`formatKrw`도 유료 구매만 빠진다(`screen-text.ts`의 `gated`).
- `COPY_ALLOWANCES`: copy 키별 허용. 지갑 이용 내역의 원장 유형 라벨 `ledgerTypeDeposit`·`ledgerTypePaymentCancel`·`ledgerTypePaymentCancelReversal`(충전·결제, 판매를 닫기 전의 행을 부르는 이름, D9). 실명·휴대전화 수집 목적 안내의 결제·구매 허용(`onboardingSubtitle`·`settingsContactHint`·`setPasswordContactHeading`)은 본인확인이 확인 없는 연락처를 대신하면서 그 문구와 함께 지웠다(ADR-0070). 허용할 낱말이 그 값에서 없어지면 시험이 실패하므로 그때 허용을 지운다.
- `SERVICE_GUIDE_ROOT`(`app/(service-guide)`): 서비스 안내(#136) 화면의 자리. 이 아래 파일과 이 아래에서만 읽는 copy 키는 서비스 안내의 허용을 받는다. 라우트 그룹은 주소에 들어가지 않으므로 주소는 #136이 정한다. 아직 아무것도 없어서 지금은 부정 안내가 어디서나 실패한다.
- `PRICE_FORMATTERS`(`formatKrw`): 원화 가격을 그리는 함수. 보존한 결제 코드와 판매 스위치 분기 밖에서 쓰면 가격표(N06)로 본다. 가져올 때 붙인 별칭(`import { formatKrw as money }` 뒤의 `money(…)`), 네임스페이스(`shared.formatKrw`), 문자열 키(`shared['formatKrw']`), 구조 분해(`{ formatKrw: won }`)로 써도 찾는다(`screen-text.ts`의 `usesOf`).
- `LEGAL_BODIES`(`test/screen-text.ts`): 약관 본문 네 파일. #137이 개정할 때까지 도박 어휘만 검사한다. 온보딩의 동의문 둘(`legal/consent-texts.ts`, ADR-0072)은 여기에 넣지 않았다 — 동의 단계가 그리는 화면 문구라 모든 항목을 검사받고, `legal/consent-texts.test.ts`도 같은 검사를 한다.

**API**(`apps/api/src/surface/registry.ts`). `preservedPaid: true`인 공개 라우트(`GET /charge-packages`, `GET /payments/provider`)만 공개에서 유료 구매를 말할 수 있다. `PaidCoinSalesGuard`가 그 라우트의 첫 가드이고 판매를 끈 동안 404로 답한다. 시험이 스위치가 `false`임과, 그 가드가 막는 라우트와 표시가 서로 맞는지를 고정한다.

**저장 데이터**(`packages/db/src/storage-names.test.ts`). 유료 구매는 찾지 않는다. 결제·충전 상품·쿠폰 표와 그 원장 유형·관리자 작업 유형은 보존한다(D9). `VARCHAR_VALUES`에 넣지 않은 열은 `approval_requests.kind`(작업마다 소비 이슈가 이름을 정하고 아직 목록이 없다, ADR-0056)와 `admin_actions.target_type`(대상 표의 이름)이다. `BONUS_NAMES`: 보너스를 담은 저장 이름(표·열·제약·enum·값) 가운데 허용한 것과 이유. 지금은 원장 유형 값 `BONUS`(보존한 쿠폰 사용, D9. #70 전에 만든 계정의 옛 가입 지급도 이 값으로 남아 있다) 하나다. 시작 Coin은 보너스가 아니라 자기 원장 유형 `START_GRANT`('시작 지급', ADR-0069 결정 4 #70, ADR-0071)라 이 목록에 들지 않는다. 줄이 더 필요 없어져도 시험이 실패한다.

**시드 시장 문구**(`packages/db/src/seed-markets.test.ts`). `WON_AMOUNTS`: 질문의 대상인 원화 금액을 시장·필드·금액으로 적은 목록. 원/달러 환율 시장(`krw-usd-yearend-2026-above-1400`)의 제목 '1,400원'과 규칙 '1,400.0원'·'1,399.9원'만 유료 구매의 원화 가격 낱말에서 지운다. 그 시장의 주제이지 Coin의 가격이 아니다. 다른 시장이나 다른 필드의 원화 금액, 그 필드에 더한 다른 금액('Coin 가격은 1,000원입니다', '11,400원')과 충전·결제·할인·'₩' 같은 다른 낱말은 그대로 찾는다. 줄이 더 필요 없어져도 시험이 실패한다.

## 등록 규칙

### 공개 API

`SessionGuard`가 없는 라우트다. 로그인하지 않은 방문자도 부를 수 있다.

1. `apps/api/src/surface/registry.ts`의 `PUBLIC_ROUTES`에 한 줄을 넣는다. 키는 컨트롤러가 쓴 그대로의 `'METHOD /path'`다(`/api`와 버전 없이, 매개변수는 `:id`). `reason`(한국어)에 왜 공개인지와 그 기획 근거, 무엇을 돌려주는지 적는다. 리뷰어가 읽는 것이 이 사유다.
2. 보존한 결제 코드라면 `preservedPaid: true`를 붙이고 `PaidCoinSalesGuard`를 첫 가드로 건다. `@ApiExcludeController`로 OpenAPI 문서에서 뺀 라우트는 `undocumented: true`를 붙이고 `docs/API.md`의 손으로 쓴 절에 적는다(그 글은 `scripts/generate-api-doc.mjs` 안에 있다).
3. `apps/api/src/surface/private-data.test.ts`에 부르는 법을 넣는다. 경로 매개변수마다 `PUBLIC_PARAMS`에 이름으로 값을 둔다(A의 기록을 가리키게). GET이 아니면 `PUBLIC_BODIES`에 본문을 둔다(A에 대해 가장 많이 말하게 하는 요청).
4. 응답 필드가 `PRIVATE_DATA`나 제외 기능 이름에 걸리면 응답을 고친다(위 '공개 금지 항목').
5. 응답이 사람을 보여야 하면(글의 작성자, 공개 프로필 — ADR-0069 결정 5) 그 줄에 `showsPerson`(한국어)을 더해 왜 보여야 하는지와 무엇만 싣는지 적는다. 실을 수 있는 것은 그 사람의 공개 id·지금 닉네임·이미지·운영자 표시뿐이고 계정 id는 어디서도 안 된다. 그 모양은 한곳에서 만든다(글과 댓글은 `posts.service.ts`의 `postAuthorOf` — 탈퇴한 작성자(#140)도 그 함수가 '탈퇴한 사용자'로 바꾼다). 지금은 `GET /posts`·`GET /posts/:postId`(ADR-0073), `GET /posts/:postId/comments`·`GET /comments/:commentId/replies`(ADR-0074), `GET /markets/:id/posts`(시장 상세의 토론, ADR-0075), 공개 프로필 `GET /profiles/:publicId`(ADR-0078 — 그 사람의 얼굴도 같은 `postAuthorOf`가 만든다)와 그 프로필의 글·댓글 목록 `GET /profiles/:publicId/posts`·`GET /profiles/:publicId/comments`(ADR-0080 — 항목마다의 작성자 표기, 같은 `postAuthorOf`) 여덟이다. 사람을 숨기는 자리표시(지운·숨긴 댓글)를 싣는 그 두 댓글 목록은 페이지 커서도 서버가 그 목록에 묶어 감춘 글자다(`comment-cursor.ts`, 오너 결정 2026-10-21 (2차)) — 자리표시가 페이지를 끝내도 그 작성 시각이 커서로 새지 않는다(`comments.controller.test.ts`가 본다). 자리표시를 싣는 공개 목록을 새로 만들면 같은 봉인을 쓴다. 다른 목록의 커서는 그대로 `<epochMillis>_<id>`다. 운영 공지의 두 공개 라우트(`GET /notices`·`GET /notices/:noticeId`, ADR-0077)는 사람을 싣지 않으므로 `showsPerson`이 없다 — 공지는 '운영팀'의 것으로 보이고(웹이 쓴다) 쓰거나 고정한 운영자는 어느 답에도 없다. 둘 다 고정한 공지만 싣고, 고정하지 않았거나 고정을 푼 공지(와 그 이미지, `GET /media/:mediaId`)는 없는 것처럼 404다(오너 결정 2026-10-21). 공지의 운영자는 관리자 라우트(운영 기록·이전 판)만 싣는다.
6. `pnpm api:openapi`를 돌려 결과를 함께 커밋한다.

빠뜨리면: `registry.test.ts`가 모듈 그래프에서 찾은 공개 라우트(컨트롤러가 상속한 처리기도 Nest의 `MetadataScanner`로 찾고, `forwardRef(() => Module)`로 가져온 모듈도 Nest처럼 풀어 본다) 가운데 등록이 없는 것과, 등록됐는데 없어졌거나 부류가 바뀐 것을 실패시킨다(오너 결정 (a)). `private-data.test.ts`의 정적 시험이 매개변수 값이나 본문이 없는 라우트를 DB 없이 실패시킨다. `registry.test.ts`는 사람 필드(`publicId`·`nickname`)를 문서에 적은 공개 라우트가 `showsPerson`으로 등록한 것과 같은지, 그 라우트들의 답에서 사람 필드를 가진 객체마다 필드가 정확히 공개 얼굴(`kind`·`publicId`·`nickname`·`imageUrl`·`isAdmin`)인지 — 작성자에 필드 하나(가입일, 본인확인 여부 같은)를 더하면 실패한다 — , 본인 전용 라우트에는 `showsPerson`이 없는지 본다. 공개 라우트에 `SessionGuard`를 걸거나 빼면 줄을 `PUBLIC_ROUTES`와 `OWNER_ROUTES` 사이에서 옮긴다.

런타임 검사는 계정 A의 이메일·닉네임·시간대·실명·휴대전화·비밀번호·세션·잔액·원장 메모·시작 Coin(지급 기록의 id·금액과 A의 번호를 `PHONE_HASH_KEY`로 해시한 값, ADR-0071 — 해시는 A 자신의 답에도 없어야 한다)·주문과 체결·보유와 손익·결제·관심 시장·검색 기록(어느 시장 제목에도 없는 검색어와 그 행의 id, ADR-0066)·본인확인 발송의 인증번호 해시와 접속 주소(ADR-0070)·동의 기록(동의 때의 접속 주소와 브라우저)·A가 내려놓은 닉네임(ADR-0072)을 심고, 모든 공개 라우트를 비로그인·B·A로 불러 답에 A의 값, 금지 항목의 필드, 제외 기능 이름의 필드가 없는지 본다. A의 금액(가용·묶인 잔액, 보유 수량, 원가, 실현 손익. 다른 숫자와 겹치기 어려운 일곱 자리)은 JSON 값으로 같을 때만이 아니라 문자열이나 키에 적힌 수로도 찾는다('잔액은 7,654,321 Coin입니다', 'balance=7654321', '−3,141,593'). 천 단위 쉼표, 'Coin' 단위, 부호, 소수점 아래 0은 지우고 견주고, 더 긴 수('17,654,321', '0.7654321')나 영숫자 id 안의 숫자('a7654321', uuid의 16진수)는 아니다. 보존한 결제 라우트는 404, 나머지는 200이어야 한다. A의 닉네임·공개 id(`profiles.public_id`, ADR-0073)와 계정 id도 찾는 값이다. 사람을 보이는 공개 라우트로 등록한 것(`showsPerson`, 아래)만 A의 닉네임과 공개 id를 실을 수 있고 — 그 라우트의 답에는 그 둘이 있어야 한다, 허용이 빈 말이 되지 않도록 — 계정 id와 A의 다른 값은 그 라우트에서도 찾는다(ADR-0069 결정 5: 계정 id 금지를 체결 응답으로 좁히지 않는다). A의 시간대도 이름 그대로(`Pacific/Chatham`) 찾으므로, 시간대를 싣는 공개 응답(#22의 판정 기준 시간대 같은)의 시험 데이터는 그 이름을 쓰지 않는다(ADR-0063). A의 관심 시장은 둘이고 두 방향을 본다. 하나는 A만 관심 등록한 마감된 시장이고 그 id와 slug를 찾는다(A가 관심 등록한 시장의 목록이 공개 답에 실리는 것). 시장은 공개이지만 이 검사의 공개 호출(쿼리 없는 `GET /markets`는 거래 중 시장만, 상세·체결·시세는 A가 거래한 시장, 그 시장의 관련 시장(`GET /markets/:id/related`)은 운영자가 그 시장과 연결한 다른 열린 시장 하나, ADR-0068)이 그 시장을 싣지 않으므로, 답에 그 값이 있으면 A의 관심 등록에서 온 것이다. 관련 시장 답은 빈 페이지가 아니라 항목 하나를 실어, 그 항목의 필드 이름도 금지 항목·제외 기능 검사를 받고 값도 A의 값과 견줘진다. 시험은 그 답이 연결한 그 시장 하나임을 확인해, 빈 페이지가 검사를 그냥 지나지 못하게 한다. 공개 라우트에 상태 필터를 붙여 부르게 되면 이 시장을 바꾼다. 다른 하나는 A가 거래한 그 시장이다. A가 그 시장도 관심 등록해 두므로, 상세·체결·시세와 시장 방의 `market:status`(아래)가 그 시장을 관심 등록한 계정을 싣게 되면 A의 계정 id나 닉네임이 걸린다(시장을 관심 등록한 계정이 공개 답에 실리는 것). 금지 항목의 낱말에 없는 이름(`followers`·`recipients` 같은)으로 실려도 값으로 걸린다(ADR-0064). A의 근거 글(#46, ADR-0073)은 A가 거래한 그 시장에 이미지를 넣어 쓴 글 하나다. 글 목록·글 화면(`GET /posts`·`GET /posts/:postId`)과 그 시장의 토론(`GET /markets/:id/posts`, #47)은 그 글의 작성자로 A의 닉네임과 공개 id를 싣고(위의 허용), 시험은 토론의 답이 그 글 하나이고 그 수(`meta.total`)가 1임을 본다 — A가 지운 다른 글은 카드에도 수에도 없다(ADR-0075), 이미지 라우트(`GET /media/:mediaId`)는 A가 올린 그 이미지를 내준다. 그 글 아래에는 A의 댓글과 A의 대댓글, A가 지웠지만 대댓글이 달려 자리표시로 남는 댓글과 그 대댓글이 있다(#48, ADR-0074). 댓글 목록(`GET /posts/:postId/comments`)과 A의 댓글의 대댓글 페이지(`GET /comments/:commentId/replies`, '답글 더 보기')는 그 작성자로 A의 닉네임과 공개 id를 싣고(위의 허용), 시험은 앞의 답이 A의 댓글과 대댓글, 지운 댓글의 자리표시임을, 뒤의 답이 A의 대댓글임을 본다. 운영자만 보는 것 — 그 글의 이전 판(`post_revisions`)과 A가 지운 다른 글, A의 댓글의 이전 판(`post_comment_revisions`)과 A가 지운 댓글 — 의 글자는 A 자신의 답에도 없어야 하는 값(`NEVER_SHOWN`)으로 찾는다. B가 A의 계정을 댄 댓글 쓰기·수정·삭제와, B가 자기 계정으로 A의 댓글을 고치고 지우려는 것은 403이고 댓글과 그 이력의 행을 바꾸지 않는다. A는 자기 글과 댓글을 좋아한다(#49, ADR-0076 — 자기 글도 받는다). 그 행은 A의 계정과 A의 번호를 `PHONE_HASH_KEY`로 해시한 값을 가지므로 글·댓글의 수에 든다. 누가 눌렀는지는 어떤 공개 답에도 없어야 하고 해시는 A 자신의 답에도 없어야 한다. B가 A의 계정을 댄 두 좋아요 취소는 403이고 좋아요의 행을 바꾸지 않는다. 본인 전용 `GET /me/likes/posts/:postId`는 B에게 아무것도 없다고(`{ postLiked: false, likedCommentIds: [] }`), A에게 A의 것을 답한다. 운영 공지(#138, ADR-0077)는 A가 쓰고 고치고 고정한(`admin_actions`의 `notice_create`·`notice_update`·`notice_pin`) 고정 공지 하나이고 그 이미지도 A가 올렸다 — A는 관리자가 아니지만, 공지의 답이 그 운영자를 읽어 싣게 되면 A의 닉네임·공개 id·계정 id가 걸린다. 고정 영역(`GET /notices`)과 공지 화면(`GET /notices/:noticeId`)은 그 공지를 싣고(시험이 본다) 사람은 싣지 않으며, 그 공지의 이전 판(`notice_revisions`)의 글자와 A가 쓰고 고정하지 않은 다른 공지의 글자(고정한 공지만 공개한다, 오너 결정 2026-10-21)는 `NEVER_SHOWN`으로 찾는다. 이미지 라우트의 이유는 공지의 이미지도 말한다. 공개 프로필(#41, ADR-0078)도 같은 `showsPerson`으로 등록했다. A에게 소개와 관심 카테고리를 심고 프로필 라우트를 A의 공개 id로 비로그인·B·A가 부른다. 그 답은 A의 닉네임과 공개 id를 싣고(위의 허용), A의 소개·카테고리와 수(지우지 않은 글 1·댓글 3 — A가 지워 자리표시로 남은 댓글은 빼고 그 아래 대댓글은 넣는다 — ·받은 좋아요 0 — 그것들의 좋아요 둘은 A가 스스로 누른 것이라 빠진다, ADR-0078)를 싣는지 시험이 보며, A의 다른 값은 그 답에도 없어야 한다. 소개는 공개 항목이라 표지값이 아니다. B가 A의 계정을 댄 `PUT /me/bio`는 403이고 A의 소개를 바꾸지 않는다(온보딩 상태의 견줌에 소개가 든다). B가 A의 계정을 댄 `POST /me/onboarding/interests`(온보딩 화면이 떠날 때 보내는 건너뛰기)도 403이고 누구의 관심 카테고리 단계도 답하지 않는다. A에게는 프로필 이미지도 심는다(#141, ADR-0079 — 행과 시험 저장소의 객체). 그 id는 A의 얼굴이 싣는 주소(`imageUrl`)에 들어가므로 A의 닉네임·공개 id처럼 찾는 값이고(`profile image`), 사람을 보이는 라우트(`showsPerson` — #48의 대댓글 페이지와 #47의 시장 토론, #41의 공개 프로필, #51의 프로필 글·댓글 목록까지 여덟)와 A 자신의 `GET /me`·MY '내 글'(`GET /me/posts`·`/me/comments`, #51)에만 있을 수 있다 — 그 표지값의 라벨 `profile image`가 `PERSON_LABELS`(사람 라우트가 실을 수 있는 라벨, `nickname`·`public id` 옆)에 든다 — 그 라우트들의 답에는 있어야 하고, 공개 프로필의 `member.imageUrl`이 그 주소인지, 이미지 라우트가 그 바이트를 누구에게나 내주는지 시험이 본다. B가 A의 계정을 댄 `PUT /me/profile-image`(계정은 쿼리 — 파일이 본문이다)와 `POST /me/profile-image/delete`는 403이고 A의 이미지를 바꾸지 않는다(프로필의 견줌에 `image_id`가 든다). 작성자별 글·댓글 목록(#51, ADR-0080)을 위해 A에게 운영자가 숨긴 글 하나와 그 아래 숨긴 A의 댓글 하나를 더 심는다(A의 가장 새 글과 댓글). 그 글자는 표지값('hidden post'·'hidden comment')이라 어떤 공개 답에도 없어야 한다. 프로필의 두 목록(`GET /profiles/:publicId/posts`·`/comments`)은 같은 `showsPerson`으로 A의 닉네임·공개 id·프로필 이미지를 싣고, 시험은 그 답이 프로필의 수가 세는 것 — A의 글 하나와 댓글 셋(지운 것과 숨긴 것은 빼고, 지운 댓글 아래의 대댓글은 넣는다) — 임을 본다. 빈 페이지가 검사를 그냥 지나지 못하게 하려는 것이다.

### 본인 전용 API

`SessionGuard`가 있고 `AdminGuard`가 없는 라우트다. 세션 계정 자신의 것만 답한다.

1. `registry.ts`의 `OWNER_ROUTES`에 한 줄을 넣는다. 키는 공개 API와 같고, `reason`에 누구의 무엇을 돌려주거나 바꾸는지와 기획 근거를 적는다. 보존한 결제 코드는 `preservedPaid: true`.
2. `private-data.test.ts`의 `OWNER_CASES`에 교차 계정 경우를 넣는다. B가 A를 겨냥해 부르는 요청이다.
   - `params`: 경로 매개변수마다 A의 기록을 가리키는 값.
   - `query`: 라우트가 읽는 쿼리 키마다 값(`@Query('키')`의 키와 `@Query({ schema })` 객체 스키마의 키, `queryKeysOf`). 키가 A의 기록이나 A를 가리킬 수 있으면 A의 것을 준다(A의 행으로 만든 페이지 커서, A의 id). 지금 원장·주문·결제 목록과 MY '내 글'의 두 목록(`GET /me/posts`·`/me/comments`, A의 숨긴 글·댓글로 만든 커서 — A가 같은 요청을 하면 그 숨긴 것이 보여야 한다, `own`)은 A의 가장 새 행 바로 뒤에서 시작하는 커서로, 보유는 `status=open`으로, 관심 시장 목록은 A의 관심 등록 행으로 만든 커서와 그 커서의 정렬(`sort=watched`, 최근 관심 등록 순, ADR-0065), 그 시장의 상태·카테고리로 부른다. 객체 스키마 없이 쿼리 전체를 받는 `@Query()`는 키를 셀 수 없어 실패하므로 스키마를 단다.
   - `body`: GET이 아니면 본문. 본문이 계정을 받으면(`expectedAccountId` 등) A의 계정. 최근 검색의 쓰기 셋(기록·하나 지우기·전체 지우기)은 A의 계정을 대 403이고, 하나 지우기의 경로는 A의 검색 행이다. 같은 시험 끝에서 B가 자기 계정으로 A의 행을 지우게 해도 200에 빈 목록이고 A의 행이 그대로인지 본다(지울 검색어를 B 자신의 행에서만 찾는다, ADR-0066).
   - `status`: B가 받아야 하는 답(자기 것만 보이는 목록은 200, A의 기록 하나는 404, A의 계정을 댄 쓰기는 403 등).
   - `own`: 같은 요청을 A가 하면 보이는 A의 값(표지값의 라벨). 검사가 눈먼 것이 아님을 확인한다. A를 바꾸는 쓰기에는 두지 않는다. 답이 표지값을 담을 수 없는 모양이면(`GET /me/watchlist/:marketId`의 `{ watched }`) 두지 않고, 같은 시험 끝에서 B와 A의 답을 따로 본다.
3. 새 라우트가 다루는 A의 비공개 기록이 표지값에 없으면 시험의 `seed()`에 그 기록을 심고 표지값을 더한다.
4. 온보딩을 마친 계정만 할 수 있는 쓰기(글·댓글·좋아요·신고·시장 제안·주문, ADR-0069 결정 1 #57-8 — MY 설정의 닉네임 변경 `PATCH /me`도, 재동의가 남은 계정 포함, ADR-0078 오너 결정 2026-10-22 답 1)면 `OnboardedGuard`를 `SessionGuard` 뒤에 걸고(`@UseGuards(SessionGuard, OnboardedGuard)`, 또는 컨트롤러의 `SessionGuard` 아래 핸들러에), `OWNER_ROUTES`의 줄에 `onboarded: true`를 적는다. 판단이 쓰기까지 유지되어야 하면 트랜잭션 안에서 `assertOnboarded`도 부른다. 관심 등록은 걸지 않는다(ADR-0061 #89 행). 자기 글 삭제(`POST /posts/:postId/delete`)도 걸지 않는다 — 로그인만 본다(오너 결정 2026-10-19, ADR-0073). 로그인만으로 하는 동작은 화면에서도 닿아야 한다(오너 결정 2026-10-20): 그 동작의 페이지를 웹 게이트의 예외 페이지(`apps/web/src/lib/onboarding.ts`의 `ONBOARDING_EXEMPT_PAGES`, 그 페이지 하나만, 까닭과 함께)에 넣고, 그 페이지의 쓰기·수정 진입은 `useOnboardingEntry`로 남은 단계로 보낸다(글 화면은 글의 '수정'과 댓글의 '답글'·'수정'·'올리기'·'저장', ADR-0074). 그 예외는 온보딩을 한 번 마친 뒤 재동의만 남은 계정의 것이고(`hasOnlyReconsentLeft`), 마치지 않은 계정은 그 페이지에서도 그 페이지를 `next`로 남은 단계에 보낸다(오너 결정 2026-10-20 3차 답 1). 지금 근거 글 화면과 MY 설정(`/my/settings` — 재동의 계정의 소개 비우기·관심 카테고리 빼기·프로필 이미지 지우기와 계정 관리 카드, 새 값(새 프로필 이미지도)·닉네임 바꾸기와 마케팅 정보 수신은 남은 단계로, ADR-0078 7-24·ADR-0079 결정 9 — 재동의 단계 화면이 이 페이지로 가는 링크를 둔다, 오너 결정 2026-10-22 답 2)이다(`lib/onboarding.test.ts`가 목록을 본다). 새 값만 온보딩을 묻고 비우기는 로그인만 보는 쓰기(공개 프로필의 소개·관심 카테고리, ADR-0078 — 재동의가 남은 계정도 자기 공개 항목을 내린다)와, 아직 답하지 않은 단계의 답이면(닉네임 단계 뒤 24시간 안의 첫 답이든 그 뒤의 것이든, ADR-0078 오너 결정 2026-10-21 3차 답 1) 고르기도 빈 목록의 건너뛰기도 온보딩을 묻고 답한 뒤에는 그 규칙과 같은 관심 카테고리 단계의 답 `POST /me/onboarding/interests`(ADR-0078 7-8 경계 (2) — 빈 목록이 비우기가 아니라 단계의 답이라, 새 계정이 그것으로 단계를 건너뛰지 못한다)는 가드를 걸지 않고 서비스가 트랜잭션 안에서 묻는다(`assertPublicItemOnboarding`, 24시간이 지난 단계의 건너뛰기는 공개 항목의 새 값이 아니라 `assertOnboarded`). 그 줄에는 `onboarded`를 적지 않고 이유에 그 규칙을 쓰며, `registry.test.ts`의 `ONBOARDING_REQUIRED` 문서 시험의 목록에 더한다. 지우기만 하는 쓰기(프로필 이미지 삭제, ADR-0079 — 재동의가 남은 계정도, 제재 중에도)는 온보딩을 묻지 않으므로 가드도 `onboarded`도 없고, 그 문서 시험의 목록에도 넣지 않는다. 그 짝인 새 값의 쓰기(프로필 이미지 올리기)는 언제나 새 값이라 지금 값과 견줄 것이 없고, 가장 비싼 단계인 변환 전에 막으려고 `OnboardedGuard`와 `onboarded: true`다. 가드는 Fastify가 본문을 다 읽은 뒤에 돈다(ADR-0073 9-31) — 그래서 본문 전의 문(`image-body.ts`의 `IMAGE_UPLOAD_ROUTES`)이 글 이미지처럼 출처·better-auth 세션·온보딩을 먼저 묻는다(ADR-0079 결정 9). 가드만으로 본문을 읽지 않고 막을 수는 없다. `OWNER_CASES`의 B는 온보딩을 마친 계정이라 가드를 지나 계정 확인에서 거절된다(ADR-0072).

빠뜨리면: `registry.test.ts`가 등록이 없는 본인 전용 라우트와 `onboarded` 표시와 `OnboardedGuard`가 서로 다른 라우트, `OnboardedGuard`를 걸고 문서(`@ApiErrors`)에 `ONBOARDING_REQUIRED`를 적지 않은 라우트를, `private-data.test.ts`의 정적 시험이 `OWNER_CASES`가 `OWNER_ROUTES`와 다르거나 경로 매개변수·쿼리 키·본문이 빠진 경우를 DB 없이 실패시킨다. 런타임 검사는 B가 그 경로·쿼리·본문으로 부른 답에 A의 값이 없고 상태가 `status`인지, A가 같은 요청을 하면 답에 `own`이 있는지 본다. A 자신의 답에도 없어야 하는 값(`NEVER_SHOWN`: A의 번호를 `PHONE_HASH_KEY`로 해시한 값, 본인확인 발송의 인증번호 해시와 접속 주소, 동의 기록의 접속 주소와 브라우저, A가 내려놓은 닉네임 — ADR-0072)은 A의 답에서도 찾는다 — 응답 봉투는 아무것도 걸러 내지 않아 서비스가 돌려준 것이 그대로 나가므로, `Me.startGrant`에 해시가 붙거나 지급 행이 통째로 실리면 여기서 걸린다(ADR-0071). better-auth 라우트의 A 자신의 답도 같다.

이름: 본인 전용 라우트의 경로에 송금·활동량 보상·현금 환전·출금의 토큰이 있으면 `registry.test.ts`가 실패한다(`/me/coins/send`, `/me/withdrawals`). 그 밖의 이름(본인의 점수나 확률을 담은 필드 등)은 보지 않는다(오너 결정 2026-10-14).

### 관리자 API

이 등록 목록에 넣지 않는다. 모든 관리자 라우트는 `/admin` 아래에 두고 `SessionGuard`, `AdminGuard`, `OnboardedGuard`를 이 순서로 건다 — 관리자가 아닌 계정은 온보딩과 상관없이 403, 온보딩을 마치지 않은 관리자는 409 `ONBOARDING_REQUIRED`(오너 결정 2026-10-19, ADR-0072)이고, 라우트의 `@ApiErrors`에 `ONBOARDING_REQUIRED`를 적는다. `admin-access.test.ts`가 그 가드와 순서를, `admin-audit.test.ts`가 상태를 바꾸는 라우트마다의 작업 유형을 확인한다(ADR-0036·ADR-0056 — 운영 공지의 쓰기·수정·고정·해제는 `notice_create`·`notice_update`·`notice_pin`·`notice_unpin`, ADR-0077). 운영 기록을 읽는 라우트(`OPERATION_RECORDS` — 감사 실패, 출시 설정과 관리자 권한의 변경 기록, 공지의 운영 기록과 이전 판)는 관리자만 읽는지 따로 부른다(ADR-0077의 오너 결정 2026-10-21). 관리자 라우트는 경로만 송금·활동량 보상·현금 환전·출금의 이름 검사를 받는다(`/admin/rewards`는 실패한다, 오너 결정 2026-10-14). 필드와 문서의 작업은 이름으로 보지 않는다.

### better-auth 라우트

better-auth가 Nest 라우팅 앞에서 `/api/auth` 아래에 내는 라우트다. 모듈 그래프에 보이지 않고 누구나 부를 수 있다(세션은 라우트가 스스로 본다).

1. `registry.ts`의 `AUTH_ROUTES`에 한 줄을 넣는다. 키는 `'METHOD /path'`(`/api/auth` 뒤의 경로)이고 `reason`에 무엇을 누구에게 하는지 적는다.
2. 계정 데이터(사용자·세션·연결된 계정·제공자 토큰)를 답하는 라우트는 `answersAccount: true`를 붙이고 `private-data.test.ts`의 `AUTH_CASES`에 경우를 넣는다.
   - `request`: 비로그인과 B가 보내는 것. 계정이나 계정 id를 받으면 A의 것.
   - `status`: 둘이 받아야 하는 답(`anonymous`, `B`).
   - `own`: A가 보내면 보이는 A의 값(표지값의 라벨). A를 바꾸거나 A의 것이 보일 수 없으면 두지 않는다.

빠뜨리면: `registry.test.ts`가 인증 인스턴스(`createAuth`로 앱과 같게 만들고 OAuth 제공자를 모두 켠 것)의 `auth.api`에서 경로가 있는 엔드포인트를 메서드마다 찾아(플러그인의 것 포함, 서버 전용과 `disabledPaths` 빼고) 등록이 빠진 것과 더는 내지 않는 줄을 실패시킨다(오너 결정 (a)). 플러그인(휴대전화 번호 로그인 등)을 켜거나 better-auth를 올려 엔드포인트가 늘면 여기서 걸린다. #183의 SMS 인증번호는 better-auth 플러그인이 아니라 API의 본인 전용 라우트다(ADR-0070). `private-data.test.ts`의 정적 시험은 `answersAccount` 줄과 `AUTH_CASES`가 다르면 DB 없이 실패한다. 런타임 검사는 앱의 실제 인증 인스턴스가 내는 라우트가 `AUTH_ROUTES`와 같은지와, 각 경우의 답에 A의 값이 없는지 본다. `/sign-up/email`은 꺼 두었다(ADR-0024, 서버의 `RegistrationService`만 부른다). `/update-user`도 꺼 두었다(ADR-0072: 그 경로가 쓰는 better-auth의 이름·사진은 두지 않는다 — 소셜 로그인의 이름·사진을 저장하지 않는다는 오너 결정, `user` 데이터베이스 훅이 다른 경로의 쓰기도 막는다). `/account-info`도 꺼 두었다(ADR-0072 7-31: 그 답은 연결한 제공자의 이름·사진이다 — 그 둘을 담는 제공자의 ID 토큰은 `account` 데이터베이스 훅이 두지 않는다). `/get-access-token`·`/refresh-token`도 꺼 두었다(ADR-0072 7-31: 연결한 제공자의 접근·갱신 토큰을 내주는 경로다 — 그 토큰도 `account` 데이터베이스 훅이 두지 않는다는 오너 결정).

### 실시간 이벤트

공개 방은 `market:<id>`(누구나 구독), 본인 방은 `user:<id>`(핸드셰이크 세션이 들어간다)다.

1. `packages/shared/src/realtime.ts`의 `REALTIME_EVENT_TYPES`에 유형을 넣고 스키마를 그 계열(`marketRealtimeEventSchema` 또는 `userRealtimeEventSchema`)에 더한다.
2. `packages/shared/src/guards/realtime-events.ts`의 `REALTIME_EVENT_REGISTRY`에 `channel`(`'market'` 또는 `'user'`)과 `reason`(한국어: 무엇을 알리는지와 기획 근거)을 넣는다. 유형을 키로 하므로 빠뜨리면 컴파일이 실패한다.
3. 본인 방 이벤트면 `realtime-events.test.ts`의 `USER_EVENTS`와 `private-data.test.ts` 시장 방 시험의 `own`에 그 이벤트의 예를 하나씩 더한다. 둘 다 유형마다 하나를 요구해서 빠뜨리면 컴파일이 실패한다.
4. `scripts/generate-api-doc.mjs`의 `REALTIME_EVENTS`에 방·설명·순서 키를 넣는다. 없으면 `pnpm api:openapi`가 실패한다.

게이트웨이와 소켓에 이벤트를 보내는 곳도 등록한다(오너 결정 (a)). 소켓은 로그인 없이도 열리므로 공개 표면이다.

- 새 `@WebSocketGateway`, 새 네임스페이스, 클라이언트가 보내는 새 메시지(`@SubscribeMessage`)는 `apps/api/src/surface/registry.ts`의 `REALTIME_GATEWAYS`에 네임스페이스를 키로 메시지 목록과 `reason`(한국어: 누가 무엇을 할 수 있고 무엇을 받는지)을 적는다. 지금은 `/ws`의 `subscribe`·`unsubscribe`다.
- 소켓에 보내는 코드를 더하면 `REALTIME_EMITS`에 파일(`src/` 아래 경로)·이벤트(호출에 쓴 그대로)·보내는 것의 스키마(`payload`: zod 스키마, 본문 없는 신호는 `null`)·`reason`을 적는다. 보내는 코드는 `emit`(`emitWithAck`·`serverSideEmit` 포함), 소켓 패키지를 가져오는 파일의 `send`·`write`(이벤트 `message`), 반환 형식이 `void`·`Promise<void>`가 아닌 `@SubscribeMessage` 처리기, 그리고 클라이언트의 응답 콜백(ack)을 부르는 곳이다. Nest가 처리기가 돌려준 값을 클라이언트에 보내므로(응답이나 `{ event, data }`) 그 처리기는 이벤트 `reply to '<메시지>'`로 적는다. 처리기의 `@Ack()` 매개변수는 읽는 곳마다(부르거나 다른 함수에 넘기거나) `ack to '<메시지>'`로, 소켓 패키지를 가져오는 파일에서 `on`·`once` 등으로 단 리스너가 마지막 인자(Socket.IO가 넘기는 응답 콜백)를 부르는 곳은 `ack to '<이벤트>'`로 적는다. 리스너는 그 자리에 쓴 함수, `this.멤버`, 파일이 그 이름으로 선언한 함수까지 따라간다. 데코레이터는 가져온 이름으로 읽는다(`import { SubscribeMessage as OnMessage }`, `import * as ws`). 그래도 읽지 못한 처리기(지역 상수나 합성 데코레이터로 붙인 것)는 Nest가 등록한 처리기·`@Ack()` 매개변수와 소스에서 읽은 것이 달라 실패한다. 지금 방에 가는 이벤트는 게이트웨이가 채널 계열 스키마로 파싱한 `event.type` 하나뿐이고, 그 밖의 `emit`은 그 소켓에만 가는 거절 봉투와 본문 없는 재동기화 신호다.
- 보내는 값은 줄의 `payload`로 검사한다. 시험은 API 소스를 TypeScript 형식 검사기로 읽어 보내는 값(이벤트 뒤의 인자, `send`·`write`의 인자, 응답 콜백을 부른 인자, 처리기가 돌려주는 값은 반환 형식)의 형식에서 속성 이름을 모든 깊이로 꺼낸다(배열의 원소와 합집합의 각 형식까지. 메서드와 `Date` 같은 TypeScript 기본 라이브러리 형식은 값으로 보고 이름을 꺼내지 않는다). 그 이름이 스키마(`z.toJSONSchema`의 속성 이름)에 없으면 실패하고, 그 이름이나 보내는 식에 적은 객체 리터럴의 키(스키마가 열어 둔 `details` 안의 `{ retryAfterSeconds }` 등), 스키마의 이름이 금지 항목·제외 기능·확률 낱말이면 실패한다. `null`로 적은 줄이 값을 보내도, 응답 콜백을 다른 함수에 넘겨 보내는 자리에서 값을 읽을 수 없어도 실패한다. 방에 가는 이벤트(`roomEvent: true`, 스키마 `realtimeEventSchema`)는 이름이 스키마에 있는지만 보고, 이름의 금지 검사는 채널별로 `realtime-events.test.ts`가 한다(본인 방 이벤트는 본인 것이다). 지금은 오류 봉투 두 곳이 `errorEnvelopeSchema`, 재동기화 신호가 `null`이다.

빠뜨리면 `registry.test.ts`가 모듈 그래프의 프로바이더에서 찾은 게이트웨이(네임스페이스와 메시지. `forwardRef`로 가져온 모듈의 것도)와, 소스에서 찾은 보내는 곳이 목록과 다르다고 실패한다. 리스너를 이름이 아닌 값으로 넘기거나(`client.on(event, handlers[event])`) 미들웨어(`use`)·`onAny`에서 응답 콜백을 부르는 것, 리스너가 응답 콜백을 다른 함수에 넘기는 것은 보지 않는다. 보내는 값의 형식이 `unknown`·`any`이면 그 안의 이름은 형식으로 읽을 수 없어, 식에 적은 객체 리터럴의 키만 본다.

검사: 등록한 채널이 게이트웨이가 그 이벤트를 파싱하는 계열과 같고, 시장 채널 스키마의 필드에 금지 항목과 제외 기능 이름, 확률·믿음 낱말이 없으며(공개 API, 오너 결정 2026-10-14), 본인 방 이벤트는 시장 채널 이벤트로 읽히지 않는다. 런타임 검사는 시장 방을 구독할 때 받는 거절 봉투(구독 적용을 기다리는 데 쓴다)에 A의 값과 금지 필드가 없는지 보고, 비로그인·B로 시장 방을 듣는 동안 A의 이벤트를 A의 방에 발행하고 시장 채널에도 몰래 실은 뒤, 관리자 마감으로 실제 `market:status`를 발행해 시장 방에 그것만 오는지 본다. `market:tick`·`market:trade`는 아직 발행하는 경로가 없다(#119). 공개 이벤트를 실제로 발행하는 경로를 더하는 이슈는 이 시험에서 그 경로로 이벤트를 발행해, 받은 이벤트에도 A의 값과 금지 필드가 없음을 확인하게 한다.

### 웹이 페이지 밖에서 답하는 것

`apps/web`의 Next 프록시(`app/` 옆, 곧 `src/`의 `proxy.ts`나 옛 이름 `middleware.ts`. 맞는 라우트보다 먼저 돌고 스스로 답을 돌려줄 수 있다), 라우트 핸들러(`app/` 아래의 `route.ts`·`route.js`), 메타데이터 라우트(`app/` 아래의 `favicon`·`sitemap`·`robots`·`manifest`·`opengraph-image`·`twitter-image`·`icon`·`apple-icon`, 확장자와 번호(`icon1.png`)를 가리지 않고 만든 것이든 정적 파일이든), Pages Router의 API 라우트(`pages/api/`), 서버 액션(`'use server'` 파일이나 함수)은 API의 등록 목록 밖에서 요청에 답한다. 시험은 화면 문구를 읽는 스크립트만이 아니라 `app/`·`pages/` 아래 모든 파일과 `src/`의 모든 스크립트를 본다. 서버 액션은 스크립트를 TypeScript 파서로 읽어, 모듈이나 함수 본문을 여는 지시문(다른 지시문 뒤도 포함)의 `'use server'`로 찾는다. 같은 줄에 코드가 이어지거나(`async function save() { 'use server'; … }`) 뒤에 주석이 붙어도 찾는다. 지금은 둘이다 — 프록시(`/admin`·`/my` 요청의 경로와 쿼리를 헤더에 덮어써 넘기기만 한다. 읽기와 쓰기는 API로 간다)와 `app/robots.ts`(`/robots.txt` — 모든 검색 로봇에게 `/api/`만 막는 고정된 두 줄(`User-Agent: *`·`Disallow: /api/`), 요청도 세션도 읽지 않는다. 시장 상세의 토론이 브라우저에서 읽는 근거 글을 로봇이 가져가지 못하게 한다, ADR-0075). 더하면 `apps/web/src/excluded-features.test.ts`의 `WEB_SERVER_ENDPOINTS`에 무엇을 답하는지와 이유를 적는다. 키는 `src/` 아래 파일이고(`proxy.ts`), 라우트 핸들러는 파일과 내보낸 HTTP 메서드마다 따로다(`app/feed/route.ts GET`, `app/feed/route.ts POST`). 메서드마다 따로 답하므로 등록한 파일에 메서드를 더해도 실패한다. 메서드는 `export function GET`, `export const PUT = …`(구조 분해 포함), `export { handler as POST }`, 이름으로 다시 내보내기, CommonJS(`exports.GET =`, `module.exports = { GET }`)로 읽고, `export * from`은 무엇이 오는지 알 수 없어 `*`로 등록한다. 빠뜨리면 그 시험이 실패한다. 이 검사는 등록과 사유만 요구하고, 답의 내용은 `private-data.test.ts`가 부르지 않는다.

### 알림 유형

알림 기능(#53) 전이라 자리만 있다.

1. `packages/shared/src/guards/notifications.ts`의 `NOTIFICATION_TYPES`에 유형마다 `type`(API와 저장 행이 쓰는 이름), `text`(사람이 읽는 모든 문구: 제목과 본문, 자리표시자는 쓴 그대로), `reason`(무엇을 알리는지와 기획 절)을 넣는다.
2. #53은 알림 유형 목록을 만들 때 이 목록을 그 원천으로 쓰거나 두 목록이 같음을 시험으로 고정해, 등록되지 않은 유형이 생기지 않게 한다. 어느 쪽으로 할지는 #53이 정한다. 뒤에 유형을 더하는 이슈도 같은 목록에 넣는다.

검사: 유형 이름은 API 값이라 공개 API의 토큰(유료 구매 포함, N05 §4)으로, 문구는 화면 문구로 찾는다(`findExcludedNotification`). 점수·순위·Forecast 수정·유료 Coin 구매 유도 알림(N05 §4)과 활동량 보상 알림이 걸린다. 알림 문구는 서비스 안내가 아니므로 현금 환전·출금 미제공 밖의 부정 안내도 걸린다.

### 저장 데이터의 값 목록

Postgres enum의 값은 저절로 검사된다. varchar 열이 고정 목록에서 값을 받으면(`market_events.type` 방식) 그 목록을 `packages/db/src/storage-names.test.ts`의 `VARCHAR_VALUES`에 `'표.열'`로 넣는다. 시험은 그 열이 실제로 있는지도 본다. 활동량 보상이나 송금은 새 원장 유형이나 작업 유형으로 들어올 가능성이 크다. 이름에 보상·출석·체크인·연속 기록·매일·로그인 보너스·송금·환전의 토큰이 있으면 토큰으로 걸리고, 보너스를 담은 값(`LIKE_BONUS`, `TRADE_VOLUME_BONUS`)과 표·열(`daily_bonuses`, `bonusClaimedAt`)은 `BONUS_NAMES`에 이유와 함께 있어야 통과한다. 그 밖의 이름이면 걸리지 않는다(아래 '검사하지 않는 것').

### 메일

메일은 모두 `apps/api/src/mail/templates.ts`에서 만들고 `MAIL_TEMPLATES`에 등록한 템플릿으로 보낸다. 메일 문구는 모든 화면 항목으로 찾고(오너 결정 2026-10-14), 서비스 안내가 아니므로 현금 환전·출금 미제공 밖의 부정 안내도 걸린다. 메일이 말하는 낱말이 모두 `templates.ts`의 문자열이어야 검사가 모든 분기를 본다. 아래 규칙은 그것을 지키는 방법이다.

1. 템플릿을 `templates.ts`에 함수로 쓰고 `MAIL_TEMPLATES`에 이름으로 넣는다. 그 파일이 내보내는 함수는 모두 등록해야 하고, 등록하는 함수는 그 파일에 선언한 것이어야 한다. `templates.ts`는 형식만 가져온다(`import type`).
2. 템플릿은 입력을 하나(객체)까지 받고, 그 키는 `templates.test.ts`의 `MAIL_INPUTS`에 있는 것뿐이다. 지금은 링크(`url`), 바꿀 이메일 주소(`newEmail`), 링크나 인증번호의 유효 시간(`expiresInMinutes`, 숫자), 개발용 SMS 발송기가 메일로 대신 보내는 본인확인 인증번호(`code`, 서버가 뽑은 숫자 여섯 자리, ADR-0070)다. 제목·본문처럼 부르는 쪽이 고르는 낱말은 입력으로 받지 않는다. 새 입력(닉네임 등)이 필요하면 `MAIL_INPUTS`에 형식(문자열·숫자)과, 그 값이 왜 메일의 낱말이 아닌지를 적어 더한다. 어느 템플릿도 받지 않는 줄은 실패한다.
3. `templates.test.ts`의 `EXAMPLES`에 그 템플릿의 예시 입력을 넣는다. 선택 입력은 한 번 이상 준다. 템플릿마다 하나 이상을 요구해서 빠뜨리면 컴파일이 실패한다.
4. 보내는 코드는 템플릿이 만든 것을 `Mailer.send`(`mail/mailer.ts`)에 그대로 넘기고 받는 주소(`to`)만 붙인다(`send(user.email, MAIL_TEMPLATES.verification({ url }))`). better-auth의 메일 훅(`sendVerificationEmail`·`sendResetPassword`·`sendChangeEmailConfirmation`)과 플러그인이 더하는 메일 훅, 개발용 SMS 발송기(`sms/dev-sms-sender.ts`, 인증번호를 Mailpit으로 보내는 `devVerificationCode`)도 같다. 제목·본문을 다른 파일에서 쓰거나 고치지 않고, `MailMessage`에 없는 키(`attachments`·`amp`·`headers` 등)를 싣지 않는다. 템플릿이 만든 값은 보내는 데만 쓴다. 배열·Map에 담거나 `Object(…)`·제네릭 함수·`Object.assign`에 넘기지 않는다.
5. 전송(`MAIL_TRANSPORTS`)은 `send`가 받은 `MailMessage`에서 키를 같은 이름으로 하나씩 읽어 메일 패키지에 넘긴다(`subject: message.subject`). 펼쳐 넘기거나(`...message`) 복사본(`{ ...message, ...extra }`)에서 읽지 않고, 받은 값을 그 밖에 쓰지 않으며, 보내는 주소(`from`)와 메시지 옵션이 아닌 연결 설정(`host` 등) 밖의 것을 더하지 않는다. 제 문구를 쓰지 않고, 메일 패키지와 형식 밖의 것을 가져오지 않는다(다른 파일의 꼬리말도 제 문구다).

검사: 등록한 템플릿마다 예시 입력으로 만든 제목·텍스트·HTML과, `templates.ts`의 모든 문자열·템플릿 조각(보간은 숫자 0으로 읽는다. 예시가 지나지 않는 분기도 본다)에서 제외 기능 문구를 찾는다. `templates.ts` 밖에서 템플릿을 부를 때 넘기는 값을 만드는 문자열(그 값이 읽는 `const`·대입과, 함수의 매개변수면 그 함수를 부르는 모든 곳의 인자를 거슬러 간다)과 전송 파일의 모든 문자열도 같은 문구로 찾는다.

빠뜨리면: 내보냈는데 등록하지 않은 템플릿은 `templates.test.ts`가 실패시킨다. `MAIL_TEMPLATES`의 값이 `templates.ts`에 선언한 함수가 아니거나, `templates.ts`가 형식 밖의 것을 가져오거나(다시 내보내기 포함), 템플릿이 `MAIL_INPUTS` 밖의 입력·적은 형식과 다른 입력·객체가 아닌 입력을 받아도 실패한다. 시험은 API 소스를 TypeScript 형식 검사기로 읽어 메일을 보내는 곳을 모두 찾는다. 메일 모양의 매개변수(형식에 `subject`와 `text`나 `html`이 있다)에 넘기는 인자다. `Mailer.send`도, 구조 분해하거나 이름을 바꾼 것도, 다른 형식의 메일러도 그렇다. 그 인자를 펼침·`const`·조건식·`await`·형식 단언과 함수의 매개변수(그 함수를 부르는 모든 곳의 인자)를 거슬러 따라가, `templates.ts`에 선언된 것을 부른 값(`MAIL_TEMPLATES.x(…)`)에서 끝나지 않으면 실패한다. 함수를 부르는 곳은 이름의 철자가 아니라 기호로 찾아서, 가져올 때 붙인 별칭(`import { relay as forward }`)이나 네임스페이스로 부른 곳도 따라간다. 가는 길에 `subject`·`text`·`html`을 쓰거나, `MailMessage`에 없는 키를 싣거나, 다른 함수를 부른 값이거나, 따라갈 수 없는 값(속성 읽기, `let`, 이름 없는 함수의 매개변수, better-auth 훅처럼 API 밖에서만 부르는 함수가 받은 값)이어도 실패다. 전송 안에서 보내는 것은 따라가지 않는다. `Mailer.send`를 부른 곳에서 이미 따라갔다. 대신 전송이 메일 패키지에 메시지로 넘기는 값(패키지가 메시지 형식으로 받는 인자. `sendMail`의 메시지, `createTransport`의 설정과 기본값)은 `Mailer.send`가 받은 값에서 같은 이름으로 읽은 키(복사본에서 읽은 것은 아니다), `from`, 메시지 옵션이 아닌 설정뿐이어야 하고(`const`·조건식·펼침을 따라간다), 받은 값을 그 밖에 쓰거나(`arguments` 포함) 메일 패키지와 형식 밖의 것을 가져와도 실패하며, 그 파일의 모든 문자열에서 제외 기능 문구를 찾는다. 보내지 않더라도 `templates.ts` 밖에서 메일 모양의 값이나 템플릿이 만든 값을 펼친 객체 리터럴에 그 키를 쓰는 것, 템플릿이 만든 값에 그 키를 쓰는 것(속성 대입, 문자열 키나 문자열 리터럴 형식의 키 대입, 구조 분해 대입, `Object.assign`·`Object.defineProperty`·`Reflect.set`)은 실패한다. 다른 이름이나 좁은 형식(`{ subject: string }`)으로 받아 쓴 것과 함수의 매개변수로 받아 쓴 것도 그 값의 출처를 거슬러 찾는다. 템플릿이 만든 값과, 보내는 것을 따라가며 지난 `const`·매개변수는 보내는 데(펼침·조건식·형식 단언을 지나 `Mailer.send`나 따라간 매개변수의 인자, 따라간 `const`의 초기값이 되는 것)와 키 읽기(`content.subject`)에만 써야 한다. 배열·Map에 담거나, `Object(content)`·제네릭 함수(`<T>(x: T) => x`)·`Object.assign`처럼 보내는 것을 따라가며 지나지 않은 매개변수에 넘기거나, `arguments`로 읽으면 따라가지 못하는 이름으로 고칠 수 있으므로 실패한다. `Mailer.send`를 부르지 않고 값으로 넘기면(무엇을 보내는지 볼 수 없다) 실패한다. 메일 패키지(이름에 mail·smtp가 든 것, SES SDK, resend, postmark)는 `MAIL_TRANSPORTS`에 사유와 함께 적은 파일만 가져온다. 지금은 `mail/mailer.ts`(`Mailer.send` 뒤의 SMTP 전송) 하나이고, 그 파일이 메일 패키지를 더 가져오지 않으면 허용이 남았다고 실패한다. 워크스페이스에서 메일 패키지를 의존성으로 두는 곳도 `apps/api`뿐이어야 한다. 따라가기가 아무것도 찾지 못하고 통과하지 않도록, 등록한 템플릿은 모두 어딘가에서 보내야 한다. 쓰지 않는 템플릿은 지운다.

### SMS

SMS는 모두 `apps/api/src/sms/templates.ts`에서 만들고 `SMS_TEMPLATES`에 등록한 템플릿으로 보낸다(ADR-0070). 지금은 본인확인 인증번호(`verificationCode`) 하나다. 메일과 같이 회원이 읽는 문구이므로 모든 화면 항목으로 찾는다(서비스 안내가 아니다).

1. 템플릿을 `templates.ts`에 함수로 쓰고 `SMS_TEMPLATES`에 이름으로 넣는다. `templates.ts`는 형식만 가져온다(`import type`). 입력은 값(인증번호, 분)뿐이고 부르는 쪽이 고르는 낱말은 받지 않는다.
2. `sms/templates.test.ts`의 `EXAMPLES`에 예시 입력을 넣는다(가장 긴 값 포함). 템플릿마다 하나 이상을 요구해서 빠뜨리면 컴파일이 실패한다.
3. 발송기(`SmsSender`: 알리고 `aligo-sms-sender.ts`, 개발용 `dev-sms-sender.ts`)는 템플릿이 만든 글을 그대로 보내고 제 문구를 쓰지 않는다. 개발용 발송기는 SMS 대신 메일 템플릿 `devVerificationCode`로 Mailpit에 보내므로 그 메일은 위 메일 규칙을 따른다.

검사: 등록한 템플릿마다 예시 입력으로 만든 글과 `templates.ts`의 모든 문자열에서 제외 기능 문구를 찾고, 글이 SMS 한 통(EUC-KR 90바이트, 알리고 `msg_type=SMS`)에 들어가는지와 모든 글자가 EUC-KR에 있는지 본다(통신사 시스템이 EUC-KR로 바꾸므로 밖의 글자는 '?'로 간다).

### 화면

- 새 화면 문구는 그냥 검사된다. 제외 기능 낱말이 그 뜻이 아니게 들어가야 하면 위 허용 가운데 맞는 것을 쓰고, 없으면 이유와 함께 가장 좁은 허용(구절, copy 키)을 더한다.
- 관리자 화면은 따로 등록하지 않는다. `app/admin` 아래 두거나 관리자 코드만 가져다 쓰면 도박 어휘만 검사된다. 관리자 전용이던 파일을 회원 화면이 가져다 쓰기 시작하면 그 파일은 회원 화면으로 모든 항목을 검사받는다.
- 보존한 결제 코드를 회원 화면에 다시 그리려면 그것은 유료 판매를 여는 일이다(#111). `PRESERVED_PAID_SOURCES`에 파일을 더해 비켜 가지 않는다.
- 서비스 안내(#136)는 `app/(service-guide)` 아래에 두거나, 다른 자리에 두면 `SERVICE_GUIDE_ROOT`를 그 폴더로 바꾼다. 부정 안내의 모양(`NEGATIVE_NOTICE`)이 #136의 문장에 맞지 않으면 그 이슈가 넓힌다.

## 검사하지 않는 것

- 저장된 행: 관리자가 쓴 시장 문구, 사용자가 고른 닉네임, 이미 DB에 있는 자동 닉네임 `예측가_XXXX`와 시드가 이미 넣은 시장 문구(TERMS.md '범위'). 검사는 코드와 스키마만 읽는다.
- 화면에 그려진 결과(Playwright로 페이지를 훑지 않는다). 화면 수준 확인은 #189다.
- 메일: 메일 패키지도 메일 모양의 형식도 쓰지 않고 메일 서비스를 부르는 코드(`fetch`로 HTTP 메일 API에 보내는 본문 등).
- 메일: `Mailer`를 느슨한 형식으로 받아 부르는 곳. `@Inject(MAILER)`를 `{ send(message: object) }`로 받거나 `as unknown as { send(m: Record<string, string>) }`로 바꾸면 메일 모양의 매개변수가 아니라서 보내는 곳으로 찾지 못한다. `createRequire(…)('nodemailer')`처럼 `require`라는 이름이 아닌 함수로 가져온 메일 패키지도 찾지 못한다.
- 메일: 추상 메서드·인터페이스 멤버로 부른 함수(`relayer.relay(…)`가 추상 선언으로 풀린다)와 문자열 키로 부른 함수(`this['relay'](…)`)의 인자. 그 함수의 매개변수를 거슬러 갈 때 부르는 곳으로 찾지 못한다.
- 메일: 다른 파일이 실행 중에 `MAIL_TEMPLATES`의 항목을 바꾸는 것(`Object.assign(MAIL_TEMPLATES, …)`, `Object.defineProperty`). `as const`는 형식뿐이고, 시험은 `MAIL_TEMPLATES.x(…)`를 부른 값을 템플릿으로 믿는다.
- 메일: `templates.ts`나 전송이 가져오지 않고 읽는 전역 값(다른 파일이 채운 `globalThis.MAIL_COPY`, `process.getBuiltinModule('node:fs')`로 읽은 파일)의 문구.
- 메일: 받는 주소(`to`)의 표시 이름(`"이번 주 베팅 마감 안내" <a@b>`). `to`는 낱말을 찾지 않고 전송이 그대로 To 머리글에 넘긴다. 보내는 주소(`SMTP_FROM`)의 표시 이름도 환경 설정이라 보지 않는다.
- 메일: 템플릿 입력에 넘기는 값 가운데 문자열 조각이 아닌 것의 내용. 함수·메서드가 돌려준 값(`newEmail: headline()`, `url: this.words()`), enum 멤버(`url: Copy.Headline`), DB·요청·better-auth가 준 값(새 이메일 주소, 링크)이다. 그 입력의 이름(`MAIL_INPUTS`)과 형식만 본다.
- 메일: `templates.ts`에서 예시가 지나지 않는 분기에 조각으로 나눠 이어 붙인 낱말(`['이번 주 ', '베', '팅 마감'].join('')`). 문자열 조각은 하나씩 찾는다.
- 메일: `src/test` 아래 파일(시험 지원)이 보내는 메일. 운영 코드가 그 파일을 가져와도 읽지 않는다.
- 메일: 전송이 메일 패키지에 메일 모양이 아닌 형식으로 넘기는 요청(SES API의 본문 등). 문자열만 찾는다.
- `apps/mobile`(화면이 없는 Expo 스캐폴드), 마이그레이션 SQL의 트리거·함수 이름, 모든 오류 봉투에 붙는 `ErrorCode` 값의 유료 구매(`PAYMENT_GATEWAY_*`).
- 기록 문서: `docs/PLAN.md`(부록 A의 옛 문구 원칙 포함), `docs/QUESTIONS.md`, ADR 본문, 마이그레이션 주석.
- 대회 어휘(상금·참가비·우승). 제외 목록에 넣지 않았고 챌린지(#81)가 다시 본다(오너 결정 2026-10-14).
- 본인 전용·관리자 API의 경로 밖 이름(응답 필드, 문서의 작업)과 경로의 송금·활동량 보상·현금 환전·출금 밖 항목, 본인 방 이벤트의 필드 이름, 관리자 화면의 도박 어휘 밖 문구(오너 결정 2026-10-14). 비공개 정보 누출과 교차 계정 확인은 그대로 본다.
- 웹 주소의 확률·믿음 낱말(`PERSONAL_PROBABILITY_WORDS`). 확률 입력·Forecast의 토큰(`probability-input`)은 찾는다(ADR-0057 결과 5).
- 사용자에게 Coin이 들어오는 경로를 닫힌 목록으로 고정하는 일(#73). 지금은 이름으로만 찾는다. 낱말을 피한 이름(Coin 없이 `send`만 쓴 `/me/send`, 보상·보너스 낱말이 없는 원장 유형)은 걸리지 않는다.
