# #333 고른 출시 값(C5·R2)으로 다시 돌린 #71 모형과 #131 서비스 시나리오

오너가 고른 출시 값으로 세 가지를 한 번에 돌렸다(오너 답 333-1, [ADR-0173](../../DECISIONS.md)). **#71 모형은 C5(`--candidate C5`, 252회), #332 driver는 C5 위 R2(`--candidate R2`, 36회), #131 서비스 시나리오는 C5(새 worker 시험 파일 12개)**다. 세 실행 모두 실패와 불변식 위반이 0이다. 다시 돌린 모형 행 288개(252 + 36)는 저장된 #71·#332 행과 행 전체 JSON으로 모두 같았다. 서비스 시나리오의 기대 결과 12개도 모두 통과했다. 오너 답은 [#333의 댓글 '오너 답 (2026-11-25)'](https://github.com/sboh1214/sw04-buddha/issues/333#issuecomment-7163359157)에 있다.

**고른 값으로 돌린 모형·서비스 실행 결과다. 검증 완료도, 추천 값도, 출시 승인도 아니다**(N01 §10 "현재 문서에서 특정 수치를 검증 완료라고 주장하지 않는다", N00 §7). 문턱이나 순위를 두지 않았다. 영수증은 모두 로컬 실행이다. 원격 CI와 배포는 별도 영수증이다.

- [모형 결과와 행 대조](RESULTS.md) — `scripts/launch-rerun-333/check.mjs`가 만든다.
- 모형 영수증: [#71 C5](71-c5/results/manifest.json)·[대조](71-c5/results/row-comparison.json), [#332 R2](332-r2/results/manifest.json)·[대조](332-r2/results/row-comparison.json)

| 소진 기준액 | 1회 지급액 | 대기기간 | 주기 / 주기 안 횟수 |  누적 상한 |

R2는 오너가 직접 고른 값이 아니다. 오너가 "너가 결정해"로 고르기를 맡겼고, 맡은 쪽(Claude Code)이 R2를 골랐다. ADR-0172 결과 7은 "오너가 다른 후보로 바꾸면 이 결과를 고쳐 적는다"라고 적는다. 따라서 R2는 아직 바뀔 수 있다. 바뀌면 같은 방식으로 #332 driver를 다시 돌린다(ADR-0129 결정 6).

## HEAD와 해시

- **기준 HEAD**는 `d38c48e30838b42652e6e3ae6e8376108e08fb20`(main)이다. 두 모형 실행의 manifest `head`가 이 값이다. 실행 전에 `pnpm install --offline --frozen-lockfile`과 `pnpm --filter @buddha/shared build`를 했다.
- **#71 C5**는 `sourceDigest aff9707deb6f86b2e2f34a24398eac79ed56c9a5254c3508b5b11ec0e5cf4ab6`(654개 파일, 실행 전후 같음), `resultsSha256 44e2c181a98e54c1707ac49ab24102015f362a52e32c1d7d65e40123355d438c`이다.
- **#332 R2**는 `sourceDigest f24e96e060940065d855700355580b35122c79c87abc66b0b839e64c249ef1a3`(667개 파일, 실행 전후 같음), `resultsSha256 dbb4fa1c4497f36fd5def2059acc019201605617cc8888bd4ed23814aee5bcc1`이다.
- 두 모형 실행 때 작업 트리에는 커밋되지 않은 파일이 이 결과 폴더뿐이었다. 모형이 읽는 소스는 HEAD 그대로였다.
- **#131 C5**는 커밋되지 않은 새 시험 파일(sha256 `b619481a6af1de72e0645af6bd0eb7e0bb77e81187b09018be51a4fba28e5aa3`)로 돌렸다. 이 문서를 담은 PR 커밋의 SHA는 기준 HEAD와 다르다. 그래서 기준 HEAD만으로 실행 코드를 특정하지 않는다. 영수증의 `sourceSha256`이 실행에 쓴 파일 667개의 해시를 남긴다. 해시는 실행 시작 직전과 끝난 직후에 찍었고 같았다.
- 부분 집합이라 `resultsSha256`는 저장된 전체 실행(#71 `01e67574…`, #332 `dcc37c30…`)의 것과 다르다.

## 저장된 행과의 대조

`check.mjs`가 두 영수증을 검사한 뒤 대조한다. 먼저 영수증을 검사한다. 저장된 #71·#332 영수증이 깨끗한지(실패 0, 소스 같음, 위반 0, `counterexamples/` 없음), 결과 해시가 manifest와 같은지, `inputs.json`의 키가 저장된 실행의 것과 같은지, 실패 0, 위반 0, `counterexamples/` 없음, 실행 전후 소스가 같은지, `qualityThresholds null`·`releaseApproved false`인지, 행 수가 맞는지 본다. 다음으로 저장된 실행과 입력이 같은지 본다. 후보 값, 9조합, 경로나 변형, seed, 주기가 저장된 실행과 같아야 한다. 마지막으로 저장된 같은 후보의 행과 행마다 대조한다. 하나라도 어긋나면 결과 문서를 쓰지 않고 멈춘다.

## 민감도 실행이 아니다 — `'scale-sensitivity'` 라벨

133-31은 민감도 실행을 "하지 않는다. 고른 출시 값으로만 다시 검사한다"로 정했다. 이 실행은 C5 열한 값과 R2 여섯 값만 돌렸고, R0 대조군도 다시 돌리지 않았다(333-6). R0과의 비교는 저장된 #332 행을 인용한다.

#71 모형의 9조합 가운데 일곱은 `scripts/economic-simulation/inputs.ts`에서 프로필 라벨이 `'scale-sensitivity'`다. 이 라벨은 **참가자 수(20/100/500)와 시장 수(1/5/20)의 축**을 가리킨다. 133-31이 막은 '승인된 설계 제안 값을 바꿔 보는 실행'이 아니다. 14경로의 `stale-*`(갱신 지연)와 `news-stop-*`(운영 중단 지연)도 시나리오 축이다. 이 축들은 C5의 값을 바꾸지 않고, 출시 설정에도 해당 키가 없다(`packages/shared/src/release-settings.ts`). #333 범위도 "두 가정(내부 테스트·초기 공개)과 9조합으로 돌린다"라고 적는다.

## #131 서비스 시나리오(C5)

새 파일은 `apps/worker/src/jobs/market-maker-launch-values.test.ts`다(333-2). 기존 #131 파일 `market-maker-scenarios.test.ts`·`market-maker-delivery.test.ts`와 그 기대 결과는 바꾸지 않았다. 기존 파일의 helper(`setup`·`cycle`·`checkpoint`·`order`·`finishAudit`)는 새 파일로 복사했다. 새 파일은 worker 시험에 들어 있으므로 CI가 이후 커밋에서도 다시 돌린다.

**값이 들어가는 길(시험 코드만).** C5는 #71의 `inputs.json`에서 id로 골라 strict schema로 읽는다. 값을 시험 코드에 다시 적지 않는다. 단계 셋(`market_maker.reduce_at_bp`·`halt_at_bp`·`reduce_ratio_bp`)은 `setReleaseSetting(status: 'test')`로, A·L·b·단계 수·물량·안전 간격은 `createOpenedMarket`의 유동성 설정으로, 가격 보호 5틱은 시장의 `priceProtectionTicks`로 넣는다. 사용자 지갑은 기존 #131처럼 100,000 Coin이다(333-4). 그래서 S·인구·수요의 효과는 이 실행이 다루지 않으며 #71 몫이다(ADR-0128 결정 4). 서비스 코드는 바꾸지 않았다.

**기대 결과는 C5 값에서 나온다.** 기존 #131 fixture(b 100,000, 보호 98)에 맞춘 '일방향 50회 안 halt'와 '고래 200'은 옮기지 않았다(333-2의 범위 밖). 거래 수량은 C5가 고른 가격의 첫 단계에서 다 체결되는 크기로 정했다. 첫 시험이 `quoteLadder(0, C5)`의 첫 단계 수량이 3 이상인지 확인한다. 한 계약은 어느 사다리에서나 첫 단계(그 가격 자신이 기준가)에서 체결된다.

| 시나리오                   | 기대 결과                                                                                                                                                                                                                                              |

| 정상 YES / NO / VOID(3개)  | 양방향 1계약 넷씩 체결 뒤 쌍 소각으로 MM 보유 0, 이어 YES 3·NO 1 보유. 마감과 겨룬 주문은 체결 없음. 실제 지급 callback 뒤 COMMIT 전 실패는 모두 롤백되고, 동시 두 번의 정산은 한 번만 지급한다(계약당 100/0, VOID 50/50). 재정산 무변화, 회수는 한 번 |

모든 시나리오는 안정된 검사 지점마다 ADR-0128 결정 2의 필수 합격을 본다. 담보 = 미정산 쌍 × 100, 원장 발행·소각 밖 총량 보존, 음수·과예약 없음, 보유·예약 위험 ≤ L(4000)이다. 순차 주문은 같은 request ID 재전송 뒤 원장·체결이 같아야 한다. 마감 뒤 체결이 없어야 하고, 정산과 회수는 한 번이어야 한다. 각 시나리오 끝에는 #93 대사(시장·사람·총량)가 통과하고 보류가 없어야 한다. MM 3회 소진 시험은 `setup()`을 쓰지 않으므로 같은 검사(멈춘 봇과 계속 호가하는 봇의 보유·예약 위험 ≤ L, 불변식, #93 대사)를 끝에서 따로 한다. 호가 공백, spread, 응답 시간은 관측만 하고 문턱을 두지 않는다(ADR-0128 결정 4). 관측값은 영수증의 `observations`에 있다.

**R2의 서비스 시나리오는 없다**(333-5). 재지급 값은 #131이 다루는 MM·판정·정산 경로를 바꾸지 않는다. #74의 `packages/db/src/regrants.test.ts`는 규칙 코드의 시험이며 R2 값의 근거가 아니다. 그래서 R2의 검증 범위는 기록대로 '#71 모형 재지급 실행만, #131 없음'이다. ADR-0172의 "R2(와 C5)로 #71 모형과 #131을 다시 돌리는 것은 #333"은 이 답으로 좁혔다(ADR-0173).

## 기록 표에 넣을 수 있게 남기는 약점

333-7에 따라 `docs/SETTINGS.md`의 기록 표는 고치지 않았다. 표 갱신은 출시 승인 ADR(133-9)에서 한다. 아래는 그때 옮길 수 있게 원문 그대로 둔다. 다시 돌린 행이 저장된 행과 같으므로 원문의 수치와 행 번호는 이 실행에도 그대로 해당한다. 원문의 행 번호는 #71·#332 폴더의 파일을 가리킨다.

**C5** — ADR-0171(`docs/DECISIONS.md`)의 원문. 'scenario-summary'와 'RESULTS'는 [#71의 파일](../71-economic-simulation/)이다.

> 기록 표에 남길 약점(133-17): 시장 하나에 100명이면 일방향·stale-0에서 halt(scenario-summary 549·555행 — 늘리기 전 판단 133-14에서 본다), 큰손 1회 주문의 기준값 변화 4.488이 C1\~C5 중 가장 큼(RESULTS 62행), 큰손 20분할은 9조합 모두 무체결, 갱신 250ms 이상에서 IOC 23.46%, 9조합 최악 손실 42300 / 80000(p500-m20), 작은 예산 무체결은 모든 후보 공통.

**R2** — ADR-0172 결과 7의 원문. 'RESULTS 요약'과 행 번호는 [#332의 후보 요약](../332-regrant-simulation/results/candidate-summary.csv)이다.

## 재현

저장소 루트, Node 24, lockfile의 pnpm 11.10.0을 쓴다. 결과 폴더에 `manifest.json`이 있으면 runner가 거부한다. manifest가 없는 폴더(중단된 실행이 남긴 폴더)는 조용히 덮으므로 반드시 새 빈 폴더에서 돌린다.

```sh
pnpm install --offline --frozen-lockfile
pnpm --filter @buddha/shared build
node scripts/economic-simulation/run.ts --out /tmp/buddha-333-c5 --candidate C5
node scripts/economic-simulation-regrant/run.ts --out /tmp/buddha-333-r2 --candidate R2
pnpm exec prettier --write /tmp/buddha-333-c5 /tmp/buddha-333-r2   # 저장소의 JSON은 prettier 형식
node scripts/launch-rerun-333/check.mjs --c5 /tmp/buddha-333-c5 --r2 /tmp/buddha-333-r2 \
  --out /tmp/buddha-333-RESULTS.md
```

prettier는 `inputs.json`과 `manifest.json`의 줄바꿈만 바꾼다. 영수증의 해시는 `results.jsonl.gz`와 `comparison.csv`의 것이라 그대로다. 저장소의 결과로 대조와 `RESULTS.md`만 다시 만들려면 인자 없이 `node scripts/launch-rerun-333/check.mjs`를 실행한다. 모형은 다시 돌리지 않는다.

```sh
pnpm exec tsc -p scripts/launch-rerun-333/tsconfig.json
node --test scripts/launch-rerun-333/check.test.ts
(cd scripts/launch-rerun-333 && ../../packages/shared/node_modules/.bin/eslint .)
```

#131 서비스 시나리오는 테스트 DB와 **전용 Redis**를 쓴다(Redis DB 번호는 Pub/Sub을 나누지 않으므로 별도 인스턴스 — #131 README). 이 실행은 이 실행만 쓰는 임시 컨테이너(`redis:7.4.11-alpine`, 포트 16433)를 띄워 돌리고 끝나고 멈췄다. `TEST_DATABASE_URL`, `TEST_DATABASE_MIGRATE_URL`, `TEST_REDIS_URL`을 테스트 인스턴스로 두고 `CI=true`를 함께 둔다. 이 값이 없으면 시험이 건너뛰어지고 `passWithNoTests` 때문에 성공으로 끝난다. `CI=true`면 DB URL이 없을 때 global setup이, `TEST_REDIS_URL`이 없을 때 새 파일의 실제 큐 시험이 실패한다. JSON 결과에서 `numPendingTests`가 0인지도 확인한다.

```sh
pnpm exec turbo run build --filter='worker^...'
CI=true MM_SCENARIO_OBSERVATIONS=1 pnpm --filter worker test \
  src/jobs/market-maker-launch-values.test.ts \
  --reporter=default --reporter=json --outputFile.json=/tmp/m333-vitest.json
```

관측값은 stdout의 `MM_LAUNCH_VALUE_OBSERVATIONS=` 줄에 나온다. 영수증 `131/results-333-c5.json`은 worker 시험 전체를 돌린 JSON 결과와 이 줄을 모아 만들었다. 형식은 #131의 [`results-final-stack.json`](../131-service-scenarios/results-final-stack.json)과 같다. 저장소에는 이를 조립하는 스크립트가 없다.

## 한계

- **로컬 실행이다.** 원격 CI·외부 리뷰·배포는 별도다. #131 영수증은 커밋 전 시험 파일로 돌렸다. 어느 실행을 #149의 시험 결과로 인정할지는 #149의 '시험 결과를 인정하는 기준'이 정한다. #333은 실행 SHA와 소스 해시만 남긴다.
- **모형은 직렬 순수 모형이다.** 승인·DB 원장·잠금·동시성·재시도는 모형에 없고, #131이 C5로 일부 경로만 실제 서비스에서 돌렸다. #71과 #332의 한계(합성 입력, seed 둘, 7분 경로, VOID 없는 재지급 주기, 주기마다 새로 발행하는 금고 등)는 그대로다([#71 README](../71-economic-simulation/README.md), [#332 README](../332-regrant-simulation/README.md#한계)).
- **#131은 시나리오 몇 개의 점 표본이다.** 사용자 지갑은 100,000 Coin이고 사람은 넷이다. 거래 크기는 작다. C5의 일방향 halt·큰손·오래된 호가는 서비스에서 돌리지 않았다. 그 약점은 #71 모형의 것이다. 관측한 공백·spread·시간은 출시 기준이 아니다.
- **R2의 서비스 시나리오는 없다**(333-5). 재지급 신청·지급을 R2 값으로 실제 DB에서 돌리지 않았다.
- **불변식 위반은 없었다.** 위반이 나왔다면 그 값을 #149에 넘기지 않고 #133에 알렸을 것이다(133-18). 출시를 미룰지, 새 후보를 고를지는 #133에서 오너가 정한다.
