# 운영 MM·판정·정산 서비스 시나리오 (#131)

2026-11-11 오너가 승인한 추천안에 따라 불변식과 시나리오의 기대 결과를 필수로 검사한다. 호가 품질과 응답 시간은 관측값이며 출시 문턱을 정하지 않는다. #71의 합성 모형이나 직접 AMM 시절 결과를 실제 DB·서비스 검증으로 대체하지 않는다. 최종 출시 수치(#133)는 같은 묶음으로 다시 실행해 #149에 별도 결과를 남긴다.

## 실행 경계와 재현

`apps/worker/src/jobs/market-maker-scenarios.test.ts`는 실제 PostgreSQL에서 주문 접수·매칭·MM 갱신·시장 마감·판정/이의 처리·확정·정산·회수·#93 대사를 호출한다. `market-maker-delivery.test.ts`는 실제 Redis/BullMQ producer와 production processor를 실행한다. 테스트 DB의 각 파일 잠금과 초기화를 사용하므로 개발·운영 DB에서 실행하지 않는다. 동시에 다른 검사를 실행할 때에는 Redis도 **별도 인스턴스**를 쓴다. Redis DB 번호는 Pub/Sub를 격리하지 않는다.

저장소의 테스트 환경 설정 후 다음을 실행한다. `TEST_DATABASE_URL`, `TEST_DATABASE_MIGRATE_URL`, `TEST_REDIS_URL`이 테스트 인스턴스를 가리켜야 한다.

```sh
pnpm exec turbo run build --filter='worker^...'
MM_SCENARIO_OBSERVATIONS=1 pnpm --filter worker test \
  src/jobs/market-maker-scenarios.test.ts \
  src/jobs/market-maker-delivery.test.ts \
  --reporter=default --reporter=json --outputFile.json=/tmp/m131-vitest.json
```

전체 CI의 worker test에 자동 포함된다. 공유 엔진과 DB는 기존 `^build` 의존으로, #71의 버전 입력 JSON은 새 worker `turbo.json` 입력으로 캐시가 무효화된다. 최종 스택·원격 CI·E2E 결과는 각각 실제 실행한 커밋에 연결한다.

개장 준비 팩토리는 명시적인 시험 금고 재원·두 관리자 검수 기록을 만들고 실제 개장/배정 함수를 호출한다. HTTP 가입·검수 화면을 이 묶음이 시험했다는 뜻은 아니다. 판정·조기 마감·정정 팩토리도 실제 domain writer를 사용하지만 API의 인증·CSRF·운영 기록을 대신 검증하지 않는다. 그 경계는 기존 API/E2E 검사에 남는다. 출처 지연과 마감·이의 기한은 시험 전용 시계/일정 조정으로 경과를 표현하며 실제 시간만큼 기다리지 않는다. raw fill·원장·잔고를 만들어 경제 경로를 건너뛰지 않는다.

모든 시나리오의 안정된 검사 지점에서 담보=미정산 쌍×100, 원장 발행/소각 밖 총량 불변, 음수·과예약 없음, 실제 체결과 주문 수량/대금의 일치를 검사한다. 네 방향 경합은 각 커밋 전 손실 한도도 검사하고, 모든 작업이 끝난 뒤 전체 불변식을 다시 검사해 서로 다른 중간 시점의 읽기를 비교하지 않는다. 순차 주문은 같은 request ID 재전송 뒤 원장·체결이 동일하며, 동시 네 주문도 모두 replay를 확인한다. 각 시나리오 뒤 시장·4개 사용자·총량의 실제 #93 대사가 통과하고 보류가 없어야 한다. 정산 완료 경로에는 스코어 계산 의존이 없다.

소규모 기본 fixture는 A=10,000, L=5,000 Coin, b=100,000, 3단계·방향별 총량10·안전1틱, 가격 보호98틱, reduce/halt=70/90%, 축소50%다. 거의 평평한 b로 재고 누적을 분리해 검사한다. #71 후보 8벌에서는 해당 후보의 MM 설정을 사용한다. 사용자 지갑은 각각100,000 Coin으로 충분히 마련하여 MM 동작을 분리하므로 S·인구·수요의 효과를 검증했다고 주장하지 않는다.

## 보존한 실행 결과와 한계

[results.json](results.json)은 2026-11-11 실행의 **24/24 통과·실패0**, 검사별 결과, 실제 설정, 23개 시나리오 관측, 당시 기반 커밋과 572개 실행 관련 파일의 해시를 보존한다. Turbo strict·force 경로의4개 작업이 모두 캐시 없이 통과했고, 전체 1793개 파일의 실행 전후 해시가 같았다. 커밋되지 않은 #131 소스를 실행했으므로 기반 SHA만으로 실행 코드를 특정하지 않으며, 해시와 테스트 파일을 함께 확인한다. 뒤에 재적층한 HEAD로 당시 기록을 바꾸지 않는다.

이 실행은 안정된 검사 지점220개, OPEN 관측203개 중 한쪽 매도 호가가 없는 관측48개였다. 이는 단계 중단·의도적으로 갱신을 보류한 상태 등을 포함하는 **물리적 게시 호가의 점 표본**이다. 지속 시간이나 공급률로 환산하지 않는다. 연속 기간 지표는 #182의 관측 시작·미관측 구분과 정의를 사용해야 한다. 양쪽 가격이 존재한 표본의 매도−매수 spread 범위는 시나리오별 JSON에 남긴다.

로컬에서 계측한 순차 주문 helper 최대 약72.7ms, MM 갱신 최대 약187.4ms였다. 다른 전체 검사도 함께 실행한 개발 환경의 단일 관측이며, HTTP 응답 시간·성능 SLA·출시 기준이 아니다. 주문 계측/수량 합계는 해당 helper를 통과한 순차 주문만 포함하며 별도 실행한 동시 주문·중단 거절·마감 경합 요청을 포함하지 않는다. replay·불변식 검사 시간은 주문 계측에서 제외한다. UUID와 실제 커밋 순서는 실행마다 달라질 수 있다.

개발 중 보존한 실패는 잘못된 원장 enum 기대, 0수량 계약의 지급 행 기대, 후보 입력의 부가 키, fixture 타입/비동기 lint, 출처 지연의 사건 기한보다 이른 판정 시각이었다. 각각 기대·시험 설정을 실제 계약에 맞춰 수정했다. 초기 단축 실행20개와 최종24개는 합산하지 않는다. 실제 before-COMMIT 오류는 의도한 실패 주입이며 그 롤백·재시도 검사가 통과해야 한다. 운영 데이터·수치 정책·기존 원장을 수정한 결과가 아니다.

현재 기록은 로컬 집중 검증이다. 실제 최종 스택의 전체 검사·외부 리뷰·CI를 별도로 확인하고 운영 머지·배포는 오너 승인 후 진행한다. 지급 후 정정은 #144, 화면 수준 거래 인수는 #189, 최종 출시 값은 #133의 범위다.
