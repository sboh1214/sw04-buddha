# #71 출시 경제 수치의 합성 후보 비교

2026-11-11 오너가 승인한 시험 가정으로 **8개 후보 × 참가자 3수준 × 시장 3수준 × 14경로 × 2seed = 2016회**를 실행했다. 불변식 오류는 0건이며, 모형의 보존 검사는 1,531,014회 호출됐다. [비교 결과](RESULTS.md)와 [원 실행 영수증](results/manifest.json)에 모든 결과와 실행한 소스 해시를 보존한다. 이는 출시 합격, 공식 권장값 또는 운영 성능 보장이 아니다. 품질 문턱·우선순위·출시 값은 #133이 결정한다.

실제 공유 계산을 쓰는 직렬 경제 모형이다. 승인·DB 원장·SQL 잠금·커밋 실패·BullMQ·재시도 경합은 실행하지 않았다. 그 서비스 증거는 #131이 별도로 만든다. 원본 직접 AMM 거래 기록이나 옛 수학 시험의 성공 횟수는 이번 결과의 근거로 사용하지 않았다.

S는 사람마다 한 번만 지급하고 여러 시장이 같은 지갑·예약을 사용한다. 시장마다 다시 지급하지 않는다. 초기 총 발행은 `참가자 수 × S + 시장 수 × A`이며 시장별 A 전액이 Coin이고 초기 쌍은 0이다. 추가 지원·재지급은 실행하지 않으므로 모형의 추가 금고 잔액은 0이다. 위 금고 숫자는 초기 배정의 최소 필요량이며 **운영 예비금 0을 권장하는 결정이 아니다**. 추가 지원 예비금과 실제 출시 시장 수는 #133의 별도 선택이다.

b는 Coin이 아니라 계약 수 단위의 곡선 민감도다. 같은 순보유 변화에서는 큰 b가 곡선을 완만하게 한다. 개장 50 부근에서 S 전액이 대략 `S/50`계약을 살 수 있다고 가정해 그 수와 b를 비교할 수 있지만, 실제 ask는 안전 간격·반올림으로 50보다 높고 물량·단계 수·가격 보호·Coin·예약 L이 먼저 자를 수 있다. 전액 주문 수량을 보장하거나 직접 LMSR 손실식을 이 봇의 보장으로 사용하는 계산이 아니다.

C1↔C2는 b, C3↔C7은 S만 다르다. C2↔C3은 물량과 단계 수, C3↔C4는 안전 간격과 보호 폭을 함께 바꾼다. C5/C6은 여러 값을 묶어 바꿨다. 모든 차이를 한 변수의 인과 효과로 해석하지 않는다. 입력은 실제 shared 유동성 schema·위험 설정 검증을 통과하며, 숫자 입력 상한 안에 있다는 사실은 경제적 타당성 판단을 대신하지 않는다.

## 가정과 14경로

참가자 20/100/500명과 시장 1/5/20개를 **9조합으로 독립 교차**한다. 20명/1시장은 내부 가정, 100명/5시장은 초기 공개 가정, 500명/20시장은 압박 가정으로 부르고 나머지 6개도 같은 방식으로 보존한다. 대표 라벨은 실제 수요 예측이나 출시 규모 선택이 아니다. seed 71과 20261112를 사용한다. 참가자·방향·시각·S에 대한 예산 비율의 tape는 후보마다 동일하다.

한 경로의 시장은 7분에 마감하며 마지막에 마감 후 주문을 한 번씩 더 시도한다. 정산 모형 시각은 마감 뒤 24시간이다. 각 시장의 각 결과를 검사하고, 공동 결과가 모두 YES/모두 NO/모두 VOID인 세 가지 지급 사본을 만든다. 3^M개의 결과 조합을 모두 열거하지 않는다. 위험은 각 시장의 세 결과 중 최악을 잡고 시장끼리 이익으로 상쇄하지 않으므로 혼합 결과를 낙관적으로 상쇄해 한도를 늘리지 않는다.

외부 요청은 정해진 도착 순서로 직렬 처리한다. 같은 시각에는 예약된 refresh, 그 다음 tape 입력 순서를 사용한다. MM 체결 뒤 갱신을 예약하고 60초 간격의 보완 scan도 명시한다. 60초와 7분은 유한한 시험 설계이며 운영 지연 SLA가 아니다. 속도 제한·세션·관리자 권한·여러 계정의 동일인 식별·네트워크 재전송은 모형에 없다. 실제 요청 빈도 제한을 우회하라는 운영 지침이 아니다.

## 공유 함수와 어댑터 경계

- 호가 생성은 `quoteLadder`, 자산·예약·단계는 `botRisk`·`planBotQuotes`, 전체 취소·재게시 계획은 `reconcileBotQuotes`를 재사용한다. 같은 가격의 그대로 남는 주문은 도착 순서를 유지하고, 줄일 주문은 행의 잔량 전부를 취소한 뒤 다시 계획한다.
- 모든 주문·위험 한도·환산 ask·자기 체결·가격 보호·예산 정수화는 `planRiskIntakeMatch`와 실제 `matchOrder` 경로를 사용한다. 어댑터가 새 매칭 알고리즘을 만들지 않는다. `projectedBook`과 실제 적용한 Coin·보유를 매번 비교한다.
- 계약 원가·매매 손익은 `applyBuy`·`applySell`, 양 보유 소각은 `applyPairBurn`, 정산은 `settlePosition`을 사용한다. 잠금은 `orderIntakeLock`·`orderRemainingLock`으로 계산한다. 모형은 총 Coin과 예약을 따로 세고 가용액에서 예약을 뺀다.
- 정수 1계약, 지급 100 Coin, VOID 양쪽 50 Coin, 틱 1, 가격 1~99, 수수료 0, 개장 50%·초기 쌍 0, L≤A가 고정값이다. 보유 차의 곡선 기준가격은 소수일 수 있으나 실제 체결가격은 정수다.
- 모형의 MM ID는 시장별 자금 구분용 합성 ID다. 한 시장에 하나의 MM만 있고 모든 비인간 주문은 같은 자기 체결 금지 그룹이다. 실제 전역 MM 로그인·계정 생성은 모형 범위가 아니다.
- 모형 소각은 OPEN에서 실행한다. 실제 서비스는 정상 PAUSED에서도 허용하지만, 이 tape는 pause에서 주문을 취소하고 이후 체결이 없어 새 쌍이 생기지 않는다. PAUSED 소각 서비스 검증을 했다고 주장하지 않는다.
- 같은 요청 ID의 완료 사본과 정산 `completed` Map으로 재지급 불변식을 확인한다. 이는 **DB 원자성·영구 멱등 키·프로세스 재시작 증거가 아니다**. 승인·발행·배정·회수도 보존을 확인하는 합성 자금 흐름이며 실제 관리자 절차는 실행하지 않는다.

## 지표 정의와 관측된 약점

모든 결과에는 시장별 보유·자본·세 결과 손익, 최악/예약 손실, 단계별 OPEN 시간, IOC 시도/완료, 게시/체결 봇 계약 수, 공급 공백, spread, 정산 지급·회수 사본이 있다. 모든 금액은 계산 중 bigint이며 JSON에는 십진 문자열이다. 비교표의 두 seed 평균은 확률적 기대 수익 또는 신뢰구간이 아니다.

- IOC 완료율의 분모는 **유효한 형태의 합성 인간 IOC 시도**다. 실제 shared 종료 상태 `filled`를 분자로 센다. 마감·자기 거래·자산 부족 거절도 분모에 포함하고, 0 Coin/0수량으로 주문 자체를 만들 수 없는 입력은 분모 밖의 `below_one_contract_input`으로 따로 센다. 예산이 양수여도 다음 1계약을 못 사는 무체결은 유효 시도이며 버리지 않는다. 실제 서비스의 저장 주문 기준 운영 지표와 구분한다.
- 봇 체결률은 체결 계약 수/게시 계약 수다. 재게시하면 새 게시 물량으로 센다. 분모가 0이면 0%로 만들지 않는다. 취소가 잦으면 체결률 해석이 바뀔 수 있어 취소·refresh 수를 함께 보존한다.
- 공급 공백은 `bookDepth`가 실제 위험 순회로 계산한 실행 가능 물량을 쓴다. MM 양 방향 bid 중 하나가 없는 시간과 전체 호가 양 방향 ask 중 하나가 없는 시간을 따로 기록한다. OPEN 시장·시간만 분모이며 PAUSED 시간은 별도다. spread는 양쪽 호가가 있는 구간만 시간 가중하며 없는 구간은 0 spread로 넣지 않는다.
- 단일 주문의 **곡선 기준값 변화**와 **실제 체결가격의 범위**를 구분한다. 전자는 소수 Coin이고 후자는 정수 틱이다. 실제 시장의 마지막 체결가격 변동률이나 슬리피지 예측이 아니다.
- C8의 S=500에서는 1%=5, 10%=50이 초기 ask보다 작아 대표 balanced 조건 세 곳 모두 체결 0이었다. 공백 0%라도 충분한 거래가 된다는 뜻이 아니다. C1~C5도 S 전액을 20분할하면 1회 50 Coin이라 해당 큰손 경로가 무체결이었다. 분할을 유리한 결과만 남기거나 최소 1계약으로 올리지 않았다.
- C7은 S만 C3보다 커서 수량·완료·재고 편중을 함께 키운다. 100명/5시장 balanced에서 MM 공백 11.52%, 큰손 20분할에서 84.88%가 관측됐다. 단일 큰 주문을 가격 보호로 잘랐다는 사실만으로 분할 경로의 누적 수요가 해결되는 것은 아니다. L은 계속 지켰다.
- 100명/5시장 C3의 stale 경로에서 갱신 0ms는 평균 185계약과 공백 99.75%, 250ms는 100계약과 공백 0.06%였다. 빠른 공급이 더 많은 일방향 체결을 허용한 뒤 위험 단계에 도달해 긴 공백을 만들었다. 낮은 공백만 보고 느린 갱신을 추천하거나, 높은 체결량만 보고 빠른 갱신을 추천하지 않는다.
- MM 이익은 사용자 손실과 반대다. VOID에서도 spread로 이익이 날 수 있으며, 양수 MM 손익을 사용자 만족·확률 정확도·경제 건전성의 점수로 취급하지 않는다. 두 seed, 고정 주문 비율, 7분의 짧은 horizon으로 실제 행동 분포를 대표한다고 주장하지 않는다.

재검토 지표는 작은 예산의 무체결 비중, 실제 보호가격 제한 빈도와 체결가격 폭, OPEN 공급 공백·단계 체류시간, 사람간 거래 비중·독립 참여·양방향 수요, 전체 시장별 최악 손실 합, 금고 초기 배정·잔액과 실제 회수, 주문 취소·재게시 빈도다. 문턱은 만들지 않는다. #133 최종 값, #74 재지급, 유료 유입·비영 수수료, 실제 주문/갱신 지연 분포, 시장 규모 또는 공유 매칭·위험·정산 규칙이 바뀌면 같은 모형을 새 입력으로 실행하고 #131 실제 서비스 검사도 별도로 실행한다.

대표 약점의 [trace 목록과 재생 digest](examples/index.json)도 보존했다. C8 무체결, C7 20분할 후 공백, C3 즉시 갱신 뒤 공백의 세 경로이며 불변식 실패 사례가 아니다.

## 재현

저장소 루트, Node 24·lockfile의 pnpm 11.10.0을 사용한다. DB·Redis·브라우저·환경 비밀이 필요 없다. 결과 디렉터리에는 `manifest.json`이 없어야 하며 기존 결과는 덮어쓰지 않는다.

```sh
pnpm install --offline --frozen-lockfile
pnpm --filter @buddha/shared build
pnpm exec tsc -p scripts/economic-simulation/tsconfig.json
node --test scripts/economic-simulation/model.test.ts
(cd scripts/economic-simulation && ../../packages/shared/node_modules/.bin/eslint .)
node scripts/economic-simulation/run.ts --out /tmp/buddha-economy-71-new
node scripts/economic-simulation/report.mjs /tmp/buddha-economy-71-new
```

단일 사례는 같은 네 좌표를 지정한다. `--trace`는 입력 tape와 모든 주문·체결·취소·소각을 gzip으로 남긴다. 원행의 `inputDigest`·`traceDigest`와 일치하면 같은 경제 경로다. 입력 생성 소스·seed·후보·전체 결과는 저장하되 2016개 전체의 거대한 trace는 중복 저장하지 않는다. 불변식 오류가 있으면 그 경로의 입력과 전체 trace를 `counterexamples/`에 자동 저장하고 나머지 경로도 실행한 뒤 종료 코드 1을 돌려준다. 모든 정상 결과도 계속 남긴다.

`results/manifest.json`은 실행 시작 HEAD, Node, 입력, 실행에 사용한 스크립트·shared source/dist·lockfile 해시, 전후 동일 여부, 결과 파일 해시를 기록한다. 재적층 뒤에는 그 shared 파일 해시를 대조해야 하며 HEAD가 바뀌었다는 이유만으로 같은 실행을 새 코드의 검증이라고 부르지 않는다. `report.mjs`는 원 결과 해시를 확인한 뒤 표시용 집계만 만들며 경제 모형에 입력되지 않는다.
