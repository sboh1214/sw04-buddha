# 미해결 질문 / 가정

PLAN §0.1-2에 따라, 문서에 없거나 애매한 사항을 여기에 기록한다.

- **질문**: 사용자 확인이 필요한 항목. 블로킹이면 작업을 멈추고 직접 묻는다.
- **가정**: 진행에 영향이 없어 가장 보수적인 선택으로 진행한 항목. 사용자가 다른 답을 주면 수정한다.

상태: `열림` / `답변됨(날짜)` / `해결` / `철회`

- `열림`은 **가정 행의 기본 상태**다. 반대 지시가 없는 한 그대로 진행한다는 뜻이지 미결이라는 뜻이 아니다 — 대부분의 `A-*` 행은 구현되어 리뷰를 거쳐 출하됐다.
- 오너의 답이 실제로 필요한 항목은 M6이 문서 끝의 **「정리 (M6) — 오너 확인 요청 목록」** 한 곳에 모았다(PLAN M6 AC 4). 이 파일을 처음 읽는다면 거기서 시작하면 된다.

| Q-M6-2 | 열림 | **운영의 `TRUST_PROXY`와 앞단 프록시.** 주소별 한도(§7.5의 기본 100req/분/IP)는 API가 진짜 클라이언트 주소를 볼 때만 의미가 있다. 이 배포에서는 볼 수 없다 — Next의 rewrite는 서버 사이드 프록시이고, Next가 채우는 `X-Forwarded-For`는 `클라이언트가 보낸 값 ?? 소켓 주소`라 신뢰할 수 없다(ADR-0034). 조건은 **앞단에 실제 리버스 프록시를 두고 그것이 `X-Forwarded-For`를 덮어쓰게 한 뒤 `TRUST_PROXY`에 그 CIDR을 넣는 것**이다. 배포 마일스톤에서 ALB로 갈 것인지, 그때의 CIDR을 무엇으로 둘지 확인 요청. 그전까지 주소별 한도는 직접 연결(소켓 핸드셰이크·모바일)에만 걸린다.                                                                                                                                                                                                 |
| Q-M6-3 | 열림 | **웹 CSP의 nonce.** `script-src`에 `'unsafe-inline'`이 남아 있다. App Router가 flight 페이로드와 부트스트랩 스크립트를 HTML에 인라인하고 그것을 끄는 설정이 없기 때문이다(ADR-0036). 제대로 하려면 요청마다 nonce를 발급하는 proxy와, 그것을 싣는 모든 인라인 태그가 필요하다 — 회귀 표면이 실제로 있는 변경이라 절반만 해 두지 않았다. 지금 CSP도 "이 오리진 밖의 스크립트 로드"는 막는다. 착수 여부 확인 요청.                                                                                                                                                                                                                                                                                                                                                                    |
| Q-M6-4 | 열림 | **가입 남용의 나머지 절반**(A-M2-10). 주소별 5req/분이 사서함 폭주와 비밀번호 추측 루프는 막지만, **서로 다른 주소로 계정을 여러 개 만드는 것**은 막지 못한다 — 가입 보너스 10,000P가 그 유인이다. 남은 선택지는 (가) 보너스를 첫 충전 이후로 미루기, (나) 도메인·플러스주소 정규화로 중복 탐지, (다) 그대로 두기. MVP는 (다)로 두었다. 확인 요청.                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Q-M6-5 | 열림 | **관리자 읽기를 감사할지.** `admin_actions`는 PLAN §6.2/§12대로 **행위 로그**이고, 읽기 전용 관리자 GET 8개는 아무 행도 쓰지 않는다(`admin-audit.test.ts`가 그 상태를 고정한다). `GET /admin/users`는 모든 계정의 이메일을 답하므로 접근 기록을 원할 수 있다. 원한다면 새 `ADMIN_ACTION_TYPES` 값과 목록 라우트의 쓰기 증폭에 대한 판단이 함께 필요하다. 확인 요청.                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Q-M6-6 | 열림 | **부하 테스트(k6).** PLAN §14는 `/trades` 동시 50, `/markets` 200rps를 **선택**으로 둔다. 저장소에는 부하 도구가 전혀 없고, M6은 대신 홈 API를 직접 재서 AC 2를 만족시켰다(워밍업 후 200회, p95 15.5ms). k6를 도입할지, 도입한다면 CI에 넣을지 확인 요청.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Q-M6-7 | 열림 | **`/admin/users`의 희귀 검색어.** M6이 더한 `profiles(created_at DESC, user_id DESC)` 인덱스는 기본 목록(4,193ms → 0.22ms)과 흔한 검색어(4,535ms → 1.06ms)를 극적으로 고치지만, **200만 행에서 10건만 맞히는 희귀 검색어는 3.6초에서 10.0초로 느려진다**(버퍼 181배). 플래너가 `LIMIT 21`을 정렬된 인덱스로 금방 채울 것이라 오판하고 200만 항목을 걷는다. 커서와 무관하고(실패하는 것은 커서 없는 첫 페이지다) 행 비교로 고쳐지지 않으며, `enable_seqscan=off`로 강제해도 같은 계획이라 통계로 되돌릴 여지도 없다. 그 분기는 인덱스가 없어도 이미 3.6초라 못 쓴다. 진짜 해법은 `email`·`nickname`의 trigram 인덱스(`pg_trgm`)이거나 검색 분기에서 정렬된 `LIMIT`을 빼는 것이다. 1만·20만 행에서는 회귀가 전혀 없으므로 MVP 규모에서는 급하지 않다. 착수 여부 확인 요청. (ADR-0039) |

| A-M6-1 | 열림 | **주소를 지목할 수 없으면 주소별 한도를 세지 않는다.** 루프백 피어는 개발자 자신의 스택이거나 같은 호스트의 rewrite이고, 둘 다 방문자를 가리키지 않는다. 세면 전 사용자와 모든 SSR이 한 버킷을 나눠 쓰고 학대자가 아니라 제품이 제한된다(ADR-0034). 계정·수신자별 한도는 이 문제와 무관하게 rewrite 뒤에서도 동작한다.                                                                                                                                                                                     |
| A-M6-2 | 열림 | **`apps/web/src/proxy.ts`의 matcher는 넓히지 않는다.** A-M3-24가 M6의 판단으로 넘긴 항목이다. 넓혀도 얻는 것이 없다 — Next의 `??=`가 이미 클라이언트가 보낸 `X-Forwarded-For`를 통과시킨 뒤라 proxy가 진짜 주소를 알 방법이 없고, SSR(`api.server.ts`)은 rewrite를 지나지도 않는다. A-M3-24와 `proxy.ts` 주석이 이 검토를 "ADR-0022"로 지목한 것은 **오기**였다(ADR-0022는 통합 테스트 인프라) — ADR-0034가 그 자리다.                                                                                     |
| A-M6-3 | 열림 | **소켓의 메시지 빈도는 Redis가 아니라 소켓 자신이 센다**(A-M4-5의 답). 연결은 한 프로세스에 살아 있으므로 자기 메시지 속도는 공유 상태가 아니고, PLAN §16이 말하는 것이 아니다. socket.io 패킷 미들웨어로 달아 **파이프보다 먼저** 세므로 잘못된 페이로드도 계산에 들어간다 — A-M4-5가 걱정한 것이 정확히 그 부류다. **IP당 연결 수 제한은 만들지 않았다**: 핸드셰이크 거절 경로는 PLAN 7 봉투를 실을 수 없고(engine.io가 자기 오류를 답한다), Origin 검사와 방 200개 상한이 이미 피해를 묶는다.           |
| A-M6-4 | 열림 | **5xx 본문은 무엇이 던졌든 자기 메시지를 싣지 않는다.** ADR-0020이 정한 규칙인데 실제로는 예상 밖의 `Error`에만 적용되고 있었다 — `AppError('INTERNAL', { message })`를 서른여섯 곳에서 던지고 그 문장이 그대로 나갔다(`'Ledger insert failed'` 등). 이제 `details`까지 함께 봉인하고 원문은 그 요청의 로그 줄에 `hidden`으로 남는다(ADR-0035).                                                                                                                                                            |
| A-M6-5 | 열림 | **키셋 커서 술어를 전부 행 비교로 바꿨다.** `a < $1 OR (a = $1 AND b < $2)`는 Postgres가 Index Cond로 만들 수 없어 Filter로 붙고, 깊은 페이지가 커서 깊이에 비례한다. `(a, b) < ($1, $2)`는 인덱스에 밀어 넣을 수 있다. M2·M3 리뷰가 "인덱스만 넣으라"는 지적을 네 번 반려하며 **인덱스와 이 술어는 한 변경**이라고 못박은 항목이다(A-M3-10). `/admin/users`의 타이브레이크는 `user.id`에서 `profiles.user_id`로 옮겼다 — 값은 같고(FK), 행 비교가 인덱스 조건이 되려면 두 반쪽이 한 테이블에서 와야 한다. |
| A-M6-6 | 열림 | **`price_ticks(trigger='resolve')`는 선언만 되어 있고 아무도 쓰지 않는다.** enum 값은 M1부터 있고 시드·API·워커는 `'trade'`와 `'open'`만 쓴다. M6에서 지우지 않았다 — 지우려면 pg enum 마이그레이션이 필요하고, Q-M5-4가 이미 "정산 시 확률 100%/0% 틱을 쓸지"를 오너 질문으로 들고 있어 답이 곧 이 값을 쓰게 만들 수 있다. 그때까지 **예약된 값**으로 문서화한다.                                                                                                                                         |
| A-M6-7 | 열림 | **시드 시장의 만료를 미리 알린다.** 기존 경고는 마감이 **이미 지난** 뒤에만 나와서, 그 주에 저장소를 클론한 개발자는 닫힌 시장만 있는 홈 화면과 아무 설명도 없이 마주쳤다. 14일 전부터 같은 신호를 낸다(`db:seed`의 stderr). 시드 문구 자체를 새로 쓰는 것은 Q-M3-4(오너의 카피 갱신 주기)이지 이 마일스톤의 결정이 아니다.                                                                                                                                                                                |
| A-M6-8 | 열림 | **`admin_actions`의 `created_at`이 두 종류다.** 시장·잔고·이의의 여덟 삽입은 잠금 뒤 `clockTimestamp`를 명시하고, `charge_package_*`·`coupon_*`의 다섯은 컬럼 기본값(트랜잭션 시작 시각)을 쓴다. 지금은 무해하다 — 그 테이블에는 순서 계약이 없다. `admin_actions`를 `(created_at, id)` 키셋으로 목록화하는 날 물리므로 그날의 항목으로 남긴다.                                                                                                                                                            |
| A-M6-9 | 열림 | **`docs/API.md`는 손으로 고치지 않는다.** `scripts/generate-api-doc.mjs`가 `apps/api/openapi.json`에서 만들고 CI가 `git diff --exit-code`로 강제한다(ADR-0037). 오퍼레이션 설명은 컨트롤러의 `@ApiOperation`, 그 밖의 산문은 생성기의 템플릿 상수가 자리다. prettier는 이 파일을 무시한다(표 재정렬 규칙이 생성기와 어긋난다).                                                                                                                                                                             |
