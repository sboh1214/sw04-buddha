# 01 경제 시스템 · Economy System

설계안 v0.2 · 2026-10-04 · 거래 중심 개편

### 1. 제품 방향과 범위

Buddha는 가상 Coin으로 YES/NO 계약을 매수·매도하는 호가창 기반 예측시장이다. 별도 확률 입력, My Forecast, Community Forecast는 제공하지 않는다. 스코어링은 미정이며 거래·정산의 선행 조건으로 두지 않는다.

초기안은 CLOB(가격·시간 우선 주문 체결) + 운영 마켓메이커다. LMSR는 봇의 호가를 계산하는 곡선으로 활용한다. 모든 사용자가 직접 AMM하고만 거래하던 이전 설계와 구분한다.

이 문서는 구현을 위한 정책 제안이다. 숫자 시뮬레이션과 운영 승인을 마친 상태는 아니다.

### 2. 코인 발행·재지급

- 인증된 참여자에게 동일한 시작 코인을 1회 지급한다. 지급 이벤트 ID로 중복 수령을 막는다.
- 코인 소진 사용자는 제한적 재지급을 신청할 수 있다. 지급 주기·대기기간·횟수·누적 상한을 설정한다.
- 가용 잔액만 보지 않고 주문 잠금액과 보유 계약을 확인한다. MVP는 미정산 계약이나 대기 주문이 있으면 재지급을 보류하여 불확실한 평가가격을 이용한 지원금 수령을 막는다.
- 출석·거래량·주문 횟수 보상, 사용자 직접 송금은 초기 제외한다. 폐쇄 테스트 거래 수수료는 0으로 제안한다.
- 현금 구매는 향후 계획이며 초기 제외한다. 별도 06 유료 코인 판매 · 도입 전 검토사항에서 검토한다. 현금 환전·출금은 제공하지 않는 방향이다.
- 거래 손실은 상대방 또는 봇으로의 이전이며 자동 소각이 아니다. 신규 발행, 운영금 이전, 담보 잠금, 수수료 회수, 실제 소각을 별도 원장 유형으로 기록한다.

### 3. 계약과 완전 담보

기본 계약 단위는 정수 1계약, 정상 결과의 지급액은 100 Coin, 거래 가격 단위는 1 Coin으로 제안한다. 거래 가격은 1–99 Coin 범위다.

100 Coin을 별도 담보 계정에 잠그면 YES 1개와 NO 1개가 생성된다. 미정산 YES·NO 총발행량은 동일하며 담보는 쌍당 100 Coin이다. 정상 판정에서는 승리 계약에 100, 패배 계약에 0을 지급한다.

기존 계약 거래는 코인과 계약의 소유권 이전이다. 기존 정산 담보는 변하지 않는다. 봇은 초기 예산 일부로 계약 쌍을 준비하고 나머지는 매수용 코인으로 보유한다.

같은 소유자가 보유한 잠기지 않은 YES·NO 한 쌍을 소각하면 담보 100 Coin을 돌려받을 수 있다. 초기에는 운영 봇의 자산 관리에 사용하고 사용자용 쌍 변환 UI는 제외한다.

레버리지·대출·무담보 공매도는 제공하지 않는다. 매도 주문은 보유 계약만 사용한다.

### 4. 체결과 자금 이동

- 동일 계약 매수·매도는 좋은 가격을 먼저, 같은 가격에서는 먼저 들어온 주문을 먼저 체결한다. 체결 가격은 대기 중인 주문의 가격이다.
- 반대 결과의 매수 주문도 완전 담보 조건으로 매칭할 수 있다. 예: NO 매수 40이 대기 중이면 들어온 YES 매수 한도 65는 YES 60 / NO 40으로 한 쌍을 발행한다. 초과 한도 5는 돌려주며 운영자가 가져가지 않는다.
- 직접 매도 호가와 반대 결과의 매수 호가를 환산한 공급 중 유리한 가격·원주문 도착 순서로 선택한다. 동일 원주문을 양쪽 화면에 노출해도 유동성을 중복 계산하지 않는다.
- 서로 다른 소유자의 YES·NO 매도 주문을 합쳐 소각하는 교차 매도 경로는 MVP에서 제외한다. 계약을 보유한 매도자와 같은 계약의 구매자가 체결되는 경로는 지원한다.
- 매수 주문은 한도가격×수량을 잠그고, 매도 주문은 수량을 잠근다. 더 좋은 가격으로 체결된 차액과 취소된 미체결 부분은 해제한다.
- 주문 취소와 체결은 서버 순서로 처리한다. 취소 요청 전송만으로 취소가 완료된 것은 아니다.
- 자기 주문끼리 체결하려는 경우 들어온 주문의 남은 부분을 취소한다. 봇 계정 간 자전거래도 금지한다.

### 5. 마켓메이커 운영 단위

공통 시스템 하나가 시장별 독립 전략을 운영한다. 각 전략이 YES·NO 양쪽과 여러 가격대를 관리하므로 가상 사용자 여러 명을 만들 필요가 없다.

시장별 배정 자금·재고·손익·대기 주문 위험을 독립 관리하고 전체 위험도 합산한다. 관련 시장 간 위험 상쇄를 전제로 예산을 늘리지 않는다.

일반 주문과 같은 규칙으로 체결하며 상대 계정은 익명으로 표시한다. 봇을 실제 사람처럼 꾸미지 않는다. 가격 조정 과정을 화면에 매번 설명하지 않되 서비스 안내에는 운영 유동성의 참여 가능성을 명시한다. 봇은 사용자 참여자 수에서 제외한다.

### 6. LMSR 기반 호가 정책

초기 기준은 50%와 균형 재고다. 50%는 실제 확률에 대한 판단이 아니라 개장 설정이며, 거래 전에는 체결가를 만들어 표시하지 않는다.

qY·qN은 봇이 각 계약을 순매도한 누적 수량(매도−재매수)이다. 사용자끼리의 거래와 동일 수량의 쌍 생성·소각은 qY−qN을 바꾸지 않는다.

가격 비율 pY = 1 / (1 + exp(−(qY−qN)/b)), pN = 1−pY. b가 크면 같은 주문에서 가격이 덜 움직인다. 100×pY는 곡선의 기준가격이며 실제 매수·매도 호가는 물량과 간격을 반영한다.

비용 함수 C(qY,qN) = 100×b×ln(exp(qY/b)+exp(qN/b))를 사용한다. YES를 x개 파는 구간의 평균 기준가격은 [C(qY+x,qN)−C(qY,qN)]/x, x개 사들이는 구간은 [C(qY,qN)−C(qY−x,qN)]/x다. NO도 대칭 적용한다. 수치 계산은 안정적인 log-sum-exp를 사용한다.

곡선을 여러 호가로 옮길 때 구간 평균을 단순한 고정 단가로 쓰면 부분 체결에서 과소 청구할 수 있다. 초기 참조 구현은 계약 1개씩의 비용 차이를 계산한 뒤 매도는 위로, 매수는 아래로 가격 단위에 맞춰 반올림하고 안전 간격을 더한다. 같은 가격의 단위를 묶어 호가로 표시한다.

YES 판매가 늘면 YES 기준가격이 오르고 추가 판매 위험이 커진다. 반대 거래는 재고 불균형을 줄인다. 별도의 비례 재고 가격 조정을 중복 적용하지 않는다.

b와 개장 기준은 시장 도중 임의 변경하지 않는다. 체결 시 기존 주문의 잔량·위험 예약을 반영하여 호가를 갱신한다. 취소 완료 전 주문을 새 주문으로 중복 간주하지 않는다.

표준 직접 LMSR의 100×b×ln(2) 손실 상한은 참고값일 뿐 이 호가봇의 보장이 아니다. 여러 방향 동시 체결·갱신 지연·가격 단위·부분 체결을 별도로 검증한다.

### 7. 예산과 손실 한도

각 시장에 배정 예산 A와 최대 손실 L을 따로 설정한다. 예산 일부는 쌍 담보, 나머지는 매수 자금이다. 전체 금고에는 시장별 배정분 외에 검토 후 사용할 추가 지원분을 남긴다.

결과별 회수액은 해당 봇의 코인(주문 잠금 포함) + 해당 결과의 계약 지급액이다. 계약 지급액에 담보를 다시 더하지 않는다.

순손익 = 회수액 + 이미 금고로 회수한 자금 − 누적 투입 자금. 최악 손실 = max(0, −YES 손익, −NO 손익, −VOID 손익). 50/50 VOID의 회수액도 계산한다.

대기 주문의 불리한 체결 조합까지 포함하여 위험을 예약한다. 한쪽 매수와 다른 쪽 매도가 모두 체결되어 상쇄될 것이라고 가정하지 않는다. 새 주문 및 각 체결은 원자적으로 가용 자산·위험 한도를 검사한다.

초기 시험 정책:

- L 사용률 70% 미만: 기본 물량.
- 70% 이상~90% 미만: 위험을 늘리는 물량을 기본의 절반 이하로 축소.
- 90% 이상: 위험 증가 주문 취소·중단. 위험 감소 거래도 자산·결과별 한도를 만족할 때만 허용.
- 어떤 상태든 L을 넘길 수 있는 주문은 등록·체결 차단.

70%·90%는 검증 전 실험값이다. 손실은 없어지는 것이 아니라 제한된다. 마감 후 결과별 정산 담보는 언제나 보존한다.

### 8. 대량 주문·분할 주문

사용자는 여러 가격대의 호가를 순서대로 체결한다. 같은 가격에 무한 공급하지 않는다. 즉시 거래는 가격 보호가 있는 IOC 주문으로 제공하고, 한도 밖 잔량은 취소한다. 지정가 GTC의 미체결 잔량은 주문장에 남긴다.

체결 전 예상 수량·평균가·최대 지출 또는 최소 단가를 안내한다. 주문 입력 예산 전체가 반드시 사용되는 것은 아니다.

봇의 재고·손실 한도는 주문을 쪼개도 누적으로 적용된다. 사용자별 주문 속도 제한은 부하·스팸 통제용이며 경제적 위험 한도를 대신하지 않는다. 다계정·공모·비정상 반복 거래는 감시하되 동일 IP만으로 단정하지 않는다.

봇 공급 부족은 사용자끼리의 거래 중단을 뜻하지 않는다. 봇 정지와 시장 전체 거래 정지는 별도 상태다.

### 9. 원장·장애·운영자 통제

발행·지원·담보·거래·수수료·정산·보상은 변경 불가능한 이벤트로 기록한다. 요청 ID·주문 ID·체결 ID·정산 버전으로 중복을 막는다. 같은 지갑의 여러 시장 주문도 자산을 이중 사용하지 못한다.

관리자는 시장별 재고·결과별 손익·예약 위험·호가 깊이·체결률·공급 중단 시간·상위 보유 집중도를 본다. 예산 추가, 중단·재개, 설정 변경은 사유·작업자·전후 값과 함께 기록한다.

가격을 수동으로 원래 값에 복원하거나 손실을 초기화하지 않는다. 장부 불일치 시 해당 거래를 중단하고 원장 대사 후 복구한다. 잔액 직접 덮어쓰기는 금지한다.

### 10. 출시 검증과 수치 결정

필수 검증: 담보=미정산 쌍 수×100, 코인 이동 보존, 음수 가용 잔액 없음, 동일 주문 재시도 단일 처리, 동시 체결 위험 상한, 마감 후 체결 없음, 정산 재시도 중복 지급 없음.

시나리오: 양방향 소액, 일방향 연속 매수, 큰손·분할 주문, 뉴스 직후 주문, 오래된 호가, 사용자간 거래, 자기 거래, YES/NO/VOID 정산.

초기 지급액·재지급 주기·A·L·b·호가 단계·기본 물량·안전 간격·가격 보호 폭은 시뮬레이션 후 출시 설정으로 확정한다. 현재 문서에서 특정 수치를 검증 완료라고 주장하지 않는다.

이전 직접 AMM 예시와 2,000회 수학 검증은 이번 호가 엔진의 검증 결과가 아니다.

### 11. 확장과 연결

초기에는 소수 시장에 집중한다. 독립 사용자·양방향 거래·실제 수요를 확인한 뒤 예산을 늘린다. 사용자 호가가 충분하면 봇 비중을 줄인다. 시장가격 추종 전략은 추후 별도 검증하며, 현재는 마지막 체결가 한 건을 자동 추종하지 않는다.
