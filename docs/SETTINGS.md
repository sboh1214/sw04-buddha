# 출시 설정 등록 규칙

시뮬레이션이나 운영 승인으로 정할 값('출시 설정')을 한곳에 두고, 서버가 그곳에서 읽게 하는 규칙이다(#170). 결정과 근거는 [ADR-0055](DECISIONS.md)에 있다. 기획 인용 표기(NR, N00\~N06 §n)는 ADR-0047을 따른다. 뒤 이슈는 이 문서대로 자기 항목을 등록한다.

- 기획: 초기 지급액·재지급 주기·b·호가 단계·가격 보호 폭 등은 "시뮬레이션 후 출시 설정으로 확정한다"(N01 §10). 문서의 수치를 검증 완료라고 주장하지 않는다(N01 §10). 설정 변경은 사유·작업자·전후 값과 함께 기록한다(N01 §9).
- 오너 결정(2026-10-13, #170): 운영 중에 관리자 화면에서 바꾸고 변경마다 기록한다(값은 DB). 출시 값이 정해지기 전에는 시험용 값을 두고 출시 값과 구분해 표시한다. 바꾼 값은 바꾼 뒤 시작하는 일에만 적용한다.
- 오너 결정(2026-10-13\~14, #170 구현 중 답): 지금 상태·값과 똑같은 변경은 거절한다. 값은 관리자 화면으로만 넣고 마이그레이션·시드는 값을 쓰지 않는다(개발 환경을 만들거나 재초기화한 뒤에는 모든 항목이 미정). 서버는 상태만 알려 주고 승인되지 않은 항목은 #149 출시 점검이 모두 확인한다(배포 등급 설정은 두지 않는다). 출시 전 재초기화 때 값과 변경 기록을 남길지는 #133이 정하고, 지금은 함께 지운다.

## 구조

| 무엇                                 | 어디                                                                                   | 누가 바꾸나                                                                    |
| ------------------------------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 항목 정의(키·이름·단위·뜻·값의 모양) | 코드. `packages/shared/src/release-settings.ts`의 `RELEASE_SETTINGS`(`@buddha/shared`) | 항목을 등록하는 이슈의 PR                                                      |
| 값과 상태                            | DB. `release_settings` 표(키마다 한 행, 행이 없으면 미정)                              | 관리자. `/admin/settings` 화면이나 `PATCH /api/v1/admin/release-settings/:key` |
| 변경 기록                            | DB. `admin_actions`의 `release_setting_change` 행(전후 상태·값, 사유, 작업자, 시각)    | 값을 바꿀 때 같은 트랜잭션에서 저절로 남는다                                   |

- 레지스트리의 항목은 지금 #70의 시작 지급액(`grant.start_coin`, ADR-0071) 하나다. #170은 장치만 만들었고, 실제 항목은 아래 '예상 항목'의 담당 이슈가 등록한다. 출시 레지스트리의 항목 목록을 고정한 곳(아래 '항목 등록하기' 4의 네 곳)은 항목을 등록하는 이슈가 모두 고친다.
- 서버는 등록된 항목을 이 레지스트리와 `release_settings`에서만 읽는다. 같은 값을 코드 여러 곳에 따로 적지 않는다. 지금 상수로 있는 값을 항목으로 옮기는 이슈는 옛 상수를 지운다. 예를 들어 #70은 시작 지급액을 항목으로 등록하면서 옛 두 곳 — `SIGNUP_BONUS_COIN`(`packages/shared/src/constants.ts`)과 가입 트리거 `create_profile_for_user()`의 10,000(마이그레이션 0019) — 을 지웠다(마이그레이션 0031, ADR-0071).

## 항목 등록하기

1. `packages/shared/src/release-settings.ts`에 `defineReleaseSetting({ key, label, unit, description, schema })`로 정의를 상수로 두고, `RELEASE_SETTINGS`의 목록에 넣는다. 목록의 순서가 관리자 화면의 순서다.
2. 값을 쓰는 서버 코드는 그 정의 객체로 읽는다(아래 '값 읽기').
3. 마이그레이션과 시드는 값을 쓰지 않는다(오너 결정 2026-10-13\~14). 값은 관리자가 화면에서 사유와 함께 넣는다. 그래서 새 항목은 미정으로 시작하고, 개발 환경을 새로 만들거나 DB를 재초기화한 뒤에도 모든 항목이 미정이다. 기획의 설계 제안 값(예: 이의 기간 24시간)도 같다. 관리자가 상태 '설계 제안'으로 넣고 사유에 근거를 적는다. 시드가 값을 쓰지 않음은 `packages/db/src/seed.test.ts`가 고정한다.
4. 시험: API 시험은 `createTestApp({ releaseSettings: defineReleaseSettings([...]) })`로 시험용 항목을 주입한다(`apps/api/src/release-settings/release-settings.controller.test.ts`가 예다). 출시 레지스트리의 항목 목록은 아래 네 곳이 고정한다. 항목을 등록하는 이슈는 네 곳을 모두 고쳐 등록한 항목을 더한다. 하나라도 빠지면 시험이 실패하거나 README가 틀린다.
   - shared: `packages/shared/src/release-settings.test.ts`의 `ships the items the issues that use them registered`(출시 레지스트리의 키 목록).
   - API: `apps/api/src/release-settings/release-settings.controller.test.ts`의 `the shipped registry (integration)`(주입 없이 뜬 앱의 관리자 목록과 그 항목의 값 규칙).
   - e2e: `apps/web/e2e/release-settings.spec.ts`의 첫 시험(관리자 API의 목록, 화면의 항목 줄과 '전체 N개 · 미정 N개', 변경 버튼의 수). 이 시험은 값을 바꾸지 않는다. 시작 지급액처럼 값을 넣으면 곧바로 일이 생기는 항목이 있고, e2e DB에 넣은 값은 다음 실행까지 남는다.
   - README: 화면 표의 `/admin/settings` 줄('등록된 항목은 …').

**필드.**

| 필드          | 뜻                                                                                 | 규칙                                                                                                                                                                                                                                       |
| ------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `key`         | 저장 키. `release_settings.key`와 변경 기록의 `admin_actions.target_id`에 남는다   | 소문자 낱말을 `_`로 잇고 `.`로 묶는다(`grant.initial_coin`), 64자 이하, 중복 금지. **한 번 배포한 키는 이름을 바꾸지 않는다.** 바꾸면 저장된 값과 기록이 옛 키에 남는다                                                                    |
| `label`       | 관리자 화면의 이름(한국어, 예: `시작 지급액`)                                      | 비어 있으면 안 된다                                                                                                                                                                                                                        |
| `unit`        | 단위(예: `Coin`, `시간`). 단위가 없는 값(켜고 끔, 목록)은 `null`                   | 빈 문자열 금지. 화면은 값과 단위를 따로 보인다                                                                                                                                                                                             |
| `description` | 이 값이 무엇을 정하는지와 담당 이슈                                                | 비어 있으면 안 된다                                                                                                                                                                                                                        |
| `schema`      | 값의 모양(zod). 관리자가 넣는 값을 검사하고, 읽을 때마다 저장된 값을 다시 검사한다 | 출력이 JSON이어야 한다(bigint 금지, Coin 금액은 정수나 10진 문자열). 자기 출력을 다시 받아야 한다(모양을 바꾸는 transform 금지). `null` 하나만으로 된 값은 '값 없음'이라 쓸 수 없다. 화면은 이 스키마의 JSON Schema를 입력 형식으로 보인다 |

관리자 화면의 값 입력은 스키마의 JSON Schema `type`이 `string`이면 입력한 글자 그대로, 아니면 JSON으로 읽는다(`24`, `true`, `[1, 2]`, `{"from": 1}`). 문자열 항목은 빈 칸과 공백도 그대로(빈 문자열 등) 보내고 받을지는 스키마가 정한다. 빈 값을 받지 않을 항목은 스키마가 거절해야 한다(예: `z.string().min(1)`). 나머지 항목의 빈 입력과 JSON `null`은 값이 아니다. 객체 값의 키 순서는 저장(jsonb)에서 바뀔 수 있다.

정의를 바꿔 저장된 값이 새 스키마에 맞지 않게 되면 서버는 그 값을 읽지 않고 오류를 낸다. 관리자 화면에는 그 값이 그대로 보이니 관리자가 새 값으로 바꾼다.

## 상태

| 상태      | 값   | 뜻                                                                                       |
| --------- | ---- | ---------------------------------------------------------------------------------------- |
| 미정      | 없음 | 값이 아직 정해지지 않았다. 행이 없는 항목도 미정이다                                     |
| 설계 제안 | 있음 | 기획이 설계 제안으로 적은 값(NR 설계 상태). 승인된 값이 아니다                           |
| 시험값    | 있음 | 출시 값이 정해지기 전(#133) 내부 배포에서 기능을 시험할 때 쓰는 값. 출시 값이 아니다     |
| 승인됨    | 있음 | 출시 값으로 승인된 값. 출시 값의 확정과 설계 제안 값의 승인은 #133·#173·#177·#180이 한다 |

- 설계 제안 값과 시험값은 어디서도 승인된 값(확정값)으로 표시하지 않는다(NR 설계 상태, N01 §10). 관리자 화면은 상태 배지로 구분한다. 승인됨만 브랜드 색이고, 설계 제안·시험값은 각자 다른 색, 미정은 눈에 띄는 주황 배지다. 화면 위의 범례가 네 상태의 뜻을 적는다. 배지의 이름과 색, 범례 문구는 #170 구현이 정한 것이다(오너 결정이 아니다, ADR-0055).
- 상태 이름은 `RELEASE_SETTING_STATUS_LABELS`(`@buddha/shared`) 하나다.

## 값 읽기

- **API 서버.** `ReleaseSettingsModule`을 가져와 `ReleaseSettingsService.get(정의, tx?)`로 읽는다. 결과는 `{ status, value }`다. 미정이면 `value`가 `null`이고, 나머지는 정의의 스키마로 타입이 붙은 값이다. 레지스트리에 등록한 바로 그 정의 객체로만 읽을 수 있다(`readReleaseSetting`이 검사한다).
- **상태에 따른 처리.** `get()`은 상태를 함께 돌려줄 뿐 설계 제안·시험값을 거절하지 않는다. 출시 환경에서도 같다. 서버는 상태만 알려 주고, 출시 환경에서 승인되지 않은 값을 막는 배포 등급 설정은 두지 않는다. 승인되지 않은 항목은 #149 출시 점검이 모두 확인한다(오너 결정 2026-10-13\~14, 아래 '출시 점검'). 항목이 미정(값 없음)일 때 그 일을 어떻게 할지(시작하지 않는다, 기능을 끈다 등)는 항목을 등록하는 이슈가 정한다. 시작 지급액은 오너가 정했다: 값이 있으면 상태(설계 제안·시험값·승인됨)와 상관없이 그 값으로 주고, 미정이면 지급을 기다리게 했다가 값이 들어오면 준다(ADR-0069 결정 4 #70·결정 7, ADR-0071).
- **워커.** 워커에는 Nest 주입이 없다. `getReleaseSetting(tx, RELEASE_SETTINGS, 정의)`(`@buddha/db`)로 읽는다. `ReleaseSettingsService.get`이 쓰는 바로 그 함수라 결과와 등록 검사가 같다. 읽을 수 없으면(등록되지 않은 정의, 정의에 맞지 않는 저장 값) 오류를 던지고 그 일은 실패한다.
- **표를 직접 읽지 않는다.** `release_settings`의 값은 `value::text`로 읽어 한 번만 `JSON.parse`해야 한다. drizzle의 jsonb 읽기가 문자열 값을 한 번 더 `JSON.parse`해 `"24"`를 24로 바꾸기 때문이다. 위의 두 길이 그렇게 읽는다. 다른 열과 함께 골라야 하면 값 열 대신 `storedReleaseSettingValue`(`@buddha/db`)를 고른다.
- **웹.** 값을 읽는 API는 관리자 전용이다. 사용자 화면이 값을 보여야 하면 그 항목의 담당 이슈가 경로를 정한다.

## 바꾼 값이 적용되는 때

오너 결정(2026-10-13): 바꾼 값은 **바꾼 뒤 시작하는 일에만** 적용한다. 이미 진행 중인 일(열린 시장, 진행 중인 이의 기간, 접수된 재지급 신청 등)은 시작할 때의 값을 끝까지 쓴다.

- 소비하는 코드는 일을 시작할 때 값을 **한 번** 읽는다. 그 일에 트랜잭션이 있으면 그 안에서 읽는다(`get(정의, tx)`).
- 일이 한 요청보다 오래 가면(기간, 신청, 시장) 읽은 값이나 그 값으로 계산한 결과(예: 이의 마감 시각)를 그 일의 행에 저장하고, 뒤에서는 저장한 것을 쓴다. 나중에 설정을 다시 읽어 진행 중인 일에 적용하지 않는다.
- b와 개장 기준은 시장 도중 바꾸지 않는다(N01 §6). 개장 전에 시장마다 고정하는 유동성 설정 버전(#72)과 규칙 버전(#80)은 출시 설정의 범위 밖이다(#170 제외, N03 §3). N01 §10은 A·L·b·호가 단계·기본 물량·안전 간격도 출시 설정으로 확정한다고 쓴다. #180은 이 여섯 값을 시장마다 입력하고 입력칸을 출시 표준값으로 미리 채우게 했다(ADR-0058). 표준값을 출시 설정 항목으로 둘지는 #72가 정한다. 시장에 고정한 값은 #130의 변경으로만 바뀌고, b와 개장 기준은 바뀌지 않는다.

## 바꾸기와 변경 기록

- **바꿀 수 있는 사람.** 관리자(`profiles.role = admin`, `AdminGuard`). 관리자 권한의 부여·회수는 #171이다. 값 변경에 다른 관리자의 승인이 필요한지는 #133이 정한다. 그 전까지는 관리자 한 명이 사유를 남기고 바꾼다.
- **사유는 필수다.** 1\~500자(`RELEASE_SETTING_REASON_MAX_LENGTH`). 사유가 없으면 거절한다(`VALIDATION_ERROR`). 미정은 값을 받지 않고, 나머지 상태는 정의의 스키마에 맞는 값이 있어야 한다.
- **jsonb가 담지 못하는 글자는 받지 않는다.** 사유와 값은 jsonb(`admin_actions.payload`, `release_settings.value`)에 저장된다. PostgreSQL의 jsonb는 U+0000(NUL)과 짝이 없는 UTF-16 서러게이트를 담지 못해 그대로 쓰면 쓰기가 500으로 실패한다. 그래서 사유(`releaseSettingChangeBodySchema`)와, 스키마를 거친 값의 모든 문자열과 객체 키(`parseReleaseSettingChange`, 스키마가 버린 키는 저장되지 않으니 보지 않는다)에 이 글자가 있으면 아무것도 쓰기 전에 거절한다(`VALIDATION_ERROR`, 경로 `['reason']`·`['value', …]`, 메시지 `JSONB_NUL_MESSAGE`·`JSONB_LONE_SURROGATE_MESSAGE`, 객체 키는 앞에 `key `). NUL 메시지는 API 전역 검증 파이프의 것과 같다. 짝이 맞는 서러게이트(이모지 등)와 NUL 밖의 제어 문자는 jsonb가 담으므로 그대로 받는다.
- **바뀐 것이 없는 변경은 거절한다**(오너 결정 2026-10-13\~14). 상태와 값이 지금과 같으면 `VALIDATION_ERROR`(`details`는 `[{ path: [], message: RELEASE_SETTING_UNCHANGED_MESSAGE }]`)로 거절하고 아무것도 쓰지도 기록하지도 않는다. 값은 JSON 값으로 비교한다(객체 멤버의 순서는 보지 않는다, `isReleaseSettingUnchanged`). 행이 없는 항목은 미정이라 미정으로의 변경도 거절한다. 키 잠금 안에서 비교하므로 다른 관리자가 먼저 같은 변경을 했으면 뒤의 것이 거절된다. 관리자 화면은 상태와 값이 지금과 같은 동안 저장 버튼을 끄고 '바뀐 내용이 없습니다.'를 보이며, 서버가 이 까닭으로 거절하면 같은 문구를 알리고 대화상자를 닫는다.
- **기록.** 변경마다 같은 트랜잭션에서 `admin_actions`에 `release_setting_change` 한 행(대상 `release_setting`/키, payload `{ key, before: { status, value }, after: { status, value }, reason }`, 작업자, 시각)을 남긴다. 그 행 없이 `release_settings`를 쓰면 DB가 커밋 때 거절한다(마이그레이션 0020의 지연 제약 트리거). 기록의 대상과 payload `key`는 모두 쓰는 행의 키여야 하고, payload `after`는 쓰는 상태와 값, payload `before`는 그 쓰기가 바꾼 상태여야 한다. 고치는 쓰기(UPDATE)의 `before`는 이전 행의 상태와 값이고, 행이 없던 키의 첫 쓰기(INSERT)의 `before`는 값이 없는 미정(`{ status: 'undecided', value: null }`)이다. payload `key`는 문자열이어야 하고, payload `reason`은 API의 사유 규칙(`releaseSettingChangeBodySchema`)대로 앞뒤 공백을 뺀 길이가 1\~500자인 문자열이어야 한다(공백은 JavaScript의 `trim`이 지우는 문자, 길이는 zod처럼 코드 포인트로 센다). 변경 기록 목록은 payload의 키와 전후 상태를 보이므로, 기록에 보이는 키와 바뀌기 전 상태가 그 기록으로 쓴 행의 것과 다를 수 없다. 변경 기록 목록은 읽을 수 없는 기록(`releaseSettingChangePayloadSchema`에 맞지 않는 payload)에서 실패하므로, 쓰기에 쓰인 기록은 모두 그 스키마로 읽힌다. 고치는 쓰기는 키를 바꿀 수 없고(키를 바꾸면 지우는 것처럼 원래 키가 미정이 되고 기록이 갈라진다), 변경 시각이 앞으로 가야 해서 앞선 변경의 기록을 다시 대어 옛 상태로 되돌려 쓸 수도 없다. 한 키의 변경 시각은 늘 앞선 변경보다 늦다(시계가 같은 밀리초를 읽으면 앞선 변경의 1ms 뒤). 그래서 기록의 순서가 변경의 순서다. `admin_actions`는 앱 계정이 고치거나 지울 수 없고, `release_settings`의 행도 지울 수 없다. 미정으로 되돌리는 것도 기록이 남는 변경이다.
- **기록을 보는 사람.** 관리자만(N04 §6). 관리자 화면의 '변경 기록'(작업자·시각·전후 값·사유)과 `GET /api/v1/admin/release-settings/changes`(`?key=`로 한 항목만). 관리자가 아닌 계정은 목록·변경·기록 모두 403이다.
- 레지스트리에서 빠진 키의 기록도 남는다. 화면에는 '등록되지 않은 항목'으로 보인다.

## 출시 점검(#149)

- `/admin/settings`에서 '미정만 보기'를 켜면 값이 미정인 항목이 모두 보인다. API로는 `GET /api/v1/admin/release-settings?status=undecided`다. 스위치 옆에 전체와 미정 항목 수가 있다.
- 승인되지 않은 값(설계 제안·시험값)은 목록의 배지로 보이고, API로는 `?status=proposal`·`?status=test`다.
- 출시 점검은 승인되지 않은 항목(미정·설계 제안·시험값)을 **모두** 확인한다. 출시 환경에서 시험값·설계 제안 값을 막는 장치(배포 등급 설정)는 없고 서버는 상태만 알려 주므로, 승인되지 않은 값이 출시에 남지 않게 하는 것은 이 점검이다(오너 결정 2026-10-13\~14).
- 운영 DB 재초기화(`deploy/reset-db.sh`, [docs/RESET.md](RESET.md))는 모든 표를 비우므로 `release_settings`와 변경 기록(`admin_actions`)도 비운다. 시드는 값을 쓰지 않으니 재초기화 뒤에는 모든 항목이 미정이고, 관리자가 사유와 함께 다시 넣는다. 출시 전 재초기화 때 값과 변경 기록을 남길지는 #133(재초기화 범위)이 정한다. 그 전까지는 함께 지운다(오너 결정 2026-10-13\~14).

## 출시 설정이 아닌 것

#170 본문의 '제외'다.

- 시장마다 고정하는 값: 유동성 설정 버전(#72), 규칙 버전(#80). 개장 뒤에는 b와 개장 기준만 고정하고 나머지 봇 설정은 #130이 기록과 함께 바꾼다(ADR-0058).
- 계약당 지급 100 Coin(설계 제안)과 VOID 50/50(설계 제안)을 전역 설정으로 둘지 시장 규칙 값으로 둘지(#177·#173).
- 초기 수수료 0(설계 제안)의 확정(#73, D14).
- 출시 설정 기록 표에 둘 값의 범위(#133).
- 이메일·푸시와 가격 알림의 임계값. 후속 설정이다(N05 §4, #146·#97).

결정 이슈가 코드의 고정값으로 정한 것도 출시 설정이 아니다.

- 닉네임의 변경 간격(30일에 한 번)과 내려놓은 닉네임의 보류(30일): 오너가 정한 고정값이다(ADR-0069 결정 1 #57-6). `@buddha/shared`의 `NICKNAME_CHANGE_INTERVAL_DAYS`·`NICKNAME_HOLD_DAYS`이고, 보류의 30일은 마이그레이션 0032의 `nickname_held()`에도 있다. 화면 문구가 같은 수를 말하는지 시험이 본다(ADR-0072).
- 약관 동의 항목의 판(`CONSENT_DOCUMENTS`, ADR-0072): 출시 설정이 아니라 코드다. 문서를 개정하는 이슈(#137)가 판을 더하고 재동의가 필요한지(`requiresReconsent`)를 정한다.
- 본인확인 인증번호의 자릿수·유효시간(3분)·재발송 간격(60초)·실패 허용(5번)과 직전 24시간의 발송 한도(계정마다 10번, 계정·번호 쌍마다 10번, 한 번호에 계정 3개, 접속 주소(IP)마다 50번, 서비스 전체 500건): 오너가 코드의 고정값으로 정했다(ADR-0069 결정 1 #57-3, ADR-0070의 오너 결정 2026-10-18 — 접속 주소마다의 50번은 2차 답). `@buddha/shared`의 `PHONE_VERIFICATION_LIMITS` 한곳에 있고 화면 문구가 같은 수를 말하는지 시험이 본다(ADR-0070).
- 근거 글(#46, ADR-0073): 제목 100자(오너 결정 2026-10-18), 본문은 서식을 뺀 5,000자, 이미지는 글마다 10장·한 장 5MB(JPEG·PNG·WebP·GIF, 긴 변 2,048px로 줄임), 글자 색 여섯 가지(오너 결정 2026-10-18): 오너가 코드의 고정값으로 정했다(ADR-0069 결정 2 #45-3). `@buddha/shared`의 `POST_TITLE_MAX_LENGTH`·`POST_BODY_MAX_LENGTH`·`POST_IMAGES_MAX`·`IMAGE_MAX_BYTES`·`IMAGE_MAX_DIMENSION`·`POST_TEXT_COLORS`이고, 화면 문구가 같은 수를 말하는지 시험이 본다(`apps/web/src/lib/post-editor.test.ts`). 구현이 고르고 오너가 그대로 두기로 한 값(오너 결정 2026-10-19)도 코드에 있다: 제목 단계 1\~3(`POST_HEADING_LEVELS`), 어느 글도 가져가지 않은 업로드를 지우기까지 24시간(`ORPHAN_MEDIA_HOURS`), 디코딩하는 화소 상한 — 모든 프레임을 더해 5,000만(`IMAGE_MAX_INPUT_PIXELS`), 한 프레임은 형식마다 풀 때 드는 메모리로 128MiB(`apps/api/src/media/image.ts`의 `IMAGE_DECODE_BUDGET_BYTES`와 `decodeBytesPerPixel`: GIF 약 839만 화소, WebP 약 895만, 점진적 JPEG 약 1,342만, 16비트 RGBA PNG 약 2,796만, 인터레이스 RGBA PNG 약 2,097만), 한 번에 하나만 하는 변환과 그 뒤에 기다릴 수 있는 8개(`IMAGE_CONVERSIONS_WAITING_MAX`, 넘으면 `RATE_LIMITED`와 2초 뒤 다시) — 바꾸려면 그 상수와 ADR-0073을 함께 고친다. 프레임마다의 값은 API 컨테이너의 메모리 한도(448MiB, `deploy/compose.yaml`)에서 나왔으니, 그 한도를 바꾸면 함께 다시 본다(ADR-0073 결정 9-8). 이미지 읽기(`GET /api/v1/media/:id`, 304 포함)는 접속 주소마다 분당 100의 기본 한도에서 빠지고 따로 분당 600에 든다(오너 결정 2026-10-19, `@buddha/shared`의 `RATE_LIMIT_BUCKETS.mediaRead`). 이미지 읽기가 한꺼번에 쥐는 바이트는 API 프로세스 전체에서 32MiB다(`apps/api/src/media/image-reads.ts`의 `IMAGE_READ_BUDGET_BYTES`, 넘으면 `RATE_LIMITED`와 1초 뒤 다시 — `IMAGE_READ_BUSY_RETRY_SECONDS`). 구현이 고른 값을 오너가 그대로 두었고(오너 결정 2026-10-20, ADR-0073 결정 9-36), 같은 448MiB에서 나왔으니 그 한도나 변환의 128MiB를 바꾸면 함께 다시 본다. 업로드 본문을 한꺼번에 받는 바이트는 API 프로세스 전체에서 64MiB다(`apps/api/src/media/image-body.ts`의 `IMAGE_UPLOAD_RECEIVING_BYTES` — 오너가 정한 값, 오너 결정 2026-10-21, ADR-0073 결정 9-43). 넘는 업로드는 `RATE_LIMITED`와 2초 뒤 다시다(변환 대기열과 같은 `IMAGE_BUSY_RETRY_SECONDS`, 구현의 선택). 몫은 본문이 오기 전에 밝힌 길이로 잡고, 길이를 밝히지 않은 본문은 파서의 한도 10MiB로 잡는다(`IMAGE_BODY_LIMIT`, 오너 결정 2026-10-21 답 5). 받는 중인 본문이 한 바이트도 보내지 않는 30초면 끊고 몫을 돌려준다(`IMAGE_UPLOAD_IDLE_SECONDS` — 바이트가 오지 않는 시간이지 마감이 아니다), 계정마다 한꺼번에 올리는 중인 업로드는 셋이다(`IMAGE_UPLOADS_PER_ACCOUNT`, 넷째는 같은 429와 2초): 둘 다 오너가 정한 값이다(오너 결정 2026-10-21 답 4, ADR-0073 결정 9-43). 서버 전체의 `requestTimeout`·`connectionTimeout`은 그대로 Fastify 5의 기본 0이고 Caddy에 `read_body`는 없다. 같은 448MiB 안에 변환·읽기와 함께 드니 그 한도를 바꾸면 함께 다시 본다. 온보딩 게이트가 쓰기·수정 화면에서 남은 단계로 보낼 때 그 탭에 두는 쓰던 글은 1시간 뒤 지운다(`apps/web/src/lib/post-drafts.ts`의 `POST_DRAFT_TTL_MS` — 오너의 «잠시»에 구현이 고른 값을 오너가 그대로 두었다, 오너 결정 2026-10-20 3차 답 2, ADR-0073 결정 9-38. 탭을 닫으면 그 전에도 사라진다). 새 업로드의 미리보기는 긴 변 640px로 함께 둔다(`DRAFT_PREVIEW_MAX_SIDE`, 구현의 선택, 9-38). 이미지 읽기가 429로 거절되면 웹은 `Retry-After`(60초까지, 없으면 1초)만큼 기다려 이미지마다 모두 세 번까지 다시 받는다(`apps/web/src/lib/image-retry.ts`의 `IMAGE_RETRY_ATTEMPTS`·`IMAGE_RETRY_MAX_WAIT_MS`·`IMAGE_RETRY_DEFAULT_WAIT_MS`, 구현의 선택, ADR-0073 결정 9-39).
