# 출시 설정 등록 규칙

시뮬레이션이나 운영 승인으로 정할 값('출시 설정')을 한곳에 두고, 서버가 그곳에서 읽게 하는 규칙이다(#170). 결정과 근거는 [ADR-0055](DECISIONS.md)에 있다. 기획 인용 표기(NR, N00\~N06 §n)는 ADR-0047을 따른다. 뒤 이슈는 이 문서대로 자기 항목을 등록한다.

- 기획: 초기 지급액·재지급 주기·b·호가 단계·가격 보호 폭 등은 "시뮬레이션 후 출시 설정으로 확정한다"(N01 §10). 문서의 수치를 검증 완료라고 주장하지 않는다(N01 §10). 설정 변경은 사유·작업자·전후 값과 함께 기록한다(N01 §9).
- 오너 결정(2026-10-13, #170): 운영 중에 관리자 화면에서 바꾸고 변경마다 기록한다(값은 DB). 출시 값이 정해지기 전에는 시험용 값을 두고 출시 값과 구분해 표시한다. 바꾼 값은 바꾼 뒤 시작하는 일에만 적용한다.
- 오너 결정(2026-10-13\~14, #170 구현 중 답): 지금 상태·값과 똑같은 변경은 거절한다. 값은 관리자 화면으로만 넣고 마이그레이션·시드는 값을 쓰지 않는다(개발 환경을 만들거나 재초기화한 뒤에는 모든 항목이 미정). 서버는 상태만 알려 주고 승인되지 않은 항목은 #149 출시 점검이 모두 확인한다(배포 등급 설정은 두지 않는다). 출시 전 재초기화 때 값과 변경 기록을 남길지는 #133이 정하고, 지금은 함께 지운다.

## 구조

| 무엇                                 | 어디                                                                                   | 누가 바꾸나                                                                    |
| ------------------------------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 항목 정의(키·이름·단위·뜻·값의 모양) | 코드. `packages/shared/src/release-settings.ts`의 `RELEASE_SETTINGS`(`@buddha/shared`) | 항목을 등록하는 이슈의 PR                                                      |
| 값과 상태                            | DB. `release_settings` 표(키마다 한 행, 행이 없으면 미정)                              | 관리자. `/admin/settings` 화면이나 `PATCH /api/v1/admin/release-settings/:key` |
| 변경 기록                            | DB. `admin_actions`의 `release_setting_change` 행(전후 상태·값, 사유, 작업자, 시각)    | 값을 바꿀 때 같은 트랜잭션에서 저절로 남는다                                   |

- 레지스트리는 지금 비어 있다. #170은 장치만 만들고, 실제 항목은 아래 '예상 항목'의 담당 이슈가 등록한다. 비어 있음을 고정한 곳(아래 '항목 등록하기' 4의 네 곳)은 첫 항목을 등록하는 이슈가 모두 고친다.
- 서버는 등록된 항목을 이 레지스트리와 `release_settings`에서만 읽는다. 같은 값을 코드 여러 곳에 따로 적지 않는다. 지금 상수로 있는 값을 항목으로 옮기는 이슈는 옛 상수를 지운다. 예를 들어 시작 지급액은 지금 `SIGNUP_BONUS_COIN`(`packages/shared/src/constants.ts`)과 가입 트리거 `create_profile_for_user()`의 `bonus_coin`(마이그레이션 0019) 두 곳에 있다(#70).

## 항목 등록하기

1. `packages/shared/src/release-settings.ts`에 `defineReleaseSetting({ key, label, unit, description, schema })`로 정의를 상수로 두고, `RELEASE_SETTINGS`의 목록에 넣는다. 목록의 순서가 관리자 화면의 순서다.
2. 값을 쓰는 서버 코드는 그 정의 객체로 읽는다(아래 '값 읽기').
3. 마이그레이션과 시드는 값을 쓰지 않는다(오너 결정 2026-10-13\~14). 값은 관리자가 화면에서 사유와 함께 넣는다. 그래서 새 항목은 미정으로 시작하고, 개발 환경을 새로 만들거나 DB를 재초기화한 뒤에도 모든 항목이 미정이다. 기획의 설계 제안 값(예: 이의 기간 24시간)도 같다. 관리자가 상태 '설계 제안'으로 넣고 사유에 근거를 적는다. 시드가 값을 쓰지 않음은 `packages/db/src/seed.test.ts`가 고정한다.
4. 시험: API 시험은 `createTestApp({ releaseSettings: defineReleaseSettings([...]) })`로 시험용 항목을 주입한다(`apps/api/src/release-settings/release-settings.controller.test.ts`가 예다). 출시 레지스트리가 비어 있음은 아래 네 곳이 고정한다. 첫 항목을 등록하는 이슈는 네 곳을 모두 고쳐 등록한 항목을 고정한다. 하나라도 빠지면 시험이 실패하거나 README가 틀린다.
   - shared: `packages/shared/src/release-settings.test.ts`의 `ships empty`(등록된 키가 없다).
   - API: `apps/api/src/release-settings/release-settings.controller.test.ts`의 `ReleaseSettingsService with the shipped registry`(출시 레지스트리로는 DB에 닿지 않고 빈 목록).
   - e2e: `apps/web/e2e/release-settings.spec.ts`의 첫 시험(관리자 API의 빈 목록, '등록된 항목이 없습니다.', '전체 0개 · 미정 0개', 변경 버튼 없음).
   - README: 화면 표의 `/admin/settings` 줄('레지스트리가 비어 있어 지금은 …').

**필드.**

| 필드          | 뜻                                                                                 | 규칙                                                                                                                                                                                                                                       |
| ------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `key`         | 저장 키. `release_settings.key`와 변경 기록의 `admin_actions.target_id`에 남는다   | 소문자 낱말을 `_`로 잇고 `.`로 묶는다(`grant.initial_coin`), 64자 이하, 중복 금지. **한 번 배포한 키는 이름을 바꾸지 않는다.** 바꾸면 저장된 값과 기록이 옛 키에 남는다                                                                    |
| `label`       | 관리자 화면의 이름(한국어, 예: `시작 지급액`)                                      | 비어 있으면 안 된다                                                                                                                                                                                                                        |
| `unit`        | 단위(예: `Coin`, `시간`). 단위가 없는 값(켜고 끔, 목록)은 `null`                   | 빈 문자열 금지. 화면은 값과 단위를 따로 보인다                                                                                                                                                                                             |
| `description` | 이 값이 무엇을 정하는지와 담당 이슈                                                | 비어 있으면 안 된다                                                                                                                                                                                                                        |
| `schema`      | 값의 모양(zod). 관리자가 넣는 값을 검사하고, 읽을 때마다 저장된 값을 다시 검사한다 | 출력이 JSON이어야 한다(bigint 금지, Coin 금액은 정수나 10진 문자열). 자기 출력을 다시 받아야 한다(모양을 바꾸는 transform 금지). `null` 하나만으로 된 값은 '값 없음'이라 쓸 수 없다. 화면은 이 스키마의 JSON Schema를 입력 형식으로 보인다 |

관리자 화면의 값 입력은 스키마의 JSON Schema `type`이 `string`이면 입력한 글자 그대로, 아니면 JSON으로 읽는다(`24`, `true`, `[1, 2]`, `{"from": 1}`). 문자열 항목은 빈 칸과 공백도 그대로(빈 문자열 등) 보내고 받을지는 스키마가 정한다. 빈 값을 받지 않을 항목은 스키마가 거절해야 한다(예: `z.string().min(1)`). 나머지 항목의 빈 입력과 JSON `null`은 값이 아니다. 객체 값의 키 순서는 저장(jsonb)에서 바뀔 수 있다.

정의를 바꿔 저장된 값이 새 스키마에 맞지 않게 되면 서버는 그 값을 읽지 않고 오류를 낸다. 관리자 화면에는 그 값이 그대로 보이니 관리자가 새 값으로 바꾼다.

## 상태

| 상태      | 값   | 뜻                                                                                       |
| --------- | ---- | ---------------------------------------------------------------------------------------- |
| 미정      | 없음 | 값이 아직 정해지지 않았다. 행이 없는 항목도 미정이다                                     |
| 설계 제안 | 있음 | 기획이 설계 제안으로 적은 값(NR 설계 상태). 승인된 값이 아니다                           |
| 시험값    | 있음 | 출시 값이 정해지기 전(#133) 내부 배포에서 기능을 시험할 때 쓰는 값. 출시 값이 아니다     |
| 승인됨    | 있음 | 출시 값으로 승인된 값. 출시 값의 확정과 설계 제안 값의 승인은 #133·#173·#177·#180이 한다 |

- 설계 제안 값과 시험값은 어디서도 승인된 값(확정값)으로 표시하지 않는다(NR 설계 상태, N01 §10). 관리자 화면은 상태 배지로 구분한다. 승인됨만 브랜드 색이고, 설계 제안·시험값은 각자 다른 색, 미정은 눈에 띄는 주황 배지다. 화면 위의 범례가 네 상태의 뜻을 적는다. 배지의 이름과 색, 범례 문구는 #170 구현이 정한 것이다(오너 결정이 아니다, ADR-0055).
- 상태 이름은 `RELEASE_SETTING_STATUS_LABELS`(`@buddha/shared`) 하나다.

## 값 읽기

- **API 서버.** `ReleaseSettingsModule`을 가져와 `ReleaseSettingsService.get(정의, tx?)`로 읽는다. 결과는 `{ status, value }`다. 미정이면 `value`가 `null`이고, 나머지는 정의의 스키마로 타입이 붙은 값이다. 레지스트리에 등록한 바로 그 정의 객체로만 읽을 수 있다(`readReleaseSetting`이 검사한다).
- **상태에 따른 처리.** `get()`은 상태를 함께 돌려줄 뿐 설계 제안·시험값을 거절하지 않는다. 출시 환경에서도 같다. 서버는 상태만 알려 주고, 출시 환경에서 승인되지 않은 값을 막는 배포 등급 설정은 두지 않는다. 승인되지 않은 항목은 #149 출시 점검이 모두 확인한다(오너 결정 2026-10-13\~14, 아래 '출시 점검'). 항목이 미정(값 없음)일 때 그 일을 어떻게 할지(시작하지 않는다, 기능을 끈다 등)는 항목을 등록하는 이슈가 정한다.
- **워커.** 워커에는 Nest 주입이 없다. `getReleaseSetting(tx, RELEASE_SETTINGS, 정의)`(`@buddha/db`)로 읽는다. `ReleaseSettingsService.get`이 쓰는 바로 그 함수라 결과와 등록 검사가 같다. 읽을 수 없으면(등록되지 않은 정의, 정의에 맞지 않는 저장 값) 오류를 던지고 그 일은 실패한다.
- **표를 직접 읽지 않는다.** `release_settings`의 값은 `value::text`로 읽어 한 번만 `JSON.parse`해야 한다. drizzle의 jsonb 읽기가 문자열 값을 한 번 더 `JSON.parse`해 `"24"`를 24로 바꾸기 때문이다. 위의 두 길이 그렇게 읽는다. 다른 열과 함께 골라야 하면 값 열 대신 `storedReleaseSettingValue`(`@buddha/db`)를 고른다.
- **웹.** 값을 읽는 API는 관리자 전용이다. 사용자 화면이 값을 보여야 하면 그 항목의 담당 이슈가 경로를 정한다.

## 바꾼 값이 적용되는 때

오너 결정(2026-10-13): 바꾼 값은 **바꾼 뒤 시작하는 일에만** 적용한다. 이미 진행 중인 일(열린 시장, 진행 중인 이의 기간, 접수된 재지급 신청 등)은 시작할 때의 값을 끝까지 쓴다.

- 소비하는 코드는 일을 시작할 때 값을 **한 번** 읽는다. 그 일에 트랜잭션이 있으면 그 안에서 읽는다(`get(정의, tx)`).
- 일이 한 요청보다 오래 가면(기간, 신청, 시장) 읽은 값이나 그 값으로 계산한 결과(예: 이의 마감 시각)를 그 일의 행에 저장하고, 뒤에서는 저장한 것을 쓴다. 나중에 설정을 다시 읽어 진행 중인 일에 적용하지 않는다.
- b와 개장 기준은 시장 도중 바꾸지 않는다(N01 §6). 개장 전에 시장마다 고정하는 유동성 설정 버전(#72)과 규칙 버전(#80)은 출시 설정의 범위 밖이다(#170 제외, N03 §3). N01 §10은 A·L·b·호가 단계·기본 물량·안전 간격도 출시 설정으로 확정한다고 쓴다. 이 값들을 출시 설정 항목으로도 둘지(예: 개장 때 읽어 그 시장의 유동성 설정에 고정)는 설정 위치를 정하는 #180과 그것을 따르는 #72가 정한다.

## 바꾸기와 변경 기록

- **바꿀 수 있는 사람.** 관리자(`profiles.role = admin`, `AdminGuard`). 관리자 권한의 부여·회수는 #171이다. 값 변경에 다른 관리자의 승인이 필요한지는 #133이 정한다. 그 전까지는 관리자 한 명이 사유를 남기고 바꾼다.
- **사유는 필수다.** 1\~500자(`RELEASE_SETTING_REASON_MAX_LENGTH`). 사유가 없으면 거절한다(`VALIDATION_ERROR`). 미정은 값을 받지 않고, 나머지 상태는 정의의 스키마에 맞는 값이 있어야 한다.
- **바뀐 것이 없는 변경은 거절한다**(오너 결정 2026-10-13\~14). 상태와 값이 지금과 같으면 `VALIDATION_ERROR`(`details`는 `[{ path: [], message: RELEASE_SETTING_UNCHANGED_MESSAGE }]`)로 거절하고 아무것도 쓰지도 기록하지도 않는다. 값은 JSON 값으로 비교한다(객체 멤버의 순서는 보지 않는다, `isReleaseSettingUnchanged`). 행이 없는 항목은 미정이라 미정으로의 변경도 거절한다. 키 잠금 안에서 비교하므로 다른 관리자가 먼저 같은 변경을 했으면 뒤의 것이 거절된다. 관리자 화면은 상태와 값이 지금과 같은 동안 저장 버튼을 끄고 '바뀐 내용이 없습니다.'를 보이며, 서버가 이 까닭으로 거절하면 같은 문구를 알리고 대화상자를 닫는다.
- **기록.** 변경마다 같은 트랜잭션에서 `admin_actions`에 `release_setting_change` 한 행(대상 `release_setting`/키, payload `{ key, before: { status, value }, after: { status, value }, reason }`, 작업자, 시각)을 남긴다. 그 행 없이 `release_settings`를 쓰면 DB가 커밋 때 거절한다(마이그레이션 0020의 지연 제약 트리거). 기록의 대상과 payload `key`는 모두 쓰는 행의 키여야 하고, payload `after`는 쓰는 상태와 값, payload `before`는 그 쓰기가 바꾼 상태여야 한다. 고치는 쓰기(UPDATE)의 `before`는 이전 행의 상태와 값이고, 행이 없던 키의 첫 쓰기(INSERT)의 `before`는 값이 없는 미정(`{ status: 'undecided', value: null }`)이다. 변경 기록 목록은 payload의 키와 전후 상태를 보이므로, 기록에 보이는 키와 바뀌기 전 상태가 그 기록으로 쓴 행의 것과 다를 수 없다. 고치는 쓰기는 키를 바꿀 수 없고(키를 바꾸면 지우는 것처럼 원래 키가 미정이 되고 기록이 갈라진다), 변경 시각이 앞으로 가야 해서 앞선 변경의 기록을 다시 대어 옛 상태로 되돌려 쓸 수도 없다. 한 키의 변경 시각은 늘 앞선 변경보다 늦다(시계가 같은 밀리초를 읽으면 앞선 변경의 1ms 뒤). 그래서 기록의 순서가 변경의 순서다. `admin_actions`는 앱 계정이 고치거나 지울 수 없고, `release_settings`의 행도 지울 수 없다. 미정으로 되돌리는 것도 기록이 남는 변경이다.
- **기록을 보는 사람.** 관리자만(N04 §6). 관리자 화면의 '변경 기록'(작업자·시각·전후 값·사유)과 `GET /api/v1/admin/release-settings/changes`(`?key=`로 한 항목만). 관리자가 아닌 계정은 목록·변경·기록 모두 403이다.
- 레지스트리에서 빠진 키의 기록도 남는다. 화면에는 '등록되지 않은 항목'으로 보인다.

## 출시 점검(#149)

- `/admin/settings`에서 '미정만 보기'를 켜면 값이 미정인 항목이 모두 보인다. API로는 `GET /api/v1/admin/release-settings?status=undecided`다. 스위치 옆에 전체와 미정 항목 수가 있다.
- 승인되지 않은 값(설계 제안·시험값)은 목록의 배지로 보이고, API로는 `?status=proposal`·`?status=test`다.
- 출시 점검은 승인되지 않은 항목(미정·설계 제안·시험값)을 **모두** 확인한다. 출시 환경에서 시험값·설계 제안 값을 막는 장치(배포 등급 설정)는 없고 서버는 상태만 알려 주므로, 승인되지 않은 값이 출시에 남지 않게 하는 것은 이 점검이다(오너 결정 2026-10-13\~14).
- 운영 DB 재초기화(`deploy/reset-db.sh`, [docs/RESET.md](RESET.md))는 모든 표를 비우므로 `release_settings`와 변경 기록(`admin_actions`)도 비운다. 시드는 값을 쓰지 않으니 재초기화 뒤에는 모든 항목이 미정이고, 관리자가 사유와 함께 다시 넣는다. 출시 전 재초기화 때 값과 변경 기록을 남길지는 #133(재초기화 범위)이 정한다. 그 전까지는 함께 지운다(오너 결정 2026-10-13\~14).
