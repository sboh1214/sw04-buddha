# 출시 설정 등록 규칙

시뮬레이션이나 운영 승인으로 정할 값('출시 설정')을 한곳에 두고, 서버가 그곳에서 읽게 하는 규칙이다(#170). 결정과 근거는 [ADR-0055](DECISIONS.md)에 있다. 기획 인용 표기(NR, N00\~N06 §n)는 ADR-0047을 따른다. 뒤 이슈는 이 문서대로 자기 항목을 등록한다.

- 기획: 초기 지급액·재지급 주기·b·호가 단계·가격 보호 폭 등은 "시뮬레이션 후 출시 설정으로 확정한다"(N01 §10). 문서의 수치를 검증 완료라고 주장하지 않는다(N01 §10). 설정 변경은 사유·작업자·전후 값과 함께 기록한다(N01 §9).
- 오너 결정(2026-10-13, #170): 운영 중에 관리자 화면에서 바꾸고 변경마다 기록한다(값은 DB). 출시 값이 정해지기 전에는 시험용 값을 두고 출시 값과 구분해 표시한다. 바꾼 값은 바꾼 뒤 시작하는 일에만 적용한다.
- 오너 결정(2026-10-13\~14, #170 구현 중 답): 지금 상태·값과 똑같은 변경은 거절한다. 값은 관리자 화면으로만 넣고 마이그레이션·시드는 값을 쓰지 않는다(개발 환경을 만들거나 재초기화한 뒤에는 모든 항목이 미정). 서버는 상태만 알려 주고 승인되지 않은 항목은 #149 출시 점검이 모두 확인한다(배포 등급 설정은 두지 않는다). 출시 전 재초기화 때 값과 변경 기록을 남길지는 #133이 정하고, 지금은 함께 지운다.

## 구조

| 무엇                                 | 어디                                                                                   | 누가 바꾸나                                                                    |
| ------------------------------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 항목 정의(키·이름·단위·뜻·값의 모양) | 코드. `packages/shared/src/release-settings.ts`의 `RELEASE_SETTINGS`(`@buddha/shared`) | 항목을 등록하는 이슈의 PR                                                      |
| 값과 상태                            | DB. `release_settings` 표(키마다 한 행, 행이 없으면 미정)                              | 관리자. `/admin/settings` 화면이나 `PATCH /api/v1/admin/release-settings/:key` |
| 변경 기록                            | DB. `admin_actions`의 `release_setting_change` 행(전후 상태·값, 사유, 작업자, 시각)    | 값을 바꿀 때 같은 트랜잭션에서 저절로 남는다                                   |

- 레지스트리의 항목은 지금 #70의 시작 지급액(`grant.start_coin`, ADR-0071)과 #184의 데이터 종류별 보존기간 다섯(`retention.*`, ADR-0087 — 아래 '보존기간 항목')이다. #170은 장치만 만들었고, 실제 항목은 아래 '예상 항목'의 담당 이슈가 등록한다. 출시 레지스트리의 항목 목록을 고정한 곳(아래 '항목 등록하기' 4의 네 곳)은 항목을 등록하는 이슈가 모두 고친다.
- 서버는 등록된 항목을 이 레지스트리와 `release_settings`에서만 읽는다. 같은 값을 코드 여러 곳에 따로 적지 않는다. 지금 상수로 있는 값을 항목으로 옮기는 이슈는 옛 상수를 지운다. 예를 들어 #70은 시작 지급액을 항목으로 등록하면서 옛 두 곳 — `SIGNUP_BONUS_COIN`(`packages/shared/src/constants.ts`)과 가입 트리거 `create_profile_for_user()`의 10,000(마이그레이션 0019) — 을 지웠다(마이그레이션 0031, ADR-0071).

## 항목 등록하기

1. `packages/shared/src/release-settings.ts`에 `defineReleaseSetting({ key, label, unit, description, schema })`로 정의를 상수로 두고, `RELEASE_SETTINGS`의 목록에 넣는다. 목록의 순서가 관리자 화면의 순서다.
2. 값을 쓰는 서버 코드는 그 정의 객체로 읽는다(아래 '값 읽기').
3. 마이그레이션과 시드는 값을 쓰지 않는다(오너 결정 2026-10-13\~14). 값은 관리자가 화면에서 사유와 함께 넣는다. 그래서 새 항목은 미정으로 시작하고, 개발 환경을 새로 만들거나 DB를 재초기화한 뒤에도 모든 항목이 미정이다. 기획의 설계 제안 값(예: 이의 기간 24시간)도 같다. 관리자가 상태 '설계 제안'으로 넣고 사유에 근거를 적는다. 시드가 값을 쓰지 않음은 `packages/db/src/seed.test.ts`가 고정한다.
4. 시험: API 시험은 `createTestApp({ releaseSettings: defineReleaseSettings([...]) })`로 시험용 항목을 주입한다(`apps/api/src/release-settings/release-settings.controller.test.ts`가 예다). 출시 레지스트리의 항목 목록은 아래 네 곳이 고정한다. 항목을 등록하는 이슈는 네 곳을 모두 고쳐 등록한 항목을 더한다. 하나라도 빠지면 시험이 실패하거나 README가 틀린다.
   - shared: `packages/shared/src/release-settings.test.ts`의 `ships the items the issues that use them registered`(출시 레지스트리의 키 목록).
   - API: `apps/api/src/release-settings/release-settings.controller.test.ts`의 `the shipped registry (integration)`(주입 없이 뜬 앱의 관리자 목록과 그 항목의 값 규칙).
   - e2e: `apps/web/e2e/release-settings.spec.ts`의 첫 시험(관리자 API의 목록, 화면의 항목 줄과 '전체 N개 · 미정 N개', 변경 버튼의 수와 차례). 이 시험은 값을 바꾸지 않는다. 시작 지급액처럼 값을 넣으면 곧바로 일이 생기는 항목이 있고(승인된 보존기간은 워커의 다음 매일 처리가 그보다 오래된 기록을 지운다), e2e DB에 넣은 값은 다음 실행까지 남는다.
   - README: 화면 표의 `/admin/settings` 줄('등록된 항목은 …').

**필드.**

| 필드          | 뜻                                                                                 | 규칙                                                                                                                                                                                                                                       |
| ------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `key`         | 저장 키. `release_settings.key`와 변경 기록의 `admin_actions.target_id`에 남는다   | 소문자 낱말을 `_`로 잇고 `.`로 묶는다(`grant.initial_coin`), 64자 이하, 중복 금지. **한 번 배포한 키는 이름을 바꾸지 않는다.** 바꾸면 저장된 값과 기록이 옛 키에 남는다                                                                    |
| `label`       | 관리자 화면의 이름(한국어, 예: `시작 지급액`)                                      | 비어 있으면 안 된다                                                                                                                                                                                                                        |
| `unit`        | 단위(예: `Coin`, `시간`). 단위가 없는 값(켜고 끔, 목록)은 `null`                   | 빈 문자열 금지. 화면은 값과 단위를 따로 보인다                                                                                                                                                                                             |
| `description` | 이 값이 무엇을 정하는지와 담당 이슈                                                | 비어 있으면 안 된다                                                                                                                                                                                                                        |
| `schema`      | 값의 모양(zod). 관리자가 넣는 값을 검사하고, 읽을 때마다 저장된 값을 다시 검사한다 | 출력이 JSON이어야 한다(bigint 금지, Coin 금액은 정수나 10진 문자열). 자기 출력을 다시 받아야 한다(모양을 바꾸는 transform 금지). `null` 하나만으로 된 값은 '값 없음'이라 쓸 수 없다. 화면은 이 스키마의 JSON Schema를 입력 형식으로 보인다 |

관리자 화면의 값 입력은 스키마의 JSON Schema `type`이 `string`이면 입력한 글자 그대로, 아니면 JSON으로 읽는다(`24`, `true`, `[1, 2]`, `{"from": 1}`). 문자열 항목은 빈 칸과 공백도 그대로(빈 문자열 등) 보내고 받을지는 스키마가 정한다. 빈 값을 받지 않을 항목은 스키마가 거절해야 한다(예: `z.string().min(1)`). 나머지 항목의 빈 입력과 JSON `null`은 값이 아니다. 객체 값의 키 순서는 저장(jsonb)에서 바뀔 수 있다.

정의를 바꿔 저장된 값이 새 스키마에 맞지 않게 되면 서버는 그 값을 읽지 않고 오류를 낸다. 관리자 화면에는 그 값이 그대로 보이니 관리자가 새 값으로 바꾼다.

## 상태

| 상태      | 값   | 뜻                                                                                       |
| --------- | ---- | ---------------------------------------------------------------------------------------- |
| 미정      | 없음 | 값이 아직 정해지지 않았다. 행이 없는 항목도 미정이다                                     |
| 설계 제안 | 있음 | 기획이 설계 제안으로 적은 값(NR 설계 상태). 승인된 값이 아니다                           |
| 시험값    | 있음 | 출시 값이 정해지기 전(#133) 내부 배포에서 기능을 시험할 때 쓰는 값. 출시 값이 아니다     |
| 승인됨    | 있음 | 출시 값으로 승인된 값. 출시 값의 확정과 설계 제안 값의 승인은 #133·#173·#177·#180이 한다 |

- 설계 제안 값과 시험값은 어디서도 승인된 값(확정값)으로 표시하지 않는다(NR 설계 상태, N01 §10). 관리자 화면은 상태 배지로 구분한다. 승인됨만 브랜드 색이고, 설계 제안·시험값은 각자 다른 색, 미정은 눈에 띄는 주황 배지다. 화면 위의 범례가 네 상태의 뜻을 적는다. 배지의 이름과 색, 범례 문구는 #170 구현이 정한 것이다(오너 결정이 아니다, ADR-0055).
- 상태 이름은 `RELEASE_SETTING_STATUS_LABELS`(`@buddha/shared`) 하나다.

## 값 읽기

- **API 서버.** `ReleaseSettingsModule`을 가져와 `ReleaseSettingsService.get(정의, tx?)`로 읽는다. 결과는 `{ status, value }`다. 미정이면 `value`가 `null`이고, 나머지는 정의의 스키마로 타입이 붙은 값이다. 레지스트리에 등록한 바로 그 정의 객체로만 읽을 수 있다(`readReleaseSetting`이 검사한다).
- **상태에 따른 처리.** `get()`은 상태를 함께 돌려줄 뿐 설계 제안·시험값을 거절하지 않는다. 출시 환경에서도 같다. 서버는 상태만 알려 주고, 출시 환경에서 승인되지 않은 값을 막는 배포 등급 설정은 두지 않는다. 승인되지 않은 항목은 #149 출시 점검이 모두 확인한다(오너 결정 2026-10-13\~14, 아래 '출시 점검'). 항목이 미정(값 없음)일 때 그 일을 어떻게 할지(시작하지 않는다, 기능을 끈다 등)는 항목을 등록하는 이슈가 정한다. 시작 지급액은 오너가 정했다: 값이 있으면 상태(설계 제안·시험값·승인됨)와 상관없이 그 값으로 주고, 미정이면 지급을 기다리게 했다가 값이 들어오면 준다(ADR-0069 결정 4 #70·결정 7, ADR-0071). 보존기간도 오너가 정했다: 상태가 '승인됨'일 때만 그 기간으로 지우고, 미정·설계 제안·시험값이면 그 종류는 지우지 않는다(보존된다 — ADR-0069 결정 1 #57-18·결정 7, ADR-0087). 되돌릴 수 없는 두 일 가운데 지급은 값이 있으면 하고 삭제는 승인된 값만 한다.
- **워커.** 워커에는 Nest 주입이 없다. `getReleaseSetting(tx, RELEASE_SETTINGS, 정의)`(`@buddha/db`)로 읽는다. `ReleaseSettingsService.get`이 쓰는 바로 그 함수라 결과와 등록 검사가 같다. 읽을 수 없으면(등록되지 않은 정의, 정의에 맞지 않는 저장 값) 오류를 던지고 그 일은 실패한다.
- **표를 직접 읽지 않는다.** `release_settings`의 값은 `value::text`로 읽어 한 번만 `JSON.parse`해야 한다. drizzle의 jsonb 읽기가 문자열 값을 한 번 더 `JSON.parse`해 `"24"`를 24로 바꾸기 때문이다. 위의 두 길이 그렇게 읽는다. 다른 열과 함께 골라야 하면 값 열 대신 `storedReleaseSettingValue`(`@buddha/db`)를 고른다.
- **웹.** 값을 읽는 API는 관리자 전용이다. 사용자 화면이 값을 보여야 하면 그 항목의 담당 이슈가 경로를 정한다.

## 바꾼 값이 적용되는 때

오너 결정(2026-10-13): 바꾼 값은 **바꾼 뒤 시작하는 일에만** 적용한다. 이미 진행 중인 일(열린 시장, 진행 중인 이의 기간, 접수된 재지급 신청 등)은 시작할 때의 값을 끝까지 쓴다.

- 소비하는 코드는 일을 시작할 때 값을 **한 번** 읽는다. 그 일에 트랜잭션이 있으면 그 안에서 읽는다(`get(정의, tx)`).
- 일이 한 요청보다 오래 가면(기간, 신청, 시장) 읽은 값이나 그 값으로 계산한 결과(예: 이의 마감 시각)를 그 일의 행에 저장하고, 뒤에서는 저장한 것을 쓴다. 나중에 설정을 다시 읽어 진행 중인 일에 적용하지 않는다.
- b와 개장 기준은 시장 도중 바꾸지 않는다(N01 §6). 개장 전에 시장마다 고정하는 유동성 설정 버전(#72)과 규칙 버전(#80)은 출시 설정의 범위 밖이다(#170 제외, N03 §3). N01 §10은 A·L·b·호가 단계·기본 물량·안전 간격도 출시 설정으로 확정한다고 쓴다. #180은 이 여섯 값을 시장마다 입력하고 입력칸을 출시 표준값으로 미리 채우게 했다(ADR-0058). 표준값을 출시 설정 항목으로 둘지는 #72가 정한다. 시장에 고정한 값은 #130의 변경으로만 바뀌고, b와 개장 기준은 바뀌지 않는다.

## 바꾸기와 변경 기록

- **바꿀 수 있는 사람.** 관리자(`profiles.role = admin`, `AdminGuard`). 관리자 권한의 부여·회수는 #171이다. 값 변경에 다른 관리자의 승인이 필요한지는 #133이 정한다. 그 전까지는 관리자 한 명이 사유를 남기고 바꾼다.
- **사유는 필수다.** 1\~500자(`RELEASE_SETTING_REASON_MAX_LENGTH`). 사유가 없으면 거절한다(`VALIDATION_ERROR`). 미정은 값을 받지 않고, 나머지 상태는 정의의 스키마에 맞는 값이 있어야 한다.
- **jsonb가 담지 못하는 글자는 받지 않는다.** 사유와 값은 jsonb(`admin_actions.payload`, `release_settings.value`)에 저장된다. PostgreSQL의 jsonb는 U+0000(NUL)과 짝이 없는 UTF-16 서러게이트를 담지 못해 그대로 쓰면 쓰기가 500으로 실패한다. 그래서 사유(`releaseSettingChangeBodySchema`)와, 스키마를 거친 값의 모든 문자열과 객체 키(`parseReleaseSettingChange`, 스키마가 버린 키는 저장되지 않으니 보지 않는다)에 이 글자가 있으면 아무것도 쓰기 전에 거절한다(`VALIDATION_ERROR`, 경로 `['reason']`·`['value', …]`, 메시지 `JSONB_NUL_MESSAGE`·`JSONB_LONE_SURROGATE_MESSAGE`, 객체 키는 앞에 `key `). NUL 메시지는 API 전역 검증 파이프의 것과 같다. 짝이 맞는 서러게이트(이모지 등)와 NUL 밖의 제어 문자는 jsonb가 담으므로 그대로 받는다.
- **바뀐 것이 없는 변경은 거절한다**(오너 결정 2026-10-13\~14). 상태와 값이 지금과 같으면 `VALIDATION_ERROR`(`details`는 `[{ path: [], message: RELEASE_SETTING_UNCHANGED_MESSAGE }]`)로 거절하고 아무것도 쓰지도 기록하지도 않는다. 값은 JSON 값으로 비교한다(객체 멤버의 순서는 보지 않는다, `isReleaseSettingUnchanged`). 행이 없는 항목은 미정이라 미정으로의 변경도 거절한다. 키 잠금 안에서 비교하므로 다른 관리자가 먼저 같은 변경을 했으면 뒤의 것이 거절된다. 관리자 화면은 상태와 값이 지금과 같은 동안 저장 버튼을 끄고 '바뀐 내용이 없습니다.'를 보이며, 서버가 이 까닭으로 거절하면 같은 문구를 알리고 대화상자를 닫는다.
- **기록.** 변경마다 같은 트랜잭션에서 `admin_actions`에 `release_setting_change` 한 행(대상 `release_setting`/키, payload `{ key, before: { status, value }, after: { status, value }, reason }`, 작업자, 시각)을 남긴다. 그 행 없이 `release_settings`를 쓰면 DB가 커밋 때 거절한다(마이그레이션 0020의 지연 제약 트리거). 기록의 대상과 payload `key`는 모두 쓰는 행의 키여야 하고, payload `after`는 쓰는 상태와 값, payload `before`는 그 쓰기가 바꾼 상태여야 한다. 고치는 쓰기(UPDATE)의 `before`는 이전 행의 상태와 값이고, 행이 없던 키의 첫 쓰기(INSERT)의 `before`는 값이 없는 미정(`{ status: 'undecided', value: null }`)이다. payload `key`는 문자열이어야 하고, payload `reason`은 API의 사유 규칙(`releaseSettingChangeBodySchema`)대로 앞뒤 공백을 뺀 길이가 1\~500자인 문자열이어야 한다(공백은 JavaScript의 `trim`이 지우는 문자, 길이는 zod처럼 코드 포인트로 센다). 변경 기록 목록은 payload의 키와 전후 상태를 보이므로, 기록에 보이는 키와 바뀌기 전 상태가 그 기록으로 쓴 행의 것과 다를 수 없다. 변경 기록 목록은 읽을 수 없는 기록(`releaseSettingChangePayloadSchema`에 맞지 않는 payload)에서 실패하므로, 쓰기에 쓰인 기록은 모두 그 스키마로 읽힌다. 고치는 쓰기는 키를 바꿀 수 없고(키를 바꾸면 지우는 것처럼 원래 키가 미정이 되고 기록이 갈라진다), 변경 시각이 앞으로 가야 해서 앞선 변경의 기록을 다시 대어 옛 상태로 되돌려 쓸 수도 없다. 한 키의 변경 시각은 늘 앞선 변경보다 늦다(시계가 같은 밀리초를 읽으면 앞선 변경의 1ms 뒤). 그래서 기록의 순서가 변경의 순서다. `admin_actions`는 앱 계정이 고치거나 지울 수 없고, `release_settings`의 행도 지울 수 없다. 미정으로 되돌리는 것도 기록이 남는 변경이다.
- **기록을 보는 사람.** 관리자만(N04 §6). 관리자 화면의 '변경 기록'(작업자·시각·전후 값·사유)과 `GET /api/v1/admin/release-settings/changes`(`?key=`로 한 항목만). 관리자가 아닌 계정은 목록·변경·기록 모두 403이다.
- 레지스트리에서 빠진 키의 기록도 남는다. 화면에는 '등록되지 않은 항목'으로 보인다.

## 출시 점검(#149)

- `/admin/settings`에서 '미정만 보기'를 켜면 값이 미정인 항목이 모두 보인다. API로는 `GET /api/v1/admin/release-settings?status=undecided`다. 스위치 옆에 전체와 미정 항목 수가 있다.
- 승인되지 않은 값(설계 제안·시험값)은 목록의 배지로 보이고, API로는 `?status=proposal`·`?status=test`다.
- 출시 점검은 승인되지 않은 항목(미정·설계 제안·시험값)을 **모두** 확인한다. 출시 환경에서 시험값·설계 제안 값을 막는 장치(배포 등급 설정)는 없고 서버는 상태만 알려 주므로, 승인되지 않은 값이 출시에 남지 않게 하는 것은 이 점검이다(오너 결정 2026-10-13\~14).
- 운영 DB 재초기화(`deploy/reset-db.sh`, [docs/RESET.md](RESET.md))는 모든 표를 비우므로 `release_settings`와 변경 기록(`admin_actions`)도 비운다. 시드는 값을 쓰지 않으니 재초기화 뒤에는 모든 항목이 미정이고, 관리자가 사유와 함께 다시 넣는다. 출시 전 재초기화 때 값과 변경 기록을 남길지는 #133(재초기화 범위)이 정한다. 그 전까지는 함께 지운다(오너 결정 2026-10-13\~14).

## 보존기간 항목(#184)

개인정보 보존기간은 데이터 종류마다 출시 설정 하나다(ADR-0069 결정 1 #57-18 «종류별 기간을 /admin/settings에서, 미정인 종류는 보존», ADR-0087). 워커의 `retention.purge`(매일 04:30 KST)가 실행마다 다섯 값을 한 번 읽고(바꾼 값은 그 뒤의 실행부터), 상태가 '승인됨'인 종류만 그 기간이 지난 기록을 지운다(결정 7). 기간을 세는 기준 시각은 오너가 정했다(ADR-0069 결정 4 #184·결정 7): 탈퇴한 계정의 남은 기록은 탈퇴 시각(`profiles.closed_at`), 탈퇴하지 않은 계정이 지운 것은 지운 시각, 수정 이력은 늘 바뀐 때, 처리 중이던 기록은 처리 시각이 더 늦으면 그때이고 처리가 끝나기 전에는 지우지 않는다. 처리 중인 신고가 있는 글·댓글과 결정을 기다리는 계정 제한 요청(걸기·감경·조기 해제·취소)이 근거로 든 글·댓글은 신고가 처리되거나 요청이 결정·철회될 때까지 원문과 수정 이력을 지우지 않는다(오너 결정 2026-10-24 4·12 — 기간은 그대로 지운 때·바뀐 때부터). 실행마다 종류·건수·적용한 기간·시각을 `retention_purges`에 남기고(개인정보 내용은 없다), 오류로 끝내지 못한 종류는 '실패'로 남기며(오너 결정 2026-10-24 14 — `outcome` `failed`), 관리자는 `/admin/retention`에서 본다.

- 값은 정수 일(1\~7,300 — 7,300은 오타를 막는 상한이지 정한 값이 아니다)이다. 하루는 DB 시계의 24시간이고, 기준 시각에서 정확히 그 기간이 지난 기록부터 지운다(`retentionCutoffOf`).
- 기간 없이 남기는 것(#57-18): 원장, 주문, 관심 등록·해제 이력(`market_watch_events`), 좋아요, 시작 지급 기록, 운영 기록(`admin_actions`와 이 처리 기록), 지우지 않은 글·댓글(탈퇴한 회원의 숨긴 채로 남은 것은 위 '신고·제재 기록'). 탈퇴하지 않은 계정의 동의·본인확인 기록, 탈퇴하지 않은 회원이 받은 조치와 탈퇴하지 않은 계정끼리의 신고도 지우지 않는다(오너 결정 2026-10-24 2).

**보존기간 항목 등록하기.** #184 뒤에 생기는 개인정보 종류(알림 #53, 방문 기록 #151, 판정 이의 #175, 링크 검토 목록 #187, 시장 제안 #77 등)도 같은 방식으로 보존기간을 받는다. 오너가 이미 정한 것: 링크 검토 목록은 '신고·제재 기록'(표시된 때와 '확인함'인 때 가운데 늦은 쪽부터), 시장 제안은 새 항목 '시장 제안 기록 보존기간'(탈퇴한 계정의 것, 처리가 끝난 뒤 — 오너 결정 2026-10-24 13, ADR-0087 결과 5). 그 종류를 저장하는 이슈가 한 PR에서:

1. 기간은 오너가 정한다 — 새 항목을 두는 것도, 기존 항목의 기간을 함께 쓰는 것도 오너의 결정이다(#57-18 '데이터 종류마다 보존기간', 기존 항목의 값은 오너가 그 항목의 종류들을 보고 승인한 것이다). 오너 결정이나 브리프가 그 종류를 이미 한 목록에 묶은 경우만 묻지 않고, 그 근거를 ADR에 적는다(예: 판정 이의(#175)는 '신고·제재 기록' — #184 브리프의 '신고·제재(와 뒤의 판정 이의) 기록' 묶음, ADR-0087 7-1). 새 항목이면 `packages/shared/src/release-settings.ts`에 `retention.<종류>` 항목(단위 '일', `retentionDaysSchema`)을 더해 `RETENTION_PERIOD_SETTINGS`·`RELEASE_SETTINGS`에 넣고(위 '항목 등록하기'의 네 곳도 고친다), 기존 항목을 쓰면 그 항목의 뜻(`description`)에 그 종류를 더한다 — 오너가 값을 승인하는 화면이 그 기간에 지우는 것을 모두 말한다.
2. `packages/shared/src/retention.ts`의 `RETENTION_PERIODS`(새 항목이면)와 `RETENTION_PURGE_KINDS`·`RETENTION_PURGE_KIND_PERIODS`에 처리 종류를 더한다. 처리 기록 표의 CHECK(`retention_purges_kind_check`)는 새 마이그레이션으로 고친다. 관리자 화면의 종류 이름은 `apps/web/src/copy.ts`의 `adminRetentionKind…`와 `apps/web/src/lib/retention.ts`다. 그 종류가 실패하면 실행이 저절로 '실패'의 기록을 남긴다(`outcome`).
3. `apps/worker/src/jobs/retention-purge.ts`의 `STEPS`에 그 종류의 단계를 외래 키의 차례대로 넣는다. 기준 시각은 위 오너 결정을 따르고, 처리 중인 기록은 남긴다(글·댓글의 내용이면 `nothingAwaits` — 처리 중인 신고와 결정을 기다리는 계정 제한 요청). 앱 롤(`buddha_app`)에 그 표의 DELETE가 없으면 가장 좁은 권한(그 표의 DELETE, 또는 지울 수 있는 행만 지우는 `SECURITY DEFINER` 함수 — `retention_delete_approval_requests`가 예다)을 마이그레이션에 더한다.
4. 시험: `retention-purge.test.ts`에 값이 '승인됨'일 때와 아닐 때, 기준 시각과 경계(기간에서 1ms 모자라면 남고 정확히 기간이면 지운다), 기록의 행, 다른 것을 지우지 않음을 더한다.

것으로 올린 형식 그대로 다시 인코딩(글 이미지와 같은 인코더 설정), 글 이미지의 디코딩 예산과 한 번에 하나의 변환 줄, 디코딩 예산 안에 들도록 고른 변환의 길(JPEG·WebP는 긴 변이 이미 2,048px 이하이거나, 긴 변을 2,048px 안으로 줄여도 짧은 변이 정사각형의 한 변보다 길면 글 이미지처럼 줄인 뒤 그 가운데를, 아니면 PNG처럼 파일에서 가운데 정사각형을 먼저 잘라 — ADR-0079 결정 7-16)와 그 먼저 자르는 WebP의 디코딩 값(통째로 풀리므로 머리 검사가 화소마다 17바이트로 세어 약 790만 화소까지 받는다 — `PROFILE_WEBP_CUT_BYTES_PER_PIXEL`, 글 이미지의 WebP는 15로 약 895만. 잰 값이다) — 바꾸려면 그 코드와 ADR-0079를 함께 고친다. 출시 설정으로 둔 것이 없다. 하루 업로드 한도(#187)는 프로필 이미지도 글 이미지와 함께 센다(오너 결정 2026-10-22, #187이 만든다). 바꾸거나 지운 이전 이미지의 파일을 저장소가 곧바로 지우지 못하면 그 키를 #46의 삭제 대기열(`media_deletions`)에 두고 워커가 1·2·4·8·16시간 뒤, 그다음은 하루마다 다시 지운다 — 그 간격은 #46의 고정값(`@buddha/shared`의 `orphanMediaRetryHours`·`ORPHAN_MEDIA_RETRY_*`)이다(오너 결정 2026-10-22, ADR-0079 7-5). 화면의 올리기가 429로 거절되면 기다렸다 두 번까지 다시 보내는 것(10초 넘게 기다리라는 것은 다시 보내지 않는다)은 글 편집기의 고정값(`IMAGE_UPLOAD_RETRIES`·`IMAGE_UPLOAD_RETRY_MAX_WAIT_MS`) 그대로다 — 오너가 정했다(오너 결정 2026-10-23: «프로필 이미지 카드의 429 → 글 편집기처럼 두 번까지 스스로 다시 올림(지금대로)», ADR-0079 7-18).
- 신고와 운영 처리(#50, ADR-0081): 신고는 한 사람(본인확인한 번호의 키 있는 해시 — 탈퇴한 계정의 것도 같은 번호면 센다)이 지난 24시간에 20건까지이고 운영자 계정은 세지 않는다, 조치의 이의는 조치마다 한 번, 조치 뒤 14일 안이다(받은 경고의 MY 요약 띠도 그 14일 동안 보인다, 오너 결정 2026-10-21): 오너가 코드의 고정값으로 정했다(ADR-0069 결정 2 #45-14·#45-15, 결정 7). `@buddha/shared`의 `REPORTS_PER_DAY`·`REPORT_WINDOW_HOURS`·`APPEAL_WINDOW_DAYS`이고, 신고 창의 한도 문장과 이의 안내가 같은 수를 말하는지 시험이 본다(`apps/web/src/lib/moderation.test.ts`). '하루'를 지난 24시간으로 센 것은 #187의 오너 결정(2026-10-22 «하루 → 지난 24시간»)을 따른 것이다. 첫 커밋이 고르고 오너가 그대로 정한 값(오너 결정 2026-10-21)과 구현이 고른 값도 코드에 있다: 신고의 설명, 운영자가 회원에게 보이는 설명, 취소·기각의 운영 기록 사유는 모두 500자(코드 포인트, `REPORT_DESCRIPTION_MAX_LENGTH`·`MODERATION_NOTE_MAX_LENGTH`·`MODERATION_REASON_MAX_LENGTH`, DB의 `varchar(500)`), 한 번의 기각은 신고 100건까지(`DISMISS_REPORTS_MAX` — 한 대상에 그보다 많이 기다리면 운영자 화면이 먼저 들어온 100건씩 나눠 기각한다, 오너 결정 2026-10-21 «지금대로»), 강제로 바꾼 닉네임은 자동 닉네임을 열 번까지 뽑는다 — 바꾸려면 그 상수와 ADR-0081을 함께 고친다. 강제로 바꾼 뒤의 옛 닉네임 보류는 다른 보류와 같은 30일(`NICKNAME_HOLD_DAYS`)이고 그 회원에게도 걸리며(오너 결정 2026-10-21), 조치를 취소하면 남은 기간 동안 그 회원의 보류가 되고 그 동안 그 회원은 그 닉네임을 30일 변경 간격(`NICKNAME_CHANGE_INTERVAL_DAYS`) 없이 한 번 고른다(오너 결정 2026-10-22 (2차)·(4차) — 되찾았다가 다시 바꾼 뒤에는 간격 그대로) — 조치·신고 내역의 보류 줄과 운영자의 취소 창의 보류 문장도 같은 30일 동안 보이고 그 뒤의 취소 창은 보류가 끝났다는 문장이며(`nicknameHoldEndOf`), 그 줄과 두 취소 창의 문장이 이 상수와 같은 수를 말하는지 시험이 본다(오너 결정 2026-10-22, (2차)). 출시 설정으로 둔 것이 없다.
- 작성 제한(#185, ADR-0082): 기간은 1·3·7·30일과 무기한이고(하루는 조치의 시각에서 24시간), 기간제는 끝나는 시각에 저절로 풀린다(일이 돌지 않고 DB의 시계로 물을 때마다 견준다): 오너가 코드의 고정값으로 정했다(ADR-0069 결정 2 #45-12). `@buddha/shared`의 `WRITING_RESTRICTION_DAYS`와 `writingRestrictionEndOf`이고, 관리자 창의 다섯 기간이 같은 목록인지 시험이 본다(`apps/web/src/lib/moderation.test.ts`). 감경은 기간 목록이 아니라 지금 끝보다 앞이고 오지 않은 아무 때로 앞당긴다(ADR-0082 7-3 — 오너에게 묻는 것, 결과 4의 3). 출시 설정으로 둔 것이 없다.
- 작성 빈도 제한(#187, ADR-0083): 근거 글 10분에 3개·하루 20개, 댓글·대댓글을 합해 1분에 5개·하루 200개(ADR-0069 결정 2 #45-15), 글·댓글의 수정을 합해 10분에 10번·하루 50번, 이미지 업로드는 글의 이미지와 프로필 이미지를 합해 하루 50장(결정 7, ADR-0079의 오너 결정 2026-10-22 답 4) — 계정이 아니라 본인확인한 번호의 키 있는 해시마다 세고(결정 7), 지운 글도 세며 가입 직후 계정을 따로 보지 않고 운영자 계정은 예외다(#45-15, 결정 4 #187): 오너가 결정 이슈에서 정한 고정값이다(#187 본문의 '출시 설정으로 두기로 하면 #170에서 읽는다'는 일어나지 않았다). `@buddha/shared`의 `WRITE_LIMITS` 한곳에 있고(이유마다의 창과 수), 거절 문장이 같은 수를 말하는지 시험이 본다(`apps/web/src/lib/write-limits.test.ts`). 구현이 고른 것도 코드에 있다: '하루'는 지난 24시간(달력의 날이 아니다 — 본인확인과 시장 제안의 하루 한도와 같다), 거절의 기다림은 분 단위로 올림(`retryAfterSeconds`), 수정은 바꾼 것이 있을 때만 세고 업로드는 저장한 이미지만 센다 — 바꾸려면 그 코드와 ADR-0083을 함께 고친다.
- 반복 링크 탐지(#187, ADR-0083): 같은 사람이 같은 주소를 24시간에 3개 이상의 글·댓글에 쓰거나 서로 다른 3명 이상이 24시간에 같은 주소를 쓰면 운영자 검토 목록에 올린다(거절·숨김 없음), 주소는 scheme·도메인만 소문자로 하고 끝 슬래시와 추적용 덧붙임을 지우며 단축 주소는 풀지 않는다, 시장의 공식 출처 주소와 운영자 계정은 예외, 본문 반복·금칙어·연락처 필터는 없다: 오너가 정한 규칙과 고정값이다(ADR-0069 결정 2 #45-15, 결정 4 #187, 결정 7). `@buddha/shared`의 `LINK_REPEAT_THRESHOLD`·`LINK_REPEAT_WINDOW_SECONDS`·`normaliseLink`다. 첫 구현이 고르고 오너가 그대로 받은 것(ADR-0083의 오너 결정 2026-10-22 답 1): 지우는 추적용 덧붙임의 목록(`TRACKING_PARAMETERS` — `utm_*`와 큰 광고·소셜 서비스의 클릭 id), `#` 뒤도 지움(`http`·`https`와 `www`의 있고 없음은 다른 주소), '사람'은 본인확인한 번호, 공식 출처는 그 주소와 그 아래 페이지, 규칙을 넘으면 그 규칙이 센 항목 모두, 작성자가 지운 글·댓글과 운영자가 숨긴 것도 셈. 그 답이 더 정한 것: 글·댓글마다 본문 순서로 앞의 링크 20개까지만 본다(`LINK_CHECK_MAX`, 답 4 — 쓰기는 거절하지 않는다), 검토 목록은 같은 주소·규칙끼리 묶고 운영자가 '확인함'(문제 없음·조치함)으로 표시하면 운영 기록(`admin_actions`)에 남고 기본 목록에서 빠지며(답 2·3), 검토 목록은 #57-18의 보존 데이터다(답 6 — 기간과 지우기는 #184). 바꾸려면 그 코드와 ADR-0083을 함께 고친다.
- 제재 이의의 안내(#186, ADR-0084): 기한은 위의 `APPEAL_WINDOW_DAYS`(조치 뒤 14×24시간의 정확한 시각 — 오너 결정 2026-10-22 답 1, 운영자는 고객센터 메일함에 도착한 시각으로 본다 — 답 10)이고, 화면이 분까지 보이는 그 기한의 분이 끝날 때(…:59)까지 기한 안이다(오너 결정 2026-10-23 답 5, `@buddha/shared`의 `appealWindowEndOf`). 조치·신고 내역 맨 위의 안내 문장이 같은 수를 말하는지 시험이 본다(`apps/web/src/lib/moderation.test.ts`). 운영자가 기한까지 3일보다 적게 남았거나 기한이 지난 뒤에 되물었으면(늦은 되묻기) 되묻는 글은 '…를 적어 3일 안에 다시 보내 주세요.'로 끝나고, 되묻는 메일을 보낸 때부터 3일 안에 다시 온 메일은 첫 메일이 도착한 시각으로 기한을 본다 — 3일은 오너가 정한 고정값이고(오너 결정 2026-10-23 답 2), 그 3일을 3×24시간으로 세는 것과 늦은 되묻기의 경계도 오너가 정했다(오너 결정 2026-10-23 (2차) 답 1). 되묻기 하나에 다시 온 이의 하나만 그렇게 보는 것은 ADR-0084의 읽기다(ADR-0084 6-8). 어느 조치가 늦은 되묻기를 정하고 그 3일을 받는지 — 되묻기를 받은 메일이 온 때까지 받았고 그 메일이 기한 안에 온 조치 — 도 그렇다. 그 읽기가 닿는 드문 경우 — 늦은 되묻기 하나에 다시 온 이의가 여럿이거나 늦은 되묻기인지가 갈리는 것 — 는 고정값이 아니라 운영자가 회원에게 유리하게 판단한다(오너 결정 2026-10-23 (3차), 운영자의 절차 7). 이 규칙은 운영자의 절차(`docs/OPERATIONS.md`)에만 있다. 안내에 보이는 고객센터 이메일은 출시 설정이 아니라 사업자 정보다(`apps/web/src/legal/business-info.ts`의 `email`, 지금 미정 — 푸터·약관과 같은 값이라 오너가 정하면 그 한 줄을 고친다, ADR-0069 결과 3). 이의는 앱 밖이라 세는 값도 저장하는 값도 없다.
