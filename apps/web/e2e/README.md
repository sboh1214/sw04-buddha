# E2E 실행 구성

#129부터 전체 검증은 다음 세 구성을 **모두** 실행한다. 기본 3샤드 통과만으로 전체 E2E를 통과했다고 기록하지 않는다. 각 구성은 별도의 fresh Postgres 시험 DB와 Redis DB를 쓰며, API·web·worker 포트는 한 구성씩만 소유한다. 서버는 해당 구성의 DB/Redis 환경으로 시작해야 한다.

| 구성                | 명령 (저장소 루트)                                          | 단계 시험값: reduce / halt / ratio | 금고 준비                                                      |
| ------------------- | ----------------------------------------------------------- | ---------------------------------- | -------------------------------------------------------------- |
| 일반 회귀 3샤드     | `pnpm --filter web test:e2e --shard=1/3`, 이어 `2/3`, `3/3` | 0 / 0 / 0                          | 실제 두 관리자 승인으로 시험용 가용 재원 100,000,000 Coin 준비 |
| 실제 봇 호가, 두 폭 | `pnpm --filter web test:e2e:market-maker`                   | 7000 / 9000 / 5000                 | 같은 승인 절차로 시험용 재원 준비                              |
| 부족 금고, 두 폭    | `pnpm --filter web test:e2e:treasury`                       | 0 / 0 / 0                          | 선발행 없음; 해당 시험의 재원 보충만 실행                      |

- 각 구성은 375px·1280px를 모두 실행한다. 기본 config가 제외한 `@market-maker-quotes`·`@isolated-treasury`는 별도 config가 선택하며 `skip`한 시험이 아니다. CI와 전체 검사 runner도 세 구성을 모두 포함해야 한다.
- 일반 구성도 `workers: 1`로 실행한다. 거래 패턴 시험처럼 같은 DB의 전역 출시 설정을 바꿨다가 복원하는 시나리오가 있으므로 한 샤드 안의 두 viewport가 동시에 설정을 덮지 않게 한다. `fullyParallel`은 시험 단위 샤드 분할을 위해 유지하며 CI의 여섯 일반 샤드(ADR-0168)는 독립 DB에서 병렬로 실행한다. `--workers`로 이 조건을 덮으면 해당 시나리오의 기존 단일 워커 검사가 실패한다.
- CI의 E2E 작업 총 한도는 빌드·준비와 단일 워커 실행을 포함해 60분이다. 기존 테스트별 180초·기대 조건별 15초 제한, CI 재시도 2회와 실패 판정은 바꾸지 않는다. 전체 한도를 늘려도 실패한 assertion을 통과로 간주하지 않는다.
- 0/0/0은 초기 보유가 없는 MM의 위험 증가 호가를 억제해 기존 사용자 주문 회귀의 빈 호가 전제를 유지하는 **시험값**이다. 봇 실행기·시장 검수·초기 배정을 우회하지 않는다. 7000/9000/5000도 실제 호가 시나리오의 명시적 시험값이며, 어느 값도 운영 기본값이나 출시 승인값이 아니다.
- 단계값이 이미 다르게 입력되어 있으면 global setup은 실패한다. 다른 프로필의 설정을 덮거나 기본값으로 추정하지 않는다. `marketMakerProfile` metadata는 두 전용 config에서만 정한다.
- 일반·실제 호가 프로필은 global setup에서만 부족한 시험 재원을 실제 발행 요청과 다른 관리자 승인으로 준비한다. 시장 helper는 금고를 자동 보충하지 않으며, 승인된 시장 A를 실제 배정해야 개장한다.
- 부족 금고 시나리오는 시장을 만들지 않는다. 다른 구성의 자동 개장·자금 배정·발행과 공유하면 실패 근거가 바뀌므로 전용 fresh DB/Redis에서 단독으로 실행한다. 두 viewport는 `workers: 1`로 순차 실행한다.
- local DB는 `5433`, `buddha_e2e_*` 등의 기존 fixture 허용 이름과 명시적인 app/owner URL이 필요하다. CI는 저장소의 disposable 서비스만 허용한다. 자격 증명을 로그·스크립트에 저장하지 않는다.
- 알림 fixture(`notification-fixture.ts`, #53, ADR-0157): #53에는 알림 유형도 알림을 만드는 기능도 없어(52-20) API·브라우저로는 알림을 만들 수 없었다. #134(ADR-0158)부터 거래 알림은, #54(ADR-0159)부터 시장 상태 알림은, #188(ADR-0160)부터 판정·정산 알림은, #135(ADR-0161)부터 커뮤니티 알림은 API로 생기고 `trade-notifications.spec.ts`·`market-notifications.spec.ts`·`judgement-notifications.spec.ts`(와 지급 완료 알림을 보는 `settlement.spec.ts`)·`community-notifications.spec.ts`가 그렇게 만든다 — 이 fixture는 `notifications.spec.ts`가 시장을 가리키는 알림(시험 전용 유형)을 만드는 길로 남는다. `notifications.spec.ts`는 native child(`notification-fixture-worker.mjs`, IPC, Playwright loader 플래그 없이 fork)로 시험 전용 유형을 실제 쓰기 경로에 넣는다(`@buddha/db/test`의 `createTestNotification`). DB 그래프를 불러오거나 연결하기 전에 정정 fixture와 같은 URL 검증(`correctionFixtureUrls`)을 거치고, app URL(buddha_app, 생산자가 쓰는 역할)로만 연결하며, 오류는 URL을 지운 문장만 돌려준다. 방금 가입한 회원의 알림만 만들어 advisory lock은 쓰지 않는다. global setup은 `retention.notifications`에 값을 넣지 않는다(승인된 값이면 워커가 지운다).
- 글·댓글을 API로 쓰는 도우미(#135, ADR-0161): `postThroughApi(context, marketId, title, text)`(글의 id)와 `commentThroughApi(context, postId, parentId, body)`(댓글이나 `parentId` 아래의 대댓글 — 답의 `{ id, createdAt }`, `createdAt`은 답글 알림의 `replyCreatedAt`이 저장하는 `toISOString()`)는 `helpers.ts`에 있고 `comments.spec.ts`와 `community-notifications.spec.ts`가 가져온다(`comments.spec.ts`는 쓰는 곳에서 `.id`를 읽는다). `reports`·`restrictions`·`account-restrictions` 스펙의 다른 꼴의 도우미는 그 파일에 그대로 있다. 댓글은 쓰는 회원마다 1분에 5개까지라(#187) 여러 회원이 나눠 쓴다.
- 알림 수신 설정 도우미(#56, ADR-0162): `helpers.ts`의 `setNotificationCategory(context, category, enabled)`는 그 컨텍스트가 로그인한 계정을 `expectedAccountId`로 대어 `PUT /me/notifications/settings/:category`를 보내고 설정 전체(답)를 돌려준다 — 화면이 아니라 관문이 사건을 어떻게 다루는지가 주제인 스펙이 쓴다. `notificationSettingsOf(context)`·`notificationCategoryOn(context, category)`는 API로 읽고, `notificationSettingBox(page, category)`는 MY › 설정 '알림 수신' 카드의 스위치를 이름으로 찾으며, `switchNotificationCategoryOnScreen(page, category, enabled)`는 그 화면에서 스위치를 눌러 200·토스트·바뀐 값을 확인한다(`notification-settings.spec.ts`, 제한 중에도 바꾸는 `restrictions`·`account-restrictions` 스펙). 알림 fixture는 실제 관문으로 쓰므로, 어떤 분류를 끈 회원에게 그 분류의 fixture 알림을 기대하지 않는다.
- 대사 보류 복구 도우미(#145, ADR-0163): `helpers.ts`의 `recoverMarketHold(admin, approver, marketId, reason?)`는 `admin`이 그 시장의 대사를 실행하고(보류는 실행의 답에 함께 온다 — 깨끗한 대사는 근거일 뿐이다) 그 보류의 복구를 요청하며, 다른 관리자 `approver`가 승인한다(#93의 두 관리자). 돌아오면 보류가 복구되어 있다 — 원장 장애로 묶인 지급 중 시장의 지급은 워커의 다음 스캔이나 운영자의 정산 다시 시도로 이어진다(`operations.spec.ts`). 승인이 실패하면 남은 요청을 철회한 뒤 오류를 던진다. 화면의 같은 단계는 `reconciliation.spec.ts`가 본다.
- 작업 이력 확인(#145 2부, ADR-0164): `helpers.ts`에 도우미를 더하지 않았다. 시장별 작업 이력의 확인(`editTags`·`workHistoryOf`·`showWholeHistory`·`workRowIds`·`onlyEntry`·`checkWorkHistory`)은 그 흐름이 필요한 `operations.spec.ts` 안에 두었고, 셋째 시험(정산 중단·재시도)이 지급 완료 뒤 그 시장의 작업 이력과 둘째 시장의 기록이 섞이지 않음을 본다. 카테고리 변경 기록은 `categories.spec.ts`의 이름 바꾸기 뒤에 본다.
- 판정 오류 사건(#144 1부, ADR-0165): `judgement-error.spec.ts`는 워커(`skipUnlessResolvable` — 전역 설정의 이의 기간 1분과 매 분 스캔을 기다려 지급 완료를 본 뒤 사건을 등록한다)와 관리자 역할 잠금(`admin-role-fixture.ts`의 `test` — `no_decider`를 볼 때 다른 스펙의 임시 셋째 관리자가 끼지 않게)이 필요하다. `helpers.ts`에 도우미를 더하지 않았다 — 등록·검토 대기의 쪽 넘기기·남은 대기 사건의 철회는 그 스펙 안에 있다. 검토 대기는 오래된 것부터이고 같은 DB를 다시 쓸수록 앞 실행의 줄이 남을 수 있어(실패한 실행이 철회하지 못했을 때) 스펙은 제 줄이 보일 때까지 '더 보기'를 누르고 줄 수를 세지 않는다. 일반 구성의 샤드에 시험 단위로 나뉘므로(`fullyParallel`) 따로 등록할 샤드 목록은 없다. 함께 다시 돌릴 스펙: `settlement`·`correction`·`judging-record`·`judgement`·`dispute`·`operations`(작업 이력)·`admin-writes`.
- 판정 오류 보상(#144 2부, ADR-0166): 같은 파일의 두 번째 시험이 도우미의 두 회원(`helperTraders` — `closeMarket`의 한 쌍에서 NO를 산 첫째가 더 받을 회원, YES를 산 둘째가 더 받은 회원)으로 사건을 API로 등록·확인한 뒤 화면에서 보상을 요청·승인하고, 두 회원의 지갑·복기·MY 정산 이력·알림을 각자의 세션(`storageState`)으로 본다. 도우미 회원은 같은 워커의 다른 시장에서도 거래하므로 잔고 대신 그 시장의 원장 줄(`/me/ledger?marketId=`)을 비교한다. 실패한 실행이 남긴 기다리는 보상 요청은 `finally`에서 철회한다. 지갑의 유형 필터가 일곱째('판정 오류 보상')를 얻어 `orders`·`regrant`의 선택지 단정도 함께 바꿨다. 함께 다시 돌릴 스펙: 위에 더해 `my`·`notifications`·`judgement-notifications`·`orders`·`regrant`.
- 관측 지표(#96, ADR-0169): `helpers.ts`에 도우미를 더하지 않았다. `observation-metrics.spec.ts`는 있는 `signUp`·`meOf`·`createOpenMarket`·`postThroughApi`·`commentThroughApi`·`expectNoSideScroll`을 쓰고, 신고(`POST /api/v1/posts/{id}/reports`)와 기각(`POST /api/v1/admin/reports/dismiss`)은 스펙 안에서 API로 보낸다. 값은 증가(`≥`)로만 본다. 메뉴의 새 링크는 맨 끝이라 앞 자리가 그대로다 — 함께 다시 돌릴 스펙: 메뉴를 누르는 `operations`·`dispute`·`market-review`·`categories`·`reports`·`admin-accounts`·`admin-sms`.
- 방문 기반 관측 지표(#151, ADR-0170): `helpers.ts`에 도우미를 더하지 않았다. `observation-metrics.spec.ts`의 셋째 시험은 있는 `helperTraders`·`createOpenMarket`·`closeMarket`·`judgeMarket`·`watchThroughApi`·`signUp`·`signIn`·`meOf`를 쓰고, 시장 상세가 보내는 `POST /api/v1/me/market-visits`를 `waitForResponse`로 기다린다(204, 본문에 시장과 `expectedAccountId`, 경로에 시장 없음). 이어지는 DB에서는 0082를 적용한 주까지 두 방문 표가 '자료 없음'이라, 두 표의 수는 그 주의 `noData`가 거짓일 때만 비교하고 참이면 `skip-reason` 주석을 남긴다(CI의 새 DB는 0082가 시드보다 먼저라 자르지 않는다). `release-settings.spec.ts`의 보존기간 목록에 `retention.market_visits`를 더했고 '전체 N개 · 미정 N개'는 `SHIPPED_KEYS`에서 계산돼 하나씩 는다. `global-setup.ts`는 그 값을 넣지 않는다(승인된 값이면 워커가 스펙의 방문을 지운다). 시장 상세마다 방문 POST가 하나 늘었다 — 함께 다시 돌릴 스펙: 상세를 여는 `market`·`orders`·`order-panel`·`settlement`·`judging-record`·`watchlist`·`dispute`·`notifications`·`onboarding`·`retention`·`release-settings`·`observation-metrics`.
- 가입 허용 목록(#330, ADR-0174): `helpers.ts`에 도우미를 더하지 않았다. 목록은 DB 전체에 걸리므로 `signup-allowlist.spec.ts`가 번호를 넣은 동안에는 다른 스펙의 `freshPhone()` 가입이 모두 거절된다. 그래서 그 시험은 시작 전(앞 실행이 남긴 것)과 `finally`에서 두 시드 관리자의 비우기(한 관리자의 요청, 다른 관리자의 승인 — API)로 목록을 비운다. 한 샤드는 `workers: 1`로 시험을 차례로 돌리고 샤드마다 DB가 따로이므로 다른 스펙은 빈 목록만 본다 — `--workers`로 이 조건을 덮으면 안 된다. 소셜 가입은 e2e에 경로가 없어 api의 `signup-allowlist.controller.test.ts`가 맡는다. 관리자 메뉴의 새 링크는 '운영자 계정' 바로 다음이라 앞의 다섯과 맨 끝('관측 지표')은 그대로다 — 함께 다시 돌릴 스펙: `onboarding`·`phone-verification`·`admin-accounts`·`admin-writes`, 메뉴의 자리를 단정하는 `operations`(앞의 다섯)·`dispute`·`market-review`·`observation-metrics`(맨 끝).
- 출시 설정 변경의 묶음별 승인(#331, ADR-0175): 미정에서 값을 넣는 것은 거의 모두 2인이라 `global-setup.ts`가 두 시드 관리자를 먼저 로그인시키고, 첫째 관리자가 요청하고 둘째 관리자가 승인하는 `changeReleaseSettingAs`(`helpers.ts`)로 값을 넣는다 — `ensureDisputeWindow`·`ensureStartCoin`·`ensureRegrantSettings`·`ensureOrderSettings`는 두 관리자(`{requester, approver}`)를 받고, `market-maker-setup.ts`의 위험 단계 세 값도 같다(주문 속도 제한은 미정에서 넣기가 1인이라 바로 반영된다). 넣는 항목은 그대로 열넷이다. 도우미는 같은 변경의 요청이 이미 기다리면(`request_pending`, 다른 실행) 요청하지 않은 쪽이 그 요청을 승인하고, 그 밖의 거절은 다시 읽어 값이 들어 있으면 통과한다 — 두 번 돌아도 안전하다. `release-setting-approvals.spec.ts`는 화면에서 2인 흐름(요청 → 요청자는 철회만·자기 승인 409 → 다른 관리자의 반려 → 다시 요청 → 승인 → 변경 기록 '2인 승인')과 1인 흐름(재지급 누적 상한 낮추기 → '1인 즉시')을 보고 두 항목을 `finally`에서 되돌린다. `admin-writes.spec.ts`의 보존기간 되돌림도 `changeReleaseSettingAs`를 쓴다. 함께 다시 돌릴 스펙: 전역 준비가 바뀌어 기본 회귀 전체와 `test:e2e:market-maker`·`test:e2e:treasury`.
- 화면 인수 시험(#189 2부, ADR-0178): #189의 수용 기준으로 세는 시험은 제목 끝에 `@ac189-<기준 번호>`(1\~12, 둘 이상이면 공백으로 이어 씀)를 단다. Playwright가 제목의 태그를 JSON 결과의 `tags`에 넣고 요약 스크립트가 태그 표로 센다(아래 '로컬 요약'). 기본 config의 `grepInvert`에 걸리지 않아 일반 회귀 샤드에서 그대로 돈다. 공통 도우미는 `acceptance.ts`에 있다 — `asMember`(도우미 회원 같은 다른 회원의 `storageState`로 지금 폭의 페이지를 연다, 닫는 것은 부른 쪽), `expectNoExcludedText`(기준 11: 렌더된 화면·알림함의 `innerText`에 `findExcludedText`의 `probability-input`·`scoring`이 없음, docs/GUARDS.md), `expectNoPrivateFigures`(기준 10: 다른 회원의 잔액·보유·주문 수치가 글자에도 HTML에도 없음 — 다른 수와 겹치지 않는 값을 고른다), 주문 패널의 `openPanel`·`fillOrder`·`openReview`·`orderOnPanel`(`order-panel.spec.ts`에서 옮김), `expectNotCollapsed`(기준 5: 확인 행이 접힌 영역 밖에서 화면 안에 보임, 375 Chromium 하나 — 189-2. 그 시험은 1280에서 건너뛰어 요약에 skipped로 남는다), `expectOrdersOnMy`(기준 1: API가 답한 그 시장의 보유·대기 주문·끝난 주문·체결이 MY 세 화면에 있음), `openSettlementRecords`(그 시장으로 거른 MY 정산 기록 — 도우미 회원은 다른 시장에서도 거래하므로 시장으로 걸러 센다). 새 시험 넷: `order-panel.spec.ts`의 모바일 주문 확인(375만)과 연결 끊김 뒤 복귀(컨텍스트 오프라인과 `routeWebSocket`으로 끊은 실시간 소켓), `market.spec.ts`의 실제 체결(1일 차트의 5분 격자 경계를 서버 시계로 기다리는 두 체결 — 한 번에 최대 5분, `test.slow()`), `discussion.spec.ts`의 비공개 비노출. 함께 다시 돌릴 스펙: 태그를 단 스펙 전부(`--grep @ac189`), 특히 시간이 늘어난 `market`·`order-panel`·`judgement-notifications`·`operations`·`settlement`·`pause`·`account-restrictions`·`restrictions`·`judgement-error`·`discussion`·`reports`.
- `--list`는 서버·global setup·DB 연결 없이 각 구성의 시험 목록을 확인한다. 실 실행의 통과를 대신하지 않는다.

완료 보고에는 일반 3샤드 및 전용 두 구성의 passed / failed / flaky / skipped를 각각 기록하고 중복 없는 합계를 낸다. 이 수는 실행이 남긴 결과 파일에서 요약 스크립트로 낸다(#189, ADR-0178).

- **결과 파일.** 실행마다 Playwright의 JSON 리포트가 `apps/web/e2e-results/<구성>[-shard-<i>-of-<n>].json`에 남는다(`playwright.config.ts`의 `e2eReporters`). 구성 이름은 `general`(일반 회귀)·`market-maker`(실제 봇 호가)·`treasury`(부족 금고)다. 실행마다 비워지는 `playwright-report/`·`test-results/` 밖에 두므로 로컬 3샤드는 파일을 하나씩 남기고, 같은 구성·샤드를 다시 돌리면 HTML 리포트처럼 그 파일을 덮는다. 리포터의 다른 출력(콘솔·HTML·`github`)은 그대로다. `--list`는 결과 파일을 쓰지 않는다. 다른 경로는 `PLAYWRIGHT_JSON_OUTPUT_FILE`로 준다(프로젝트마다 따로 돌 때, 루트 README).
- **로컬 요약.** 세 구성을 모두 돈 뒤 저장소 루트에서 `node apps/web/scripts/e2e-summary.mjs --sha "$(git rev-parse HEAD)" --expect general --expect market-maker --expect treasury apps/web/e2e-results`를 돌리면 `e2e-summary/`에 `e2e-summary.md`와 `e2e-summary.json`을 쓴다. 구성별·결과 파일별 passed / failed / flaky / skipped / did not run / interrupted, 같은 시험을 한 번만 센 합계, `@ac189-N` 태그 표, 통과하지 못한 시험이 들어간다. 빠진 구성·샤드·프로젝트, 시험 밖 오류(global setup·서버 기동), 중단되거나 돌지 않은 시험, 두 파일에 함께 있는 시험이 있으면 '불완전'과 그 까닭을 적는다. 앞 실행의 파일이 섞이지 않게 새로 돌기 전에 `apps/web/e2e-results/`를 비운다.
- **CI.** e2e job마다 통과한 실행에도 결과 파일을 artifact `e2e-results-<job id>`로 90일 남긴다. 실패한 job의 HTML 리포트·trace·서버 로그(`playwright-report-<job id>`)는 그대로 실패할 때만 7일이다. `E2E Results Summary` job이 모든 결과를 모아 같은 요약을 job 요약 화면과 artifact `e2e-summary-<sha>`(90일)로 남긴다. 실패한 시험은 이 job을 실패시키지 않는다(그 e2e job이 이미 실패한다). e2e job이 모두 통과했는데 요약이 불완전할 때(결과가 빠짐, 시험 밖 오류, 중단되거나 돌지 않은 시험, 두 파일에 함께 있는 시험, 읽을 수 없는 파일 따위)만 실패하고, 취소된 실행에서는 돌지 않는다. 출시 점검(#149)은 배포한 sha의 main CI 요약만 인정한다(149-2a, ADR-0178).
